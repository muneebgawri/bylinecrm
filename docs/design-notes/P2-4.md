# P2-4 — email templates: variables, a safe render, the outreach footer

Issue #57. Doc 48 FR-CRMS-3 (templates), FR-CRMS-7 (unsubscribe), FR-CRMS-12 (postal address); doc 50
§C (the template editor). No Gmail dependency: this package is the template store, the variable
registry and the one renderer that preview (now), send (P2-3) and sequences (P3) use.

## Data

| Table                     | What                                                                                                                                                                                              |
| ------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `email_templates`         | `name`, `kind` (`personal` \| `outreach`), `subject` (text with `{{path}}` tokens), `body` (rich-text JSON — the notes' shape, restricted to the template subset), `version`, actors, soft delete |
| `workspace_mail_settings` | one row per workspace, absent until first saved: `postal_address` (structured), `default_sender_name`, `unsubscribe_footer_text`                                                                  |

Both are tenant tables in P0-2's shape (`workspace_isolation`, FORCE); the app role has SELECT,
INSERT, UPDATE and no DELETE. `email_templates` checks `version >= 1` and that `body` is a `doc`.
`created_by`/`updated_by` are `Actor` JSON, as on records, so an API key can write a template.

## The variable registry (`packages/shared/src/templates.ts`)

One list, `TEMPLATE_VARIABLES`: `person.firstName|lastName|fullName|email|jobTitle|city`,
`company.name|domain`, `deal.name|amount`, `sender.firstName|fullName|signature`. Custom fields are
`<source>.custom.<key>` for `person`, `company` and `deal` (the opportunity object).

**Deviation from the card:** the card wrote custom variables as `custom.<key>`. A key is unique per
object, not per workspace — `beat` can be defined on both a person and a company — so `custom.beat`
would be ambiguous. The source is therefore part of the path. `custom.<key>` alone is refused as an
unknown variable.

Variables are **nodes** in the body (`{ type: 'variable', attrs: { path } }`), never text, and
`{{ path }}` tokens in the subject. On save every path must be in the registry or name an **active**
custom field of its source; an unknown one is `400 validation.failed` with a field error at its
place (`subject`, or `body.content.1.content.0`). `GET /templates/variables` lists the registry and
the workspace's custom fields for the editor.

`sender.signature` is the one optional variable: no signature is stored yet (a member profile adds
it), and an email without one is a normal email, so it renders empty. Every other variable with no
value makes the render unsendable. `sender.firstName` is the first word of the member's display name.

`deal.amount` formats through the one money formatter, now in `packages/shared/src/money.ts`
(`formatMoneyIn(money, locale)`), in `TEMPLATE_RENDER_LOCALE` (`en-US`) because the recipient's locale
is unknown. **Owed:** the web app's `apps/web/src/lib/money.ts` still has its own copy of the
fraction-digit rule; it should delegate to the shared one (outside this package's files).

## The template subset

`TEMPLATE_BODY_NODES` (paragraph, heading, bulletList, orderedList, listItem, hardBreak, text,
variable), `TEMPLATE_BODY_MARKS` (bold, italic, link), headings at levels 2 and 3, links to `https:` or
`mailto:` only. Checked on save (`bodyProblems`: one field error per problem, at its path) **and**
again on render, where anything else is dropped. Two lines, the first being the refusal.

## The render (one place)

`RenderService.render(template, { personId, dealId?, senderMemberId? })` → `{ subject, html, text,
missing, sendable }`. It reads the person, the deal and the person's company under the caller's
policies — `recordWhere`, so an own-scoped caller's preview of another owner's person is `404`, the
same answer reading it gives — and composes with three pure functions:

- `renderBody` (`render/serializer.ts`): an **allowlist**, not a sanitiser. Only the subset becomes
  markup; no attribute is ever copied from the document except a link's `href`, which must be
  `https:`/`mailto:` (with no surrounding whitespace) and is escaped. Text and values are escaped.
  Marks apply in one fixed order (link ⊃ bold ⊃ italic) whatever order they arrive in. The text
  alternative comes from the same walk (lists as `- ` / `1. `, a link as `text (href)`).
- `renderSubject`: tokens filled; values are not escaped (a subject is text).
- `composeEmail`: subject + body (+ footer for outreach), `missing` de-duplicated in order of first
  use, `sendable = missing.length === 0`.

**A missing variable is never blank.** It is named in `missing`, marked in the HTML as
`<span data-missing-variable="path">{{path}}</span>` (the editor's preview highlights it), and kept as
`{{path}}` in the subject and the text. There is no partial render that blanks a variable; the send
path refuses anything not `sendable`.

## The outreach footer (FR-CRMS-7, FR-CRMS-12)

Not part of the stored body, so no edit can remove it: `composeEmail` appends it on every render of
an outreach template — `<hr>`, the workspace's unsubscribe notice with an **Unsubscribe** link to
`UNSUBSCRIBE_URL_PLACEHOLDER` (`{{unsubscribe_url}}`, which the send path in P3 replaces per recipient
and which is not a variable), and the postal address. With no postal address set, the render names
`workspace.postal_address` in `missing` and is not sendable.

## Rules on the data, not the route

- **Outreach needs `outreach:write`.** The routes are gated by `template:read` / `template:write`
  (preview by `template:read` + `record:read`). Whether a template is outreach is in the data, so the
  service checks it: creating, editing, deleting, restoring or duplicating a template that **is or
  would become** `outreach` without `outreach:write` is `403`. This is a field-level rule like an
  own-scoped member's owner reassignment, not a second copy of a route gate.
- **Optimistic concurrency.** A PATCH names the version it edited — body `version` or `If-Match`
  (`3`, `"3"`, `W/"3"`); neither is `400` at `version`, both disagreeing is `400`. A stale version is
  `409 conflict` ("…since version 1; it is now version 2"). The write is `updateMany where version =
the read one`, so a concurrent writer between the read and the write also gets the `409`.
- **A no-op writes nothing** (P1-4a's rule): a PATCH whose result equals the stored template leaves
  `version` and `updatedAt` alone and publishes no event.

## Events

`template.created|updated|deleted|restored` join the catalogue with the object `template`. They
leave no timeline entry (a template is on no record; the timeline subscriber writes nothing for a
non-record, non-linked object) and webhooks may subscribe to them. A duplicate is a `created`.

## What later packages add

- **P2-UI-2** builds the editor on `GET /templates/variables`, the subset constants and `preview`.
- **P2-3 / P2-5** send through `RenderService` and refuse a render that is not `sendable`; the
  sender's signature arrives with a member profile.
- **P3** resolves `{{unsubscribe_url}}` per recipient and adds the one-click endpoint.
