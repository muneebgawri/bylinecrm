# P0-7 — One ESLint config: `apps/api` adopts `@bylinecrm/eslint-config`

**Issue:** #18. **Rule served:** doc 49 §0, no divergence — one definition of the lint floor.

## What moved

- `apps/api/eslint.config.mjs` was a full copy of the floor (`@eslint/js` recommended,
  `typescript-eslint` recommended, the three repo rules) kept in step with `packages/eslint-config/base.mjs`
  by nobody. It is now two lines importing a new entry point, `@bylinecrm/eslint-config/nest`.
- `nest.mjs` = `base` + Node globals for `*.ts/*.mts/*.cts` + two type-aware rules (below), with type
  information from the package's own tsconfig through typescript-eslint's project service. The
  package's `eslint.config.mjs` needs no wiring; `tsconfigRootDir` is the package directory ESLint runs in.
- `apps/api` drops its direct `@eslint/js`, `globals`, `typescript-eslint` devDependencies and depends on
  `@bylinecrm/eslint-config` like `apps/web` and `packages/ui` already do. Its `lint` script also covers
  the two `*.mts` vitest configs it was skipping.
- Root `lint-staged` had three per-package entries, each naming its config file by path. It is now one
  glob for `**/*.{ts,tsx,mts,mjs}` running `prettier --write` and one `eslint --fix --max-warnings 0`;
  ESLint resolves each staged file's nearest `eslint.config.mjs` with `--flag v10_config_lookup_from_file`
  (the stabilised name in ESLint 9.39; the `unstable_` spelling is rejected). A second glob formats
  `json/yml/md`. Files that belong to no package with a config of its own (`scripts/*.mjs`,
  `packages/eslint-config/*.mjs`, the root config itself) made the lookup fail with "couldn't find an
  eslint.config", so the repo root now has a two-line `eslint.config.mjs` importing `base`; per-file
  lookup still finds a package's own config first, so it overrides nothing. Verified from the repo root
  against one file from each of api, web, ui, two `scripts/`, the config package and the root config:
  exit 0; a probe file with an un-awaited promise under `apps/api` is caught (`no-floating-promises`)
  through that same root invocation.

## Rules newly applied to `apps/api`

| Rule                                      | Why it belongs on a Nest service                                                                                            | Findings on main |
| ----------------------------------------- | --------------------------------------------------------------------------------------------------------------------------- | ---------------- |
| `@typescript-eslint/no-floating-promises` | a handler or job that forgets to `await`/`return` a promise reports success before its work ran, and swallows the rejection | 0                |
| `@typescript-eslint/await-thenable`       | `await` on a non-promise hides a missing call (`await service.method` without `()`)                                         | 0                |
| `*.mts` now linted (vitest configs)       | they were outside the old glob                                                                                              | 0                |

Nothing was weakened: every rule the old api config enabled is in `base` with the same options
(`no-async-promise-executor` was listed explicitly there and is already part of `js.configs.recommended`,
so it still applies). The old comment's reason for _not_ enabling type-aware rules — "correctness belongs
to `pnpm typecheck`" — is true for what `tsc` can see; the two rules above are exactly what it cannot.

## What was not changed, and why

- `packages/shared` still has `lint: echo …` although it has sources (`src/*.ts`). That is a second
  divergence of the same kind and belongs in its own small card (it should import `base`); out of this
  card's scope (`packages/eslint-config`, `apps/api/eslint.config.mjs`, root `lint-staged`).
- No `eslint-disable` was added and no rule option was loosened.
- A fresh worktree typechecks `apps/api` only after `pnpm --filter api prisma:generate` (stale generated
  client, not a code error); README's worktree note already says `pnpm install` + build shared — generate
  belongs on that line too (README is outside this card; noted for the next README touch).
