# P1-5a — A sweep resumes, never restarts (#97)

**Problem.** Each backstop sweep read "the N oldest candidates" per pass and skipped those with a
live job. When the first N all had live jobs, a genuinely lost row behind them was never reached —
the cap limited _coverage_, not just work per pass.

**Fix: one helper, `infra/resumable-sweep.ts`.** A pass reads candidates in keyset order
`(time, id)` — ties at a page boundary are neither skipped nor read twice — a page at a time, up to a
per-pass cap, and stores where it stopped in Redis (`bylinecrm:sweep-cursor:<name>`, 24 h TTL, shared
by every worker and kept across restarts). The next pass resumes there; a pass that reaches the end
clears the cursor, so the next starts over. Every candidate is therefore examined within
`ceil(backlog / cap)` passes.

**Applied to every capped sweep:**

| Sweep                           | Order                                                                          | Page / cap per pass |
| ------------------------------- | ------------------------------------------------------------------------------ | ------------------- |
| Webhook deliveries (P1-5)       | `createdAt, id`                                                                | 500 / 5,000         |
| Mail sends (P2-5)               | `createdAt, id` (was `sendAt, createdAt`; every due row is visited regardless) | 200 / 2,000         |
| Sequence steps due (P3-3)       | `nextRunAt, id`                                                                | 500 / 5,000         |
| Sequence outcomes missed (P3-3) | `createdAt, id`                                                                | 500 / 5,000         |

**Reviewed, unchanged:** the mail-sync tick reads every connected mailbox with no cap, so nothing
can hide behind anything.

**Tests.** `resumable-sweep.spec.ts`: coverage across passes, the end clears the cursor, tied times
at a page boundary. `webhooks.spec.ts`: 600 deliveries with held live jobs and one lost delivery
behind them — the lost one is re-enqueued within `ceil(601/500)+1` passes (on main it never is).
