# P1-1b — Opportunities, notes, tasks, attachments, members summary

**Package:** doc 49 §5, Phase 1 (P1-1 split a/b). **Loop step 2 (design).** Closes #13. Spec: doc 48 §5; parity
ledger PAR-007 (opportunity), PAR-010 (note, note targets), PAR-011 (task), PAR-013/014 (targets, linked
activities), PAR-016 (attachment). Conventions: P1-1a's design note, followed exactly.

## Data touched

Six tenant tables (migration `20261009000400_deals_notes_tasks_attachments`), every one under row-level
security in P0-2's shape; `opportunities` is owner-bearing and carries P1-1a's restrictive `owner_scope`
policy too. Two columns on existing tables: `workspaces.default_currency` (read here, edited by a later
settings package) and `workspace_members.display_name` (see _Members summary_).

| Table           | What                                                                                                                                                            | Owner-bearing | Custom fields |
| --------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------- | ------------- |
| `opportunities` | PAR-007: name, exact amount in minor units + currency, close date, probability, owner, point of contact, company, actor, `custom`, trash. **No stage columns.** | yes           | `opportunity` |
| `notes`         | PAR-010: title, rich-text `body`, derived `body_text`, author, actor, trash.                                                                                    | no            | —             |
| `note_targets`  | One row per record a note is on; `(note, target)` unique.                                                                                                       | no            | —             |
| `tasks`         | PAR-011: title, body, `status`, due, assignee, `completed_at`, actor, trash.                                                                                    | no            | —             |
| `task_targets`  | As note targets.                                                                                                                                                | no            | —             |
| `attachments`   | PAR-016: name, `storage_key` (unique), mime, size, one target, author, actor, trash.                                                                            | no            | —             |

**Amounts are exact.** `amount_minor` is a `BIGINT` in the currency's minor unit, exposed as `amount:
{ amountMinor, currency }` and sorted on directly; sums in P1-2's pipeline views never round. A company's ARR
stays the reported decimal (`Money`) it already was — two types because they are two things (`MinorMoney` is the
arithmetic one), both named in `@bylinecrm/shared`. A deal always has a currency: the caller's, or the
workspace's default when none is named. `amount: null` on patch clears the amount and keeps the currency.

**Targets are polymorphic and have no foreign key.** `target_type` is the `record_object` enum (so a target is
anything a custom field can be on) and `target_id` is the row; records are only ever soft-deleted, so a target
never dangles, and the service checks every target before writing it. Custom objects (P4-3) extend the enum, not
the table shape.

**Generated columns** as in P1-1a: the search vectors (`opportunities.name`; notes' and tasks' title + body text)
are built by the database; `migrate diff` reports no drift.

## Stage and pipeline — reserved for P1-2

P1-2 adds `pipeline_id`, `stage_id` and the stage-history table beside `opportunities`, and the `deal:move`
routes. This package deliberately leaves no nullable placeholders for them: a column that nothing writes is a
column whose meaning is undefined.

## Visibility follows the targets — one rule, one function

Notes, tasks and attachments carry no `owner_id`. Who may see one follows from the records it is on:
`readableTargets(tx, targets)` looks the targets up **in the caller's transaction**, so the workspace policy and,
for an own-scoped caller, the restrictive owner policy decide what "can see" means — the function adds no rule
of its own. Three callers, one definition:

- **Writing** (`assertTargetsReadable`): every target named on create or on a `targets` replace must be a live
  record the caller can see — `422`, naming the first that is not, so a target outside the caller's scope reads
  as missing (P1-1a's no-existence-leak rule, now for targets).
- **Reading** (`anyTargetReadable`): a note or attachment is visible when the caller can see at least one of
  its targets; `404` otherwise, including in the trash. Listing is by target (`?target=person:<id>`), and a
  target the caller cannot see "has no notes" (`404`), never an empty page that would confirm it exists.
- **Tasks** add the assignee: a task is visible to its assignee whether or not they can see its targets — it is
  their work. Listing by `assigneeId` is one's own list; a caller whose role sees every record may list anyone's,
  an own-scoped caller only their own (`403`: refusing leaks nothing about another member's tasks). A list names
  a target or an assignee, never both and never neither (`400`).

The row-level policies on the six tables scope them to the workspace; the per-record narrowing above is the
service's, by design: a policy on `note_targets` that joined three record tables under their own policies would
be a second, slower copy of the same rule.

## `completedAt` — the one rule

`completedAtFor(next, previous, now)` in `task-rules.ts`: the instant a task becomes `done`, kept while it stays
`done`, cleared the moment it leaves. The service is the only writer; the database checks the two columns agree
(`CHECK ((status = 'done') = (completed_at IS NOT NULL))`), so a second writer that disagreed would fail.

## Rich text

A note's or task's `body` is the editor's ProseMirror document, stored as given (the API validates the root and
node shape, never the semantics). `body_text` is derived from it on **every** write by `richTextToPlain` — one
function — and is what the search vector and previews read. There is no second path that writes a body.

## Attachments and the storage interface

`FileStorage` (`infra/storage`): `put(key, stream)`, `get(key)`, `delete(key)`. `LocalDiskStorage` is the driver
now (root from `FILE_STORAGE_ROOT`, default `.data/attachments`, git-ignored): writes go to a `.part` sibling and
are renamed into place, so a reader never meets a half-written file and a failed upload leaves nothing. A key is
`<workspaceId>/<uuid>`; the driver refuses any other shape and anything that would leave the root. An S3 driver
implements the same three methods and is swapped in `InfraModule`, nowhere else.

**Upload** is a streamed `multipart/form-data` body (`busboy`, one `file` field): the target is checked **before
a byte is stored**; bytes go to storage; the row is written; if the row fails the bytes are removed. The size cap
(`ATTACHMENT_MAX_BYTES`) is the parser's own limit, answered `413`; the content type is the client's declaration
checked against `ATTACHMENT_MIME_ALLOWLIST` (`415`) — a policy on the declaration, not a sniff of the bytes; a
sniff would be a later addition in `multipart.ts`, one place. **Download** streams through the API with
`Content-Disposition: attachment` and `Cache-Control: private, no-store`; there is no public URL to a file, and
the row — under the policies — is the only way to its key. Deleting is soft and keeps the bytes; restore is a
row change.

## Members summary

Owner, assignee and point-of-contact pickers need the workspace's members, and `GET /members` is admin-only
and carries emails. `GET /api/w/:id/members/summary` (`record:read`) returns `{ memberId, name }` — the seat and
a display name, nothing that identifies the account. `workspace_members.display_name` is new: set at creation
to the local part of the member's address (`displayNameFor`, one function in `AuthService`, both creation
paths) and backfilled by the migration; a profile route to change it is owed (P1-UI-3 raises it). `avatarUrl`
is not returned because nothing stores one yet — a field that is always `null` is a lie about the contract.

## Events

The catalogue in `@bylinecrm/shared` grows `opportunity.*`, `note.*`, `task.*` and `attachment.created|deleted|
restored`. `EVENT_OBJECTS` is the record objects plus `note`, `task`, `attachment`; note, task and attachment
events carry `targets`, so the timeline (P1-3, PAR-014) can write an entry on each record without a lookup.
Published after `withWorkspace` returns, as before.

## The contract

`apps/api/openapi.json` regenerated in this PR (the snapshot test enforces it); the Prism mock serves the new
paths. Capabilities: deals read with `deal:read` and write with `deal:edit`; notes and tasks read with
`record:read` and write with `note:write` / `task:write`; attachments read and write with `record:read` /
`record:write`. Every tenant route declares its gate; the router-walking test still finds exactly one
`@AnyMember` route.

## Failure modes

| Failure                                                     | Behaviour                                               |
| ----------------------------------------------------------- | ------------------------------------------------------- |
| Target outside scope, in another workspace, or deleted      | Write `422` naming it; read `404`.                      |
| No target on create, or `targets: []`                       | `400` (DTO).                                            |
| Point of contact / company / assignee not visible or member | `422`.                                                  |
| Own-scoped caller lists another member's tasks              | `403`.                                                  |
| Own-scoped caller names another owner on a deal             | `403` (P1-1a's rule).                                   |
| Upload too large / type off the allowlist / not multipart   | `413` / `415` / `400`; nothing stored.                  |
| Row write fails after the bytes landed                      | Bytes removed, error propagated.                        |
| Attachment row exists but storage lost the bytes            | `404 attachment content is missing` (said, not hidden). |
| Storage key of an unsafe shape                              | Driver throws; never reaches the disk.                  |
| A later table without its policy                            | `schema-invariants.spec.ts` (P0-2) fails CI.            |

## Not handled here — named

Pipelines, stages, stage history, `deal:move` (P1-2); the timeline (P1-3); listing notes/tasks across records,
filters, group-by (P1-4); permanent destroy and trash retention incl. attachment bytes (PAR-079's second half,
not v1); a profile route for `display_name`; member avatars; attachments on notes and emails (PAR-016 `watching`);
content sniffing of uploads; an S3 driver; editing `workspaces.default_currency`.
