# P2-2b — one message per workspace (#107)

**Defect (staging, 2026-10-11).** Mail between two connected mailboxes of one workspace was stored once per
mailbox: `mail_messages` was unique per `(mailbox, Gmail id)`, so matt@ → outreach@ became two rows with the same
RFC 822 Message-ID. Every consumer read rows, so the person timeline showed "sent" and "wrote" for one email, the
thread list showed two threads, counts doubled, and a reply seen by both mailboxes could be judged twice.

**Fix: the model, not the views.** A message is a workspace fact; a mailbox holding it is a copy. Twenty models the
same thing (one `message` keyed by its header Message-ID, one `messageChannelMessageAssociation` per channel holding
the external ids) — its logic was read (D-243), nothing copied.

## Model

| Table                 | Was                             | Now                                                                                                                                                                                                                                                                                                                                      |
| --------------------- | ------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `mail_messages`       | one row per mailbox copy        | **one logical message per workspace**, unique on `(workspace_id, identity_key)`. `identity_key` is the RFC 822 Message-ID (Gmail's own — Gmail rewrites ours, #87); a message without one (rare, malformed mail) is keyed `gmail:<mailbox>:<gmail id>` and never merges. No `mailbox_id`, `provider_message_id` or `label_ids` any more. |
| `mail_message_copies` | —                               | **one row per mailbox holding the message**: `mailbox_id`, `provider_message_id` (unique per mailbox — the sync's dedupe key, as before), `mailbox_thread_id`, `direction` _from that mailbox's view_, `label_ids`.                                                                                                                      |
| `mail_threads`        | one Gmail thread in one mailbox | **one logical conversation per workspace**. No `mailbox_id` / `provider_thread_id`.                                                                                                                                                                                                                                                      |
| `mailbox_threads`     | —                               | **a mailbox's Gmail thread → the logical thread**, unique `(mailbox_id, provider_thread_id)`. A reply goes into _its mailbox's_ Gmail thread through this.                                                                                                                                                                               |

`mail_participants` stay on the logical message (one set of addresses per email). Grants follow the old tables:
messages, copies and mailbox threads are `SELECT, INSERT, DELETE` (the blocklist purge deletes); nothing updates a
message or a copy.

## The writer (sync's `store`, the one path for every import)

1. The copy `(mailbox, Gmail id)` is already stored → nothing (a duplicate, as before).
2. The logical message exists (`identity_key`) → **only the copy is written**: its `mailbox_threads` row is created
   pointing at the message's thread if the mailbox has none for that Gmail thread. No participants, no events, no
   timeline: those happened when the message first arrived. An outbound copy is still linked to our send
   (`linkOutbound`) — the send's own mailbox may be the second to store it.
3. The message is new → its thread is, in order: the mailbox's mapped thread for that Gmail thread; else the thread of a
   message it names in `In-Reply-To` / `References` (so the first message one mailbox sees of a conversation another
   mailbox started joins it); else a new thread. Then message, participants, copy, events — exactly as before.

Threads are never merged. Two mailboxes' Gmail threads normally map to one logical thread (the second mailbox's first
copy is of a message already stored); if Gmail threads them differently, each mailbox's later mail follows its own
mapping, as in Twenty. Correctness never depends on threads: identity is the message.

**Direction of the logical message** (what the timeline says, "sent" or "received"): outbound when its `From` is the
address of any mailbox of the workspace, or the first copy is outbound; inbound otherwise. Internal mail between two
mailboxes is therefore "sent", once. The copy keeps its own mailbox's direction.

**Replies (`email.replied`, P2-3).** Judged once, when the logical message is created — never for a later copy. The
send it answers is found by header (our Message-ID or Gmail's, both on the send row) or by thread: the send's mailbox
maps the send's Gmail thread to the message's logical thread, and the message is not later than the send. A message
_from the send's own mailbox_ is never a reply to it. The rule no longer requires the message to be inbound from the
storing mailbox's view: a reply from outreach@ to matt@'s send may first be stored from outreach@'s _sent_ copy.

## Readers

- **Thread list / thread view:** logical threads; `mailboxIds` (every mailbox holding a copy of any message in it)
  replaces `mailboxId`. Visibility per message: its owner-of-a-copy sees everything; otherwise a person it concerns
  must be readable, and bodies show when any copy is in a **pool** mailbox. `bodiesVisible` on the thread is true when
  every message's bodies are; each message carries its own `bodiesVisible` and `mailboxIds`.
- **Replying from the CRM:** the sending mailbox must hold a copy of the parent; the Gmail thread is that copy's.
- **Events:** `EmailSummary.mailboxId` is the mailbox whose copy first stored the message.
- **Blocklist purge:** judges each _copy_ by its mailbox's entries (unchanged rule), deletes the doomed copies, then
  deletes logical messages left with no copy (with their timeline entries), then empty threads and their mappings.
- **Disconnecting a mailbox** removes nothing (unchanged), so a message stays visible through every copy.

## Migration (`20261011004000_mail_message_identity`)

Deterministic, in one migration, against real duplicates (staging holds the 2026-10-11 test mail between matt@ and
outreach@):

1. Every old thread becomes a `mailbox_threads` row for its own mailbox; every old message becomes its own copy.
2. `identity_key` is set; duplicates are grouped by `(workspace_id, identity_key)`. The **keeper** is the earliest
   `created_at`, then the smallest `id`.
3. Each duplicate's copy moves to the keeper; sends pointing at a duplicate (`mail_outbound.mail_message_id`,
   `reply_to_message_id`) move to the keeper; a duplicate's timeline entry on a record the keeper already has an entry
   on is deleted, any other is re-pointed to the keeper. Duplicates (and their participants) are deleted.
4. Threads joined by a duplicate are one conversation (rows stored before this migration were threaded per
   mailbox): each connected group of them becomes its earliest thread; messages and mailbox mappings move to it and
   the rest are deleted.
5. The keeper's direction becomes outbound when any of its copies was outbound. Thread counts are recounted.

Webhook deliveries and outbox rows already sent are history and are not rewritten.
