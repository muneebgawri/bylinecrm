# P1-1d — one error envelope for every API error

Issue #44. P1-1c found three error shapes on the wire: Nest's `{ statusCode, message, error }`
(plus the validation pipe's `errors`), a 409 carrying `{ message, field }` with no status, and the
custom-field validator's `{ message, issues }`. The standing rule allows one definition.

## The envelope

```ts
{ statusCode, code, message, fieldErrors?: [{ path, message }], requestId }
```

- `code` is the stable machine name; a client branches on it, never on `message`.
- `message` is human and safe to show. A server error's message is always the generic one.
- `fieldErrors` appear only when the failure is about specific request fields. `path` is a dotted
  path into the request body (`emails.primary`, `custom.beat`). The key is absent, never `undefined`.
- `requestId` is also sent as the `X-Request-Id` header on **every** response, success included.

`ApiErrorBody`, `FieldError`, `ERROR_CODES`, `ERROR_CODE_FOR_STATUS`, `codeForStatus`,
`REQUEST_ID_HEADER` and `REQUEST_ID_PATTERN` live in `packages/shared/src/errors.ts` — the API's
filter, the OpenAPI `ApiError` schema (held to `ApiErrorBody` by a compile-time check) and the web
client all read them.

## The code table

| Code                     | Status | Raised by                                                                          |
| ------------------------ | ------ | ---------------------------------------------------------------------------------- |
| `validation.failed`      | 400    | a request DTO (zod), a custom-field value, an unparsable body, any `400`           |
| `unauthorized`           | 401    | no session / API key, a wrong password (same answer as an unknown email)           |
| `forbidden`              | 403    | a gate: not a member, a missing capability, CSRF                                   |
| `not_found`              | 404    | no such record, or one the caller cannot see (never told apart); an unknown route  |
| `conflict`               | 409    | a state conflict (a stage that still has deals, the last admin)                    |
| `conflict.unique`        | 409    | a unique violation (`UniqueConflict`); `fieldErrors` name the field when safe      |
| `gone`                   | 410    | an expired or used invitation                                                      |
| `payload_too_large`      | 413    | an upload over the cap, a body over the parser's limit, an export over the row cap |
| `unsupported_media_type` | 415    | a non-multipart upload, an unsupported body charset                                |
| `unprocessable`          | 422    | a well-formed request naming something unusable (another owner's company)          |
| `rate_limited`           | 429    | too many login attempts (`RateLimited`)                                            |
| `bad_request`            | 4xx    | any other 4xx (catch-all)                                                          |
| `not_implemented`        | 501    | a route whose package has not landed (password reset)                              |
| `internal`               | 5xx    | anything unexpected; generic message, stack logged under the request id            |

## Mapping rules (`apps/api/src/infra/errors/error.filter.ts`, `toErrorBody`)

1. `ApiException` (and its subclasses `ValidationFailed`, `UniqueConflict`, `RateLimited`): rendered
   as raised — status, code, message, field errors.
2. `ZodValidationException` (nestjs-zod's request DTO pipe): `400 validation.failed`, the fixed
   message "the request is not valid", one field error per zod issue at its dotted path.
3. Any other `HttpException`: its status; the code from `codeForStatus`; its message (a list is
   joined with `; `). A **5xx other than 501** gets the generic message instead.
4. Anything else (a thrown `Error`, a non-Error): `500 internal`, generic message; the filter logs
   `requestId method url: name: message` with the stack. Nothing internal is sent.
5. A response that was already streaming (an export failing after its first byte) is closed; the
   status cannot change any more, and the log has the cause.

Throw sites that used ad-hoc bodies now raise typed errors: the custom-field validator raises
`ValidationFailed` with `custom.<key>` paths; people/companies/roles/pipelines/custom-field
uniqueness raises `UniqueConflict` with its field; sign-up and invitation uniqueness raise
`UniqueConflict` **without** a field, because naming `email` would tell a caller an account exists;
`TooManyAttempts` is a `RateLimited` (it was an `UnauthorizedException` overriding its status).
Ordinary Nest exceptions (`NotFoundException`, …) stay — the filter codes them by status.

## Body parsing moved into `createApp`

Nest turns an express body-parser `SyntaxError` into a bare `BadRequestException` carrying the
parser's text ("Unexpected end of JSON input"), with nothing left to recognise it by. `createApp`
therefore creates the app with `bodyParser: false` and installs the same parsers Nest would
(`express.json()`, `express.urlencoded({ extended: true })`, default limits) followed by
`parserErrors`, which turns an exposed 4xx parser error into a typed one: `entity.parse.failed` →
`ValidationFailed("the request body is not valid JSON")`, anything else → `ApiException` with the
status's code. `express` (5.2.1, the version `@nestjs/platform-express` already uses; MIT) is now a
direct dependency of the API.

## Request id

`requestId` middleware (first in `createApp`, before the parsers) keeps an inbound `X-Request-Id`
that matches `REQUEST_ID_PATTERN` (letters, digits, `.`, `_`, `-`, 8–128) and otherwise generates a
UUID, stores it on the request and sets the response header. An application built without
`createApp` (the health boot test) still gets an id from the filter's fallback.

## OpenAPI

`ApiError` is now the exact envelope (`code` an enum of `ERROR_CODES`; `FieldError` a component);
the 501 response carries it too; every response documents the `x-request-id` header through one
`components.headers.RequestId`. Still 85 paths; `contract:check` passes.

## Web

`apps/web/src/api/client.ts` reads only the envelope: `ApiError` gains `code: ErrorCode` and
`requestId`. A body that is not the envelope (an edge proxy's 502 page) is coded with the same
`codeForStatus` and the status text. `FieldError` is the shared type, no longer redeclared.

## Tests

- `error.filter.spec.ts`: a golden body per kind; a 500 (and a 5xx `HttpException`) never carries
  the internal message, stack or host; every produced code is in `ERROR_CODES`.
- `body-parsing.spec.ts`, `request-id.spec.ts`: the parser mapping; id keep/replace rules,
  including a log-injection attempt.
- `test/cross-tenant/errors.spec.ts` (14 tests, all red on `main` first): every way the real app
  fails answers with exactly the envelope and a matching header; custom-field and unique failures
  arrive as `fieldErrors`; 404/403/422 bodies about another workspace's records contain none of
  its ids, names or emails.
- The anti-enumeration login test now compares the two refusals without their per-request ids.
