# P2-3 — Send from a connected mailbox, threaded replies, reply detection

Issue #56. Doc 48 FR-CRMS-2, FR-CRMS-3, FR-CRMS-9 and §6.1; parity ledger PAR-026, PAR-031, PAR-032, PAR-098.
Builds on P2-1 (mailboxes, `MailboxTokens`), P2-2 (sync, `GmailPort`, the one writer), P2-4 (templates,
`RenderService`), P1-2/P1-2a (stage rules, one move), P1-5 (webhooks), P1-1d (errors).

## The two halves

**The request (`POST /api/w/:id/mail/send`, `email:send`) decides everything and stores it built.**

1. **Mailbox.** It must be visible to the caller (`MailboxesService.get` — one rule), **personal**, **the caller's own**
   and **connected**. A pool mailbox is `403` ("sends only through sequences"); another member's personal mailbox is
   `403` even for an admin; a mailbox that is not connected is `409` (`MailboxUnavailable`). An API key is no one and
   has no mailbox: `403`.
2. **Recipients.** `to` defaults to the person's primary address; `{ personId }` resolves to that person's primary under
   the caller's record scope (`404` when unreadable, `422` when they have no address); `{ address }` is taken lower
   case; duplicates dropped. `SendPolicy.assertSendable(recipients)` is called on every send — today it checks there is
   someone to send to and at most `MAIL_SEND_RECIPIENTS_MAX` (50); **Phase 3's suppression and outreach gates go here**,
   so sending does not change when they arrive.
3. **Content — one path.** Either a template (`templateId`) or a written `subject` + `body`. A written body is checked by
   the templates' own rule (`TemplatesService.validateDraft`: inside the subset, only known variables) and rendered
   by the same `RenderService` a template is, as kind `personal`. **An outreach template is refused** (`422`): its
   unsubscribe link is resolved per recipient by sequences (Phase 3). **A render with any empty variable is refused**
   (`422 unprocessable`, `fieldErrors` naming each path) — nothing is queued, nothing is sent blank.
4. **Threading.** `replyToMessageId` must be a stored message **in the sending mailbox** (`400` naming the field
   otherwise; another workspace's message is `404`). The reply carries `In-Reply-To: <parent>` and
   `References: <parent's references> <parent>`, and is sent into the parent's Gmail thread. A reply with no subject of
   its own takes the parent's, prefixed `Re:` once — **as written, never rendered**, so braces in someone else's subject
   are not variables.
5. **Build and store.** `buildMime` (one builder, pure) → a `mail_outbound` row in status `queued` with the exact MIME,
   our `Message-ID` (`<uuid>@bylinecrm`, unique), recipients and context; then a BullMQ job whose id is the row's. The
   answer is `202 { messageId, status: 'queued' }`.

**The job (`MailSendService.deliver`) sends the stored MIME, exactly once.**

- A row already `sent` or `failed` is left alone (a repeated job sends nothing).
- A mailbox no longer `connected` fails the send at once (`reconnect_needed` / `mailbox_disconnected`), without
  calling Gmail.
- The send runs under sync's quota and per-request retry (`MailSyncService.gmailRequest`, `send` = 100 units).
- **A lost answer never sends twice.** Gmail's answer to a `5xx` or a timeout does not say whether the message went.
  So before every retry — and on a delivery after an attempt that already started (`sending`) — the job searches the
  mailbox for `rfc822msgid:<our id>`; a message Gmail already has is recorded as sent and not sent again.
- Gmail refusing the message for good (a non-transient error) fails the send. Every request failing transiently is
  recorded (`sending`, `last_error`) and **rethrown**, so the queue retries the job (`MAIL_SEND_JOB_ATTEMPTS`, 3,
  exponential from 30 s); after the last, the worker marks it failed (`markExhausted`).
- Once sent: status `sent`, Gmail's ids, `sent_at`; then **the message is stored through sync's one writer**
  (`MailSyncService.importMessage`) — the same parse and store a sync does. That writer announces it once
  (`email.sent`, on the person's timeline) and links it to the send. A later sync sees Gmail's id already stored and
  does nothing. If storing fails, the send is still sent; the next sync stores it.

## Statuses (PAR-098, resolved as ours)

`queued` → `sending` → `sent`, or `failed`. `GET /api/w/:id/mail/messages/:messageId` (`email:send`) shows a send to
its sender and to an admin, `404` to anyone else. Delivered / bounced / held belong to deliverability (FR-CRMS-6/7,
Phase 3).

## Reply detection — in sync's writer (`mail-sync/replies.ts`)

Every stored message passes one writer, so this happens exactly once, whichever path stored it:

- **Outbound** messages that are one of our sends are linked to it (`mail_outbound.mail_message_id`), by our
  Message-ID or by Gmail's id.
- An **inbound** message is a **reply** when it names one of our sends in `In-Reply-To` / `References` — our
  Message-ID, or the stored copy's (in case Gmail rewrote it) — or when it arrives **in the same mailbox's Gmail thread,
  after the send** (a thread match alone could pick up mail sync stored late that predates the send). It is announced
  as **`email.replied`**: `email` = the reply's summary, `related` = the people it is from and their companies (what the
  stage rules read), `reply = { messageId, inReplyToOutboundId, inReplyToMessageId, threadId, personIds, dealIds }`
  (deals: the senders' open deals as point of contact, plus the deal the send was about if still open).
- It writes **no timeline entry** of its own — the reply is already there as `email.received` — and webhooks deliver it
  once. The stage-rule engine (P1-2) moves the deal forward, attributed to the rule.

## Data (migration `20261010000100_mail_send`)

`mail_outbound` under RLS in P0-2's shape; SELECT / INSERT / UPDATE for the app role, **no DELETE** (what was sent
stays on record). Checks: at least one recipient; a `sent` row has Gmail's id and a time; addresses lower case.

## Decisions and deviations

- **A separate outbound table**, not a `sending` row in `mail_messages`: a stored message is what the mailbox holds and
  stays insert-only (P2-2); a send's progress is a different thing with its own lifecycle. The two are linked.
- **No signature is appended server-side** (Twenty does, PAR-031): the signature is the `sender.signature` template
  variable, so what is sent is what was previewed.
- **Tracking** (open pixel, rewritten links) is FR-CRMS-8, Phase 3 — not added here.
- **`MAIL_SEND_WORKER`** (default `1`) runs the job in this process; the cross-tenant suite sets `0` and delivers sends
  itself against the fake Gmail.

## What a later package needs to know

- Phase 3 (sequences): fill `SendPolicy.assertSendable`; send pool mail through `deliver`; resolve the outreach footer's
  unsubscribe URL per recipient before building the MIME.
- **To verify against real Gmail:** whether Gmail keeps a client-supplied `Message-ID` on `messages.send`. The design
  does not depend on it (replies also match the stored copy's Message-ID and the Gmail thread; the lost-answer search
  uses ours), but if Gmail rewrites it, the `rfc822msgid:` search before a retry would not find a message Gmail
  accepted, and a lost answer could send twice. The real-mailbox test should confirm it.
