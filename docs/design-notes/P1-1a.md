# P1-1a — Core records: people, companies, owner scope, custom fields, search, events, the contract freeze

**Package:** doc 49 §5, Phase 1. **Loop step 2 (design).** Closes #12. Spec: doc 48 §5; parity ledger
PAR-001…006 (person, company), PAR-003 (actor), PAR-004 (search), PAR-073/074 (custom fields), PAR-079 (trash),
PAR-084 (position).

## Data touched

Three tenant tables (migration `20261009000300_records`), all under row-level security in P0-2's shape:

| Table                      | What                                                                                                                                                                     | Owner-bearing |
| -------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------- |
| `people`                   | PAR-001: composite name, emails `{primary, additional[]}`, phones, job title, city, links, avatar, position, company, owner, `created_by` actor, `custom`, `deleted_at`. | yes           |
| `companies`                | PAR-005: name, domain, employee count, ARR (amount + currency), address, links, ICP flag, position, owner, actor, `custom`, `deleted_at`.                                | yes           |
| `custom_field_definitions` | One row per field a workspace added to an object: key, label, type, options, required, position, `archived_at`.                                                          | no            |

Plus `roles.record_scope` (`all` \| `own`, default `all`; the admin role is always `all`).

**Two columns are generated by the database.** `people.email_primary` is `lower(NULLIF(emails->>'primary',''))`
and `people.search` / `companies.search` are `to_tsvector('simple', …)` over the searchable text. They are
generated rather than written so the column the uniqueness index covers can never disagree with the JSON it is
derived from, and so search needs no second writer. Prisma knows them as `@default(dbgenerated(...))` with the
migration's exact expression; `prisma migrate diff` reports no drift, so `migrate dev` on a developer machine
proposes nothing.

**Uniqueness (PAR-002/006)** is a partial unique index per workspace over non-null values: a person's primary
email (case-insensitively, through the generated column) and a company's domain (stored lower-cased; a `CHECK`
refuses anything else). Deleted rows stay in the index, so a trashed record still holds its email — the ledger's
rule. The API answers `409` with the field that collided.

## Owner scope — the account-manager rule, applied twice

A role has a `recordScope`. For `own`, the workspace guard records the caller's member id as
`ownerScopeMemberId` in `WorkspaceContext`, and `withWorkspace` sets a second transaction-local setting,
`app.owner_member_id`, beside `app.workspace_id` (one place: `RlsPrismaService.scoped`). The migration adds one
SQL function, `app_owner_member_id()`, and a **RESTRICTIVE** policy on every owner-bearing table:

```
USING      (app_owner_member_id() IS NULL OR owner_id = app_owner_member_id())
WITH CHECK (app_owner_member_id() IS NULL OR owner_id = app_owner_member_id())
```

A restrictive policy ANDs with the permissive workspace policy, so an own-scoped caller can read, update, delete
and — through `WITH CHECK` — create only rows they own, whatever the application layer forgot. The application
layer does not forget: `ownerWhere()` adds the same filter to every read, and `resolveOwner()` decides who a write
may name (an own-scoped caller: themselves, always; anyone else: the requested owner, defaulting to themselves on
create and to the current value on patch). **The route is the gate; the policy is the backstop** (P0-2).

**404, not 403.** A record outside the caller's scope does not exist as far as they are concerned: `GET`, `PATCH`,
`DELETE` and `restore` answer `404`. A `403` would confirm the record exists and belongs to someone else — an
existence leak with no benefit, since the caller cannot act on it either way. The one `403` in the package is an
own-scoped caller naming another owner on their own record: nothing is leaked (it is their record) and the refusal
explains itself.

**API keys.** A key acts with a role; a role scoped `own` has no member to be "own" relative to, so the guard
refuses such a key with `403` rather than let it see an empty workspace and wonder why.

## The caller's standing — `GET /api/w/:workspaceId/me`

The UI shows or hides controls by what the caller may do (FR-CRMS-UI-6), and before this nothing told it:
`/api/me/workspaces` names workspaces only and `/members` is admin-gated. `GET /api/w/:id/me` returns
`{ workspaceId, memberId, userId, apiKeyId, roleId, roleName, recordScope, capabilities }` read straight from
`WorkspaceContext` as the workspace guard populated it — one source, no second computation (the guard now
records `roleId`/`roleName` beside the capabilities). It is the one tenant route without `@Requires`: a caller
asking what they may do cannot be asked for a capability first, so it is marked `@AnyMember(reason)` and the
router-walking test accepts that marker only with a written reason, and asserts this route is the only one.

## Custom fields

Definitions are rows; values live in each record's `custom` JSONB under the definition's `key`. One module,
`CustomValuesValidator`, builds a zod schema from the object's active definitions at request time: unknown keys,
wrong types, missing required fields (on create) and unknown select options are `400` with the path
`custom.<key>`. On patch, keys are merged one by one (a key set to `null` clears it); a required field cannot be
cleared. The built schema is cached in Redis per `(workspace, object)` and the cache entry is deleted on every
definition write, so a new definition applies on the next request; Redis being down degrades to reading the rows.

A definition is **never deleted**: `DELETE` archives it. An archived key is unknown to the validator from then on
(a write naming it is `400`), while values already stored are left alone. A definition's `type` is immutable;
label, options, required and position can change.

## Search

`?q=` matches the generated `search` vector (`plainto_tsquery('simple', q)`) or a prefix of the primary email /
domain. The candidate ids come from one raw query (RLS applies to it like any other, same transaction), capped at
`SEARCH_CANDIDATE_LIMIT`, and the page is then ordered and cut by the ordinary query — so sort and cursor behave the
same with or without `q`. Global search across objects is P1-4.

## Lists

Cursor pagination over `(sort field, id)`: the cursor is the last row's id (base64url); Prisma's cursor mode
continues after that row under the same ordering, with `id` as the tie-break. `limit` defaults to
`LIST_LIMIT_DEFAULT` and is capped at `LIST_LIMIT_MAX` — both in `@bylinecrm/shared`, nowhere else. `sort` is
`field:asc|desc` over a per-object allowlist; anything else is `400`. Deleted records are excluded; the trash is
its own route (`GET …/deleted`, `record:write`) rather than a query flag, because a route declares its gate once
with `@Requires` and a flag would need a second gate mechanism.

## Events

Every mutation publishes a `DomainEvent` (`@bylinecrm/shared`: the catalogue, the shape) through
`DomainEvents.publish` **after `withWorkspace` returns**, i.e. after the transaction committed — a subscriber never
sees an event for a write that rolled back. `updated` events carry a `diff` of the fields that changed. Nothing
subscribes yet except the cross-tenant test; P1-3 (timeline) and P1-5 (webhooks) will.

## The contract freeze

`apps/api/openapi.json` is the frozen contract. `pnpm --filter api openapi:write` regenerates it from the
application (built, then written with the placeholder environment); the unit test `openapi.spec.ts` builds the
document the same way and fails if it differs from the file. A change to the API is therefore a deliberate
regeneration in the same PR, reviewed as a diff of the contract. `pnpm mock:api` serves the file with Prism on
`MOCK_API_PORT` for the P1-UI packages (README: "Working against the mock").

## Failure modes

| Failure                                   | Behaviour                                                                               |
| ----------------------------------------- | --------------------------------------------------------------------------------------- |
| Duplicate primary email / domain          | `409`, naming the field; deleted rows count.                                            |
| Owner is not a member of the workspace    | `422` (the member lookup runs under RLS, so another workspace's member is "not found"). |
| Company does not exist / is deleted       | `422` on `companyId`.                                                                   |
| Own-scoped caller names another owner     | `403`.                                                                                  |
| Record outside scope, deleted, or unknown | `404`.                                                                                  |
| Custom value invalid                      | `400` with `custom.<key>` paths.                                                        |
| Unknown sort field, bad cursor            | `400`.                                                                                  |
| Redis down                                | Definitions are read from the database; validation unchanged.                           |
| A later tenant table without its policy   | `schema-invariants.spec.ts` (P0-2) fails CI.                                            |

(today `GET /members` is admin-only; P1-UI-3 raises it).
