# P2-3c — Who sees a send, who changes it (#133)

## The rule

One rule for every send route, implemented once in `apps/api/src/mail-send/send-access.ts`:

| Action                                                                                         | Who                                                                                         | Otherwise                                 |
| ---------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------- | ----------------------------------------- |
| **Read**: `GET /mail/messages?target=` (#104), `GET /mail/messages/:id`, `GET /mail/scheduled` | anyone who can read the send's record (its person or its deal); its sender always; an admin | `404` — never a hint that the send exists |
| **Change**: `PATCH /mail/messages/:id` (reschedule), `POST …/cancel` (and retry, #134)         | its sender or an admin                                                                      | `403` for a caller who can read it        |

Why: on a shared record, a colleague must see that someone is already writing to this person (a
scheduled follow-up, a failure) or two people email the same contact — the standard CRM behaviour.
Changing someone else's send stays with its sender (and admins), as before.

Until #133 a send was visible only to its sender and admins (P2-3, kept by #104 for consistency).
#104's builder declined to widen only the list, because then a send could be listed but answer
`404` by id and be impossible to manage. This note changes all the routes together.

## How "can read the record" is decided

`readableSends(caller)` returns a Prisma filter: the sender's own sends, or sends whose `person` or
`deal` relation is a live row. The relation filter joins `persons` / `opportunities` **inside the
caller's transaction**, so those tables' row-level security decides what "can read" means — the
workspace policy for everyone, and the restrictive owner policy for an own-scoped role. The function
adds no rule of its own; it is the same source of truth `readableTargets` uses for notes, tasks and
files. An admin's filter is empty (every send in the workspace — the workspace policy still applies).

A send whose record was deleted (soft-deleted person and no deal) is its sender's and an admin's
alone: no live record, so no reader. Hard deletion sets `person_id` to `NULL` (`onDelete: SetNull`)
and behaves the same.

## Sends a sequence creates (P3-3, #139)

A sequence step's send is an ordinary `mail_outbound` row, so this rule covers it with no special
case: anyone who can read its record sees it; its sender or an admin changes it. P3-3 records the
sender of a step's send as **the pool mailbox's owner** (`senderMemberId = mailbox.ownerMemberId`,
`sequence-runner.ts`), not the member who enrolled the person — so that owner (or an admin) may
reschedule or cancel it. Whether the enrolling member should also be able to manage their
enrolments' sends is a sequences question (stop/pause the enrolment is the sequence's own control),
not a send-visibility one; it is not changed here. The sequence runner's own reads of sends are
worker-side (no caller) and unaffected.

## Telling the page what it may do

`MailOutboundView.canChange` is computed by the same `canChangeSend` the change routes enforce, so the
page shows Reschedule and Cancel only where the API will take them. The browser does not re-derive
the rule. A colleague's scheduled send renders read-only, named by its sender. The record's sends are
fetched for every reader, not only for members who may send mail.

## Tests

- `test/cross-tenant/mail-record-sends.spec.ts` (#133 cases): a member sees an admin's send on a
  shared record (list and by id) with `canChange: false`; the scheduled list follows the rule; a
  member gets `403` on reschedule and cancel and the send stands; an admin changes a rep's send; an
  own-scoped rep gets `404` for a send on a record outside their scope (list, by id, cancel); a
  deleted record leaves the send to its sender and admins; another workspace gets `404`.
- `mail-schedule.spec.ts` and `mail-send.spec.ts`: three cases that asserted the old rule now assert
  this one.
- `apps/web/src/routes/w/mail/sends.spec.tsx` (#133): a colleague's scheduled send shows its time and
  sender without Reschedule or Cancel; a reader without `email:send` still sees the record's sends.
