# P2-5 — Scheduled send: re-checked at send time, cancellable, durable

Issue #58. Doc 48 FR-CRMS-4; parity ledger PAR-097. Extends P2-3's `mail-send` module (no fork): one send path,
one `prepare`, one job.

## The rule

A send can be scheduled for later. **Everything a send now checks is checked twice**: at the request (so the sender
learns at once what would refuse it) and again at `sendAt`, **as the sender, the mailbox and the person stand then**.
Any refusal at send time fails the send with its reason — never a partial send, never a send that would have been
refused had it been sent now.

## The request

`POST /mail/send` gains `sendAt` (ISO 8601 with an offset) and `timeZone` (IANA, echoed back only).

- `sendAt` must be at least `MAIL_SEND_MIN_LEAD_SECONDS` (60 s) from now — sooner is a send now — and at most
  `MAIL_SEND_HORIZON_DAYS` (90) ahead; otherwise `400 validation.failed` naming `sendAt`. Both numbers live in
  `@bylinecrm/shared` so the web app's picker reads the same ones.
- The request runs `prepare` — mailbox (the caller's own, personal, connected), recipients under the caller's record
  scope, the render (an empty variable is `422` naming it), threading, `SendPolicy.assertSendable` — exactly as a send
  now does. Then, instead of storing the built MIME, it stores **what was asked** (`request`: the input without its
  timing), `status = scheduled`, `send_at` (UTC) and `sender_time_zone`, and adds a **delayed** job whose id is the
  message's (the same job a send now uses). It announces `email.scheduled` and answers
  `202 { messageId, status: 'scheduled', sendAt, senderTimeZone, recipientTimeZone: null }`.
- `recipientTimeZone` is always `null`: the recipient's zone is inferred later (Phase 3 enrichment). The UI says
  "recipient's zone unknown"; nothing guesses.

## At send time (`MailSendService.deliver` → `activate`)

The delayed job is only the trigger; **the row decides**.

1. A job that fires more than `MAIL_SEND_EARLY_TOLERANCE_MS` (5 s) before `send_at` — the send was moved later after
   its job was set — throws `SendNotDue`; the worker moves the job back to wait (`moveToDelayed` + `DelayedError`), no
   attempt counted, nothing changed.
2. A send whose time passed more than `MAIL_SEND_STALE_MS` (24 h) ago — the workers were down, Redis lost the job — is
   failed as **`stale`**. Why: a message meant for 09:00 arriving the next afternoon is worse than a clear "this was
   not sent"; the sender sees the reason and can send it again. The number is one constant.
3. The sender's scope is rebuilt **as they are now**: still a member, their current role still grants `email:send`,
   with that role's record scope (`own` included). Otherwise the send fails as `forbidden`.
4. `prepare` runs again inside that scope (`WorkspaceContext.run`) with the message's existing Message-ID. A refusal
   fails the send: **`unsendable`** with `fields` naming the variables that are now empty; the mailbox's state
   (`reconnect_needed` / `mailbox_disconnected`); the policy's code (e.g. `validation.failed`, with `fields`);
   `not_found` for a person no longer readable.
5. The row moves `scheduled → queued` with the freshly built MIME **only if it is still `scheduled`**
   (`updateMany … where status = 'scheduled'`). A cancel or a second delivery that got there first wins; the loser
   returns `cancelled` or `skipped` (it re-reads which). From here it is P2-3's delivery, unchanged: one send, the
   lost-answer search, `email.sent` once through sync's writer.

## Cancel, move, list

- `POST /mail/messages/:id/cancel` (`email:send`; sender or admin, `404` otherwise): `scheduled → cancelled` with
  `cancelled_at`, conditional on the status; the job removed afterwards (a job firing in between finds the row
  cancelled and sends nothing); `email.cancelled` once. Cancelling a cancelled send answers as it stands
  (idempotent); anything else is `409 conflict` with `details.status`.
- `PATCH /mail/messages/:id` `{ sendAt, timeZone? }`: same window checks, conditional on `scheduled`; then the job is
  pointed at the new time — `changeDelay` while it waits, removed and added again when it is waiting to run now or
  gone, left alone while it runs (it reads the new `send_at` and waits again via step 1).
- `GET /mail/scheduled?cursor&limit` (`email:send`): the caller's own scheduled sends, an admin's everyone's, soonest
  first (keyset on `send_at, id`).

## Durability — the sweep (`MailSendSweep`)

P1-5's stranded-delivery pattern for mail: a repeatable job on `mail-send-maintenance` every
`MAIL_SEND_SWEEP_EVERY_MS` (60 s), plus one run when a worker starts. It gives a job back to:

- `queued` rows older than `MAIL_SEND_SWEEP_GRACE_MS` with no job (the add failed — a gap P2-3 left open);
- `scheduled` rows due before the next two passes (`MAIL_SEND_SWEEP_HORIZON_MS`) with no job. A send due later is
  looked at when it comes due, so one pass never scans every future send; an overdue one gets a job that runs at once
  and decides `stale` at its time.

The job id is the message's: a send with a live job is never given a second, and running the sweep twice enqueues
nothing twice. The worst case of a sweep and a delayed job racing is two deliveries of one send, and step 5 makes one of
them a no-op — the spec proves a single Gmail send. It runs as the owner (it spans workspaces).

## Data (migration `20261011000000_mail_schedule`)

`mail_outbound_status` gains `scheduled` (first) and `cancelled`; `mime` becomes nullable; new columns `send_at`,
`sender_time_zone`, `request`, `cancelled_at`; index `(status, send_at)` for the sweep. Checks: a send on its way or
gone (`queued`, `sending`, `sent`) has its MIME; a `scheduled` one has `send_at` and `request`; a `cancelled` one has
`cancelled_at`. The checks compare `status::text`, so they do not depend on the new enum values being committed first.

## Events

`email.scheduled` and `email.cancelled` (catalogue): about the send (`recordId`), no `targets` — nothing is on a
record's timeline until it is sent (`email.sent`, once, at the real send). Webhooks deliver them.

## Deviations and notes

- **PAR-097 / PAR-037.** Twenty's campaigns return a scheduled send that fails validation to draft. A 1:1 scheduled
  send here fails with its reason instead: there is no draft state for a single message, and silently holding a send
  the sender believes is going would be worse. Sequences (Phase 3) keep their own lifecycle.
- **The subject on a scheduled send's status** is the one it had when scheduled; it is rebuilt at `sendAt`.
- **Red evidence:** the new spec run against `main` (54553d2) failed to import (`sweep` module missing); with the four
  new symbols stubbed locally it failed 18 of 21 on behaviour. The 3 that passed are refusals `main` also produces for
  other reasons (an empty variable, a disconnected mailbox, a 404 for someone else's send). Quoted in the PR.

## What a later package needs to know

- Phase 3 fills `SendPolicy.assertSendable`; it is already called at send time for scheduled sends.
- The web app (P2-UI-1) shows `sendAt` in the sender's zone and "recipient's zone unknown"; it reads the window numbers
  from `@bylinecrm/shared`.
- When enrichment knows a recipient's zone, `recipientTimeZone` becomes a value; the schema already carries the field.
