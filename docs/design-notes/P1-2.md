# P1-2 — Pipelines, stages, stage history, stage rules

**Package:** doc 49 §5, Phase 1. **Loop step 2 (design).** Closes #14. Spec: doc 48 FR-CRMS-9 (stage rules),
FR-CRMS-UI-3 (board, days-in-stage); parity ledger PAR-007 (opportunity stage), PAR-008 (time in stage — Twenty
needs a workflow for it; here it is native). Conventions: P1-1a's and P1-1b's design notes, followed exactly.

## Data touched

Four tenant tables and four columns on `opportunities` (migration `20261009000600_pipelines`), every table
under row-level security in P0-2's shape. None carries an owner: a pipeline and its stages are workspace
configuration, and a history row is reached through its deal, which carries the owner policy.

| Table                       | What                                                                                                                                                                  |
| --------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `pipelines`                 | Name, `is_default` (exactly one per workspace — a partial unique index), position.                                                                                    |
| `pipeline_stages`           | Name, 1-based `position` (unique per pipeline, **deferrable** so a reorder swaps inside one transaction), probability, `kind` open/won/lost, threshold, colour token. |
| `opportunity_stage_history` | One row per stage a deal entered: from, to, `entered_at`, actor, `reason` manual/rule/import/close.                                                                   |
| `stage_rules`               | Per pipeline and event: the stage to move to, `allow_backward`, `enabled`; one rule per (pipeline, event).                                                            |
| `opportunities` +           | `pipeline_id`, `stage_id` (NOT NULL), `closed_at`, `lost_reason`.                                                                                                     |

**Days-in-stage is computed, never stored.** A deal's `stageEnteredAt` is the `entered_at` of its latest history
row (`withStageInclude` loads the current stage and that one row with every deal); `daysInStage` is whole days
from it at read time. There is no column that could disagree with the history.

**One seed, two writers, one list.** Workspaces that existed before this migration were given the default
pipeline by SQL inside it; workspaces created since get it from `seedDefaultPipeline` inside `AuthService`'s
workspace creation (the owner transaction, like the roles). Both read the same list: `DEFAULT_STAGES` in
`@bylinecrm/shared`, and `default-stages.spec.ts` parses the migration's `VALUES` and fails if the two ever differ.
Deals that existed were placed in the first stage with a history row whose reason is `import` and whose actor is
the system.

## The one writer — `StageMoveService`

Every stage change goes through `move`: it checks the target is a stage of the deal's own pipeline (`422`),
decides with `decideMove` (pure: already there → nothing; backward and not allowed → nothing; else move), writes
the deal's columns and the history row **in the caller's transaction**, and returns what happened. `announce`
publishes after the transaction committed: `deal.stage_changed` always, plus `deal.won` / `deal.lost` on a close.
A new deal goes through `place`, which writes its first history row. Three callers — a member's move, the rule
engine, a close — one definition; nothing else sets `stage_id`, and a plain `PATCH` on a deal cannot (the DTO has
no such field; the test proves the stage stays).

**Closing.** A move into a `won` or `lost` stage is a close: it needs the close payload (`400` without it) — the
won amount (optional, replaces the deal's amount) or the lost reason — writes `closed_at` and `lost_reason`, and
its history reason is `close`. A move out of a closed stage reopens the deal and clears both columns. A deal is
never born closed: a named starting stage must be open (`422`).

## The rule engine — `StageRulesService`

`@OnEvent('email.replied')` and `@OnEvent('meeting.booked')` call `apply(event)`. The event's `related` targets
name the person and company it concerns; the engine runs **as the system in the event's workspace**
(`withWorkspace(event.workspaceId, …)` with no request context, so no owner scope and no member), reads the
workspace's enabled rules for that event, finds the open deals in each rule's pipeline whose point of contact or
company is named, and moves each through `StageMoveService.move` with `reason: 'rule'` and the rule's
`allowBackward`.

- **Forward only** unless the rule says otherwise (FR-CRMS-9): `decideMove` refuses the backward case.
- **Idempotent:** a deal already in or past the target stage is `already` → nothing written, nothing announced; a
  repeated event moves nothing (the test applies the same event twice and counts one history row).
- **Rules never close:** a rule's target must be an open stage (`422` on create/update) — closing is a member's
  decision with its own payload.
- **Never across workspaces:** the engine sees only the event's workspace through the policies; a rule in A fed
  B's person finds no deal (tested).

A member moving a deal **backward** by hand is allowed; the response lists the enabled rules of the pipeline
whose target is ahead of the new stage, so the UI can say "a rule may move it forward again" (doc 50 §B).

## Board and totals

`GET /pipelines/:id/board` returns every stage with the deals in it under the caller's scope and the query
(`q`, `sort`, the same as the deal list), up to `BOARD_STAGE_LIMIT` per column plus `hasMore`, and per-stage
`count` and `amountMinorByCurrency` aggregated over **that same filtered set** — an own-scoped member's totals
are their own deals, never the stage's (tested). Sums are exact per currency; a deal without an amount adds
nothing. P1-4's compiled filter plugs into the `where` beside `q` in `board` — one place.

## Configuration rules

A stage with deals (trash included) or with a rule pointing at it stays (`409`); a pipeline keeps at least one
stage; the first stage must be open, on create, on patch and on reorder (new deals are placed there); a reorder
names every stage exactly once (`400`); the default pipeline cannot be deleted, nor a pipeline with deals (`409`);
making a pipeline default clears the flag on the previous one in the same transaction.

## The contract

New routes, all under `/api/w/:workspaceId`, every one gated: `pipelines` (`deal:read` to read, including
`/board` and `/rules`; `pipeline:configure` to write pipelines, stages, order and rules) and
`opportunities/:id/move` (`deal:move`) and `/history` (`deal:read`). Deal views gain `pipelineId`, `stageId`,
`stageEnteredAt`, `daysInStage`, `closedAt`, `lostReason`; create accepts `pipelineId` / `stageId`. The event
catalogue gains `deal.stage_changed|won|lost` (carrying `stage`) and `email.replied` / `meeting.booked` (carrying
`related`), with `deal`, `email`, `meeting` as event objects. `apps/api/openapi.json` is regenerated (63 paths).

## Failure modes

| Failure                                                                           | Behaviour                                         |
| --------------------------------------------------------------------------------- | ------------------------------------------------- |
| Target stage not in the deal's pipeline                                           | `422`.                                            |
| Close without its payload                                                         | `400`.                                            |
| Rule targeting a closed stage / second rule for an event                          | `422` / `409`.                                    |
| Deleting a stage with deals or rules, a pipeline with deals, the default pipeline | `409`.                                            |
| First stage made closed, reorder not a permutation                                | `400`.                                            |
| Deal outside the caller's scope                                                   | `404` (P1-1a's rule), for move and history alike. |
| Event with no related person or company                                           | Nothing happens.                                  |
| A later tenant table without its policy                                           | `schema-invariants.spec.ts` (P0-2) fails CI.      |

## Not handled here — named

Filtering the board beyond `q` (P1-4's compiled filter; the hook is in `board`); the forecast view (weighted
amounts); per-stage thresholds raising notifications (the threshold is stored and reported, nothing acts on it
yet); emitting `email.replied` (P2) and `meeting.booked` (P3) — only the enum members and the engine exist;
`deal.stage_changed` on the timeline (P1-3) and in webhooks (P1-5); moving a deal between pipelines; bulk moves
(`deal:bulk`, P1-UI-4).
