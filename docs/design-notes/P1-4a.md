# P1-4a — List totals, reading by id, related names on rows, bulk actions

**Package:** issue #47 (found by P1-UI-2). Builds on P1-4 (planner), P1-1c (response schemas) and
P1-1d (error envelope). Conventions of P1-1a/b followed.

## One `where` for every reader of a list

`listScope(tx, context, customFields, object, raw, deleted)` (`query/query.service.ts`) resolves a
list request — filter, sort, view, search — into the plan and **one** `where`: `recordWhere`
(live or trash, owner scope), the compiled filter, the search's candidate ids. The record lists'
page and total, the group-by, the CSV export and a bulk action over a filter all take their rows
from it, so none of them can disagree about which rows a request means. `recordWhere`
(`records/record-scope.ts`) is the base every record read starts from; the services' private
copies of it are gone.

## Totals

Every record list (`GET`, `GET …/deleted`, `POST …/query`) answers `{ items, nextCursor, total,
totalIsExact }`. The total is a `count` over the same `where` as the page, asked for at most
`LIST_COUNT_CAP + 1` rows (`countTotal`): past the cap the total is the cap and not exact
("10,000+"); a search whose candidates hit `SEARCH_CANDIDATE_LIMIT` is never exact either, because
there may be more matches than the candidates. Cursor paging is unchanged — the total is of the
whole set, not of what remains.

## Reading by id

`id` is a filterable field on every object (`ID_FIELD`, shared). It is deliberately **not** in
`STANDARD_FIELDS`: a list never offers it as a column, sort or group, but the planner resolves it, so
the filter and the export accept it by name. `in`/`nin` on `id` take up to `FILTER_MAX_IDS` (500)
values; every other list keeps `FILTER_MAX_LIST` (100). More ids is **`413` `payload_too_large`**,
checked before the structural limits — a request too large to serve, not a malformed one; a
non-uuid id is `400` `validation.failed`. Ids the caller cannot see simply do not come back.

500 ids do not fit in a URL (Node's header limit), so the twins carry them in a body: the list's
`POST …/query` (P1-4) and, new here, **`POST …/export.csv`** — the same parameters and the same CSV
as the `GET`, for exporting a selection.

## Related names on rows

People carry `company` and `owner`; companies `owner`; deals `company`, `pointOfContact` and
`owner` — `{ id, name }` for records (`RecordSummary`), `{ memberId, name }` for members (the
existing `MemberSummary`). Each object has **one include** (`personInclude`, `companyInclude`,
`opportunityInclude`) used by every read and write of it, and **one view**; the board reads deals
with `opportunityInclude` too, so a card and a list row are the same shape. The selects and the
shaping live once in `records/summaries.ts`; `personName` is also what search titles use.

A summary is `null` when there is no related record, when it is in the trash, or when the caller
cannot see it (an own-scoped member's person at another owner's company — the restrictive policy
hides the company, Prisma's include returns nothing). The `…Id` column beside it is unchanged.

**No N+1, measured.** Prisma resolves each include with one statement per relation for the whole
page. `RlsPrismaService.observeQueries` (a listener on the client's query events) lets the
cross-tenant suite count the statements touching the list's tables for a page of ten and a page
of fifty people, each at its own company: the counts are equal.

## Bulk actions

`POST /api/w/:id/{people|companies|opportunities}/bulk` with
`{ action: 'assign_owner' | 'delete' | 'restore', ids? | filter? / view? / q?, ownerId? }` — ids
**or** a list selection, one or the other; `ownerId` with `assign_owner` only. Gates: people and
companies `record:write`; deals `deal:bulk` (doc 50 §B — the bulk bar's capability, not in the
member default), and the service also requires the object's edit capability (`deal:edit` for
deals) because each change is an edit. `@Requires` names one capability, so the second is checked
in the service, before anything is read.

`BulkService` (`records/bulk/`) acts through **the record services' own single-record writes**
(`updateIn` / `removeIn` / `restoreIn`, which the single routes now also run inside their own
transactions). So a record changed in bulk is validated, written and announced exactly as a single
`PATCH`/`DELETE`/`restore` would: N records changed are N single `…updated` / `…deleted` /
`…restored` events — the timeline and webhooks see no bulk event.

- **Limits:** at most `BULK_MAX_IDS` (500) distinct ids, or a selection of at most that many
  (counted with one row over; more is `413`, never a shorter run).
- **Chunks:** `BULK_CHUNK_SIZE` (100) records per transaction; each chunk's events are published
  after it commits.
- **Owner:** resolved once for the request with the single-write rule (`resolveOwner`): an
  own-scoped caller may only name themselves (`403`), and the owner must be a member (`422`) —
  both before any record changes.
- **Results:** one per record, in the order named. A record the caller cannot act on in this
  state — another owner's, another workspace's, already in that state, never existed — is
  `{ ok: false, error: 'not_found' }`, the same answer whatever the reason (the code is from the
  P1-1d table). A record that vanishes between the check and its write gets the same answer, and
  the others in the chunk still change.

## Failure modes

| Failure                                       | Behaviour                                                                                         |
| --------------------------------------------- | ------------------------------------------------------------------------------------------------- |
| More than 500 ids in a filter or a bulk body  | `413` `payload_too_large`, nothing read or changed.                                               |
| A selection matching more than 500 records    | `413`, nothing changed.                                                                           |
| A non-uuid id                                 | `400` `validation.failed`.                                                                        |
| Ids and a selection together; stray `ownerId` | `400` `validation.failed`.                                                                        |
| Own-scoped caller assigning to someone else   | `403`, nothing changed.                                                                           |
| Owner not a member                            | `422`, nothing changed.                                                                           |
| Missing `deal:bulk` / the edit capability     | `403`.                                                                                            |
| Another workspace's or owner's id             | Row result `not_found`; the list read omits it.                                                   |
| A database error inside a chunk               | That chunk rolls back and the request fails (`500`); earlier chunks stay committed and announced. |

## Not handled here — named

A bulk "edit any field" (only owner, delete, restore); bulk on notes, tasks or attachments; a
background job for selections over 500; totals on the pipeline board (it has per-stage counts);
exact totals past `LIST_COUNT_CAP`.
