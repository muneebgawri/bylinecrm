# P1-5 — Outbound webhooks: signed, queued, retried

**Package:** doc 49 §5, Phase 1. **Loop step 2 (design).** Closes #17 (and #34, its duplicate). Spec: doc 48 §8
(the integration contract: NewswireOS meets the CRM at an API and signed webhooks; no integration concept
inside the API), parity ledger `api` rows on webhooks (fire on record create/update/delete with a described
payload). Conventions: P1-2's and P1-3's design notes, followed exactly.

## Data touched

Two tenant tables (migration `20261009000800_webhooks`) under row-level security in P0-2's shape. The app
role may `SELECT, INSERT, UPDATE` both and `DELETE` neither: an endpoint is retired by `deleted_at`, and
delivery rows are pruned by the retention job as the owner (§ Retention).

| Table                | What                                                                                                                                                                                                                                                       |
| -------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `webhook_endpoints`  | URL, description, `events` (catalogue types or `*`), `enabled`, `disabled_reason` + `consecutive_failures` (the auto-disable state), the sealed secret and its display prefix, the sealed previous secret with its expiry during a rotation, `deleted_at`. |
| `webhook_deliveries` | One row per (endpoint, event): the envelope as sent (`payload`), status, attempts, next attempt, when the current attempt began, last status code and error, delivered-at. `event_id` is shared by every endpoint's delivery of one event.                 |

**The secret is sealed, not hashed.** A password or an API key is only ever _compared_, so a hash is enough; a
signing secret has to be _used_ on every delivery. It is encrypted at rest with AES-256-GCM under the one
`SECRETS_KEY` (`SecretBox`, `apps/api/src/infra/secret-box.ts`), shown to the administrator once at creation
and at rotation, and listed afterwards only as `whsec_xxxxxxxx…`. P2-1's customer OAuth client secrets will use
the same box. _(Deviation from the card, which said `secret_hash`: a hash cannot sign.)_

## The wire — what a receiver verifies

```
POST <endpoint url>
content-type: application/json
user-agent: BylineCRM-Webhooks/1
x-byline-event: person.created          (or `ping` for a test send)
x-byline-delivery: <delivery id>        (the same on every attempt of one delivery)
x-byline-timestamp: 1760000000
x-byline-signature: t=1760000000,v1=<hex>[,v1=<hex>]

{ "id": "<delivery id>", "event": "person.created", "occurredAt": "…", "workspaceId": "…", "data": { …the domain event… } }
```

`v1` is `HMAC-SHA256(secret, "<t>.<raw body>")`, hex. During a rotation's grace window (`WEBHOOK_ROTATION_GRACE_S`,
24 h) there are two `v1` entries — the new secret's and the old one's — so a receiver still holding the old secret
verifies until it switches. `data` is the domain event exactly as the catalogue (`@bylinecrm/shared`
`DomainEvent`) defines it: the same object the timeline received, unreshaped. The header names, the payload
string the HMAC covers (`signaturePayload`), the parser (`parseWebhookSignature`) and the replay window
(`WEBHOOK_REPLAY_WINDOW_S`, ±5 min) are in `packages/shared/src/webhooks.ts`, so a receiver and the sender read one
definition.

A receiver in Node:

```ts
import { createHmac, timingSafeEqual } from 'node:crypto';
import { WEBHOOK_REPLAY_WINDOW_S, parseWebhookSignature, signaturePayload } from '@bylinecrm/shared';

function verify(rawBody: string, header: string, secret: string): boolean {
    const parsed = parseWebhookSignature(header);
    if (!parsed) return false;
    if (Math.abs(Date.now() / 1000 - parsed.timestamp) > WEBHOOK_REPLAY_WINDOW_S) return false; // replay protection is yours
    const mine = createHmac('sha256', secret).update(signaturePayload(parsed.timestamp, rawBody)).digest('hex');
    return parsed.signatures.some(
        (s) => s.length === mine.length && timingSafeEqual(Buffer.from(s, 'hex'), Buffer.from(mine, 'hex')),
    );
}
```

Verify over the **raw bytes** received, never a re-serialised body. Dedupe on `x-byline-delivery` if you must be
idempotent: a retry carries the same id; a redelivery is a new delivery with a new id.

## The two moments

**Enqueue** — `WebhooksSubscriber` listens on `**` and keeps catalogue events (the same shape as the timeline's
subscriber, P1-3). For each enabled, live endpoint whose `events` contain `*` or the type, `enqueueForEvent` writes
a `pending` delivery row with the envelope already built, then adds one BullMQ job per row (`jobId` = the delivery
id, so a duplicate add is a no-op). The bus is in-process and synchronous to the request that published; nothing
is sent from the subscriber, and a failure to enqueue is logged, not thrown into a request that already answered.

**Attempt** — the delivery worker (queue `webhook-deliveries`, concurrency and per-endpoint rate from the
constants) runs `WebhooksProcessor.process`, which calls `WebhooksService.attempt(job, n)`. It reads the row and its endpoint fresh (an endpoint retired
or disabled since the enqueue makes the delivery `dead` with that reason), marks it `delivering`, re-checks the
URL (§ SSRF), signs with every valid secret, POSTs through `WebhookSender` — the one HTTP sender, used by real
deliveries and test sends alike — and records the result:

| Result                                  | Row                                                                   | Endpoint                                                                                                |
| --------------------------------------- | --------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------- |
| 2xx                                     | `succeeded`, `delivered_at`, status code                              | `consecutive_failures` reset to 0                                                                       |
| anything else, attempts remain          | `failed`, `next_attempt_at` = now + `backoffDelayMs(n)`, code + error | —                                                                                                       |
| anything else, last attempt             | `dead`, code + error                                                  | `consecutive_failures` +1; at `WEBHOOK_AUTO_DISABLE_AFTER_DEAD` (5) → `enabled = false` with the reason |
| test send (`singleShot`), anything else | `failed`                                                              | untouched — a test is not a signal about the endpoint's health                                          |

**Retry policy.** Five attempts; after the n-th failure the wait is 1 s · 2^(n−1), capped at 60 s, ± 20 % jitter
(`backoffDelayMs`, one function). `attempt` computes the wait once from the row's count, writes it to
`next_attempt_at`, and hands the same number to the queue, so the queue and the log never disagree. A 2xx is success; a 3xx is not followed; 4xx and 5xx are retried alike (a 4xx
is usually a receiver bug that gets fixed, and a dead delivery can be redelivered). Timeout `WEBHOOK_REQUEST_TIMEOUT_MS`
(10 s) for connect, headers and body; the response body is read up to 64 KiB for the log and discarded.

**Per-endpoint rate.** A sliding counter in Redis (`webhooks:rate:<endpoint>`) allows `WEBHOOK_ENDPOINT_RATE`
(60 per minute) starts; a job past it is moved back to delayed until the window turns — not failed, not counted.

**Auto-disable** is a system decision with a written reason (`disabled_reason`) an administrator sees on the
endpoint; switching it back on is theirs (`PATCH { enabled: true }` clears the reason and the count). The log
keeps every dead delivery, and any one can be redelivered once the receiver is fixed.

## SSRF — where an endpoint may point

An endpoint URL is a request the API will make on the workspace's behalf, into the network the API runs in.
`url-guard.ts` refuses at **save time**: non-`https:`, credentials in the URL, a literal address that is not
public, a host that resolves to any non-public address (RFC 1918, loopback, link-local, carrier-grade NAT,
multicast, the IPv6 equivalents and v4-mapped forms — `isPublicAddress`, unit-tested). And at **connect time**:
the undici dispatcher's `lookup` resolves the host again and refuses a private answer, so the address checked is
the address connected to and a name that changes its mind later is refused then. `WEBHOOK_ALLOW_PRIVATE_TARGETS`
(an environment flag, never a request option) admits `http:` and private targets for a receiver on this machine —
development and the cross-tenant suite, which stands up its receiver on 127.0.0.1. The flag is off by default
and must stay off in production.

## Worker placement

`WEBHOOK_WORKER` (default `1`) decides whether this process runs the workers. One API process delivers by
default; a deployment that wants a separate worker runs the same image with `WEBHOOK_WORKER=0` on the API and
`1` on the worker — same module, same constants. `WebhookWorkers` reads the flag from the injected environment
in `onApplicationBootstrap` and constructs the BullMQ `Worker`s itself, so a process that only compiles the
application (the OpenAPI writer, the router walk) neither starts a worker nor opens a connection (queues are
lazy).

## Retention

`WebhooksRetention.prune` runs hourly from a repeating job (`upsertJobScheduler`, idempotent across processes) and deletes
`succeeded` rows older than 7 days and `failed`/`dead` rows older than 30 (`WEBHOOK_RETENTION_DAYS`), as the owner:
it spans workspaces, and the app role has no `DELETE` on the table — the one place deliveries are removed.

## Routes (`/api/w/:workspaceId/webhooks`, all `workspace:admin`)

`GET events` (the catalogue: name + object; the body shape is `WebhookEnvelopeDto` in the document) · `GET` ·
`POST` (returns the secret once) · `GET :id` · `PATCH :id` · `DELETE :id` (retire) · `POST :id/rotate` (new
secret once; old one valid for the grace window) · `POST :id/test` (a `ping` now; answers `{ ok, statusCode,
delivery }`) · `GET :id/deliveries?status&cursor&limit` (readable for a retired endpoint too) ·
`POST :id/deliveries/:deliveryId/redeliver` (a new delivery of the same event). OpenAPI 63 → 74 paths.

## Stranded deliveries — the sweep

A delivery row is written before its job is added, so a Redis outage at that moment, or a worker killed
mid-attempt, leaves a row nothing will pick up. `WebhooksSweep.run` (`sweep.ts`) runs once when a worker starts
and then every `WEBHOOK_SWEEP_EVERY_MS` (60 s) on the maintenance queue, as the owner across workspaces:

- a `delivering` row whose `attempt_started_at` is older than `WEBHOOK_STUCK_DELIVERING_MS` (10 × the request
  timeout, so a slow live attempt is never taken for a dead one) returns to `pending` **with its attempt count
  unchanged** — the lost attempt still counts;
- a `pending` row older than `WEBHOOK_SWEEP_GRACE_MS` (60 s), or a `failed` row whose `next_attempt_at` passed
  that long ago, **with no live job** is enqueued again (up to `WEBHOOK_SWEEP_BATCH` per pass).

It never double-sends. Every enqueue — event, redelivery, sweep — goes through `WebhooksService.enqueue`, whose
BullMQ job id is the delivery id, so a delivery with a live job is never given a second one; and `attempt` re-reads
the row and skips one already `succeeded` or `dead`. **The row, not the queue, counts attempts:** an attempt is
`row.attempts + 1`, and its retry wait is computed from that and handed to the queue through the thrown error
(the worker's `backoffStrategy` uses it), so a re-enqueued job — whose BullMQ count restarts at zero — neither
restarts the schedule nor exceeds the limit. Tests: a row written with no job is delivered by the sweep and two
more passes send nothing more (the receiver counts one); a row with a live delayed job is not given another; a
stuck `delivering` row is freed and delivered as attempt 2.

## Failure modes

| Failure                                            | Behaviour                                                                                              |
| -------------------------------------------------- | ------------------------------------------------------------------------------------------------------ |
| Redis down when an event is published              | Row written `pending`; `queue.add` fails; logged. The sweep (§ Stranded deliveries) enqueues it later. |
| Receiver slow / down / non-2xx                     | Retried on the schedule; then dead; then auto-disable after five dead in a row.                        |
| Endpoint retired or disabled while a job is queued | The attempt marks the delivery dead with that reason; nothing is sent.                                 |
| Host resolves to a private address at connect time | Refused by the pinned lookup; counts as a failed attempt (logged as the error).                        |
| Receiver answers with a huge body                  | Read up to 64 KiB, the rest discarded.                                                                 |
| `SECRETS_KEY` wrong for a sealed secret            | `open` throws; the attempt fails and is retried, then dies — the log says why.                         |
