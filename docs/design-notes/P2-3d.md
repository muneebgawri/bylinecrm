# P2-3d — Retry a failed send from the server (#134)

**What.** `POST /mail/messages/:id/retry` sends a failed send again. Before, Retry existed only in the
tab that sent (it re-posted what the tab remembered), so a failure loaded after a reload (#104)
showed its reason with no way to act on it.

**One path.** A retry does not resend the failed MIME. It moves the row `failed → scheduled` with
`sendAt = now` and lets the existing job run `activate` — the path a scheduled send takes at its time
— so the message is rebuilt and every check runs again as things stand now: the sender's role, the
mailbox, the person and their variables, the suppression list, the pool's gate (P3-2). The web's
Retry calls this route for every failed send, its own tab's included; the old re-post is gone.

**What is kept.** `request` (what was asked, as a scheduled send already kept it) is now stored for
every send, and wiped once the send is final (`sent` or `cancelled`); a failed send keeps it, so it
can be retried. The migration wipes it from rows already final.
_Not sealed_ (deviation from the issue's suggestion): `mail_outbox` seals its payload because it
holds a single-use link — a credential. A send's request holds message content, which the CRM
already stores in plain text everywhere else (synced bodies, the built MIME, scheduled requests);
sealing only this copy would make two storage formats and need a key-holding data migration for
existing scheduled rows, while protecting nothing the database does not already hold in the clear.

**Rules.**

- Manage rule (#133, `send-access.ts`): sender or admin; a reader gets `403`, others `404`.
- Not retried (`409 send.not_retryable`): a refusal that would repeat (`recipient.suppressed`,
  `MAIL_SEND_NOT_RETRYABLE`), a sequence's send (its enrolment reschedules or stops it, P3-3), a send
  whose content is no longer kept (failed before this change). `canRetry` on every send view says
  which, so the UI offers Retry only where the API will take it.
- Idempotent: the move from `failed` is one conditional update; `retried_at` marks a retry, so a
  second click while it is under way answers `200` with where the send stands and changes nothing.
- A send that was attempted before (`attempts > 0`) is looked for in the mailbox's sent mail before
  it is sent again (the #87 dedupe), so a retry after a lost answer cannot double-send.
