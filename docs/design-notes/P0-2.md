# P0-2 — Tenancy, row-level security, the cross-tenant suite

**Package:** doc 49 §5, Phase 0. **Loop step 2 (design).** Closes #5.

## Data touched

Three tables. `workspaces` (the tenant) and `users` (a login identity) are **global**; `workspace_members`
is the first **tenant table** — it carries `workspace_id` and is under row-level security, as every tenant
table after it will be. Prisma models `Workspace`, `User`, `WorkspaceMember` (`apps/api/prisma/schema.prisma`).
`users.email` is unique as stored; the application lower-cases it before writing (P0-3 is the first writer).

## The two database identities

| Identity                        | Connection         | Used for                                                         | Bypasses RLS |
| ------------------------------- | ------------------ | ---------------------------------------------------------------- | ------------ |
| owner (`bylinecrm` locally)     | `DATABASE_URL`     | migrations; creating workspaces and users; the specs' fixtures   | yes (owner)  |
| `bylinecrm_app` (`APP_DB_ROLE`) | `RLS_DATABASE_URL` | **every tenant query**, through `RlsPrismaService.withWorkspace` | no           |

The role name is defined once, `APP_DB_ROLE` in `@bylinecrm/shared`. The migrations must name it in SQL;
`apps/api/src/infra/app-role.spec.ts` reads every migration and fails if any `GRANT … TO` names anything else.
The role itself is created by `scripts/db-ensure-app-role.mjs` (its password is a secret and cannot live in a
migration): it reads the role and password from `RLS_DATABASE_URL`, refuses a URL whose user is not
`APP_DB_ROLE`, and creates or alters the role with `LOGIN NOSUPERUSER NOCREATEDB NOCREATEROLE NOINHERIT
NOBYPASSRLS NOREPLICATION`. `pnpm --filter api db:setup` = ensure the role, then `prisma migrate deploy`; CI
and the local recipe both run it.

## Policies (migration `20261009000100_tenancy_rls`)

- One definition of "the current workspace": the SQL function `app_workspace_id()` =
  `NULLIF(current_setting('app.workspace_id', true), '')::uuid`. **Unset or empty → NULL → no row matches.** A
  query that forgot to scope itself sees nothing; it never sees everything.
- `workspace_members`: `ENABLE` + `FORCE ROW LEVEL SECURITY`; policy `FOR ALL TO bylinecrm_app USING
(workspace_id = app_workspace_id()) WITH CHECK (same)`; grants `SELECT, INSERT, UPDATE, DELETE`.
- `workspaces`: `SELECT` only, policy `id = app_workspace_id()` — a workspace sees itself.
- `users`: `SELECT` only, policy "is a member of the current workspace".
- `REVOKE ALL ON SCHEMA public FROM PUBLIC`, `GRANT USAGE … TO bylinecrm_app`, `REVOKE ALL ON ALL TABLES …
FROM bylinecrm_app` before the explicit grants. **`_prisma_migrations` gets no grant** and the suite proves
  it is unreadable.

**What P0-3 adds:** an `app.user_id` setting and a policy letting a signed-in user list their own memberships
before a workspace is chosen; the decision whether sign-up writes `users`/`workspaces` through the owner client
or through a narrow grant. Nothing here pre-empts that.

## `withWorkspace`

`RlsPrismaService.withWorkspace(workspaceId?, fn)` opens an interactive transaction on the restricted client,
runs `SELECT set_config('app.workspace_id', $1, true)` — **bound as a parameter, transaction-local** — and
hands the transaction client to `fn`. Without an explicit id it reads `WorkspaceContext` (an
`AsyncLocalStorage` a request guard or job runner populates) and throws `NoWorkspaceError` if there is none.

**RLS is the backstop, never a route's only gate.** The guard (P0-3) decides whether the caller may act in the
workspace and records it in `WorkspaceContext`; the policies make a wrong decision, or a missing one, fail
closed. A route whose only protection is RLS is a defect, not a design.

**Pool.** Each `withWorkspace` pins one connection for its transaction. Sizing and retry are the five
constants in `rls-pool.constants.ts` (pool 10, pool timeout 10 s, retry 3× on Prisma `P2024` with 100 ms
doubling); `withPoolDefaults` applies the first two to the URL unless the operator set them. A pool-exhausted
error is retried; any other error propagates.

## Health

`/health` gains `rls: 'ok' | 'misconfigured'`: `ok` only when the restricted client's `current_user` is
`APP_DB_ROLE` **and** that role has `rolbypassrls = false`. `status` is `ok` only when `rls` is. The owner's
credentials in `RLS_DATABASE_URL` therefore show up on the first health check, not on the first leak.

## Failure modes

| Failure                                                | Behaviour                                                                               |
| ------------------------------------------------------ | --------------------------------------------------------------------------------------- |
| `RLS_DATABASE_URL` unset or misspelled                 | Boot stops (zod).                                                                       |
| `RLS_DATABASE_URL` is the owner, or role has BYPASSRLS | `/health` → `rls: misconfigured`, `status: degraded`; the cross-tenant suite fails.     |
| A tenant query runs with no workspace set              | Zero rows (policy) — and `withWorkspace` without id or context throws before the query. |
| A write names another workspace                        | Refused by `WITH CHECK` (Postgres error mentioning row-level security).                 |
| The restricted role tries `SET ROLE owner`             | Permission denied (NOINHERIT, no membership).                                           |
| Pool exhausted                                         | Retried 3× with backoff, then the `P2024` error propagates.                             |

## The cross-tenant suite (CI gate)

`apps/api/test/cross-tenant/`: `rls-role.spec.ts` (precondition: the client **is** the app role, cannot
`SET ROLE` to the owner, cannot read `_prisma_migrations`), `workspace-isolation.spec.ts` (A sees only A;
update/delete of B's row → 0; insert into B refused; global tables scoped; no setting → nothing; no id and
no context → throws; context supplies the id; the setting does not outlive its transaction),
`health.boot.spec.ts` (the real app boots and reports `rls: ok`). Real Postgres, no mocks, fixtures created
by the owner client and removed after each test.

## What later packages must do (checked by `schema-invariants.spec.ts`)

Every table with a `workspace_id` column **must**, in the migration that creates it: `ENABLE` and `FORCE ROW
LEVEL SECURITY`, create at least one policy `TO bylinecrm_app` with `USING`/`WITH CHECK` on
`workspace_id = app_workspace_id()`, and grant only the privileges it needs. Every table without one is either
a scoped global table (RLS + policy) or carries no grant to the app role at all; `_prisma_migrations` stays
ungranted. The cross-tenant suite reads `pg_catalog` for every table in `public` and fails on the first
exception — a tenant table added without its policy fails CI the day it is added, not the day a tenant leaks.

## Not handled here

Authentication, sessions, the request guard that populates `WorkspaceContext` (P0-3); roles and object-level
permissions (P0-3); any domain table (Phase 1).
