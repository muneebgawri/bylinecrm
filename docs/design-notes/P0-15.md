# P0-15 — Transactional email: verify the address, mail invitations, reset passwords

**Package:** doc 49 §5, Phase 0 (added 2026-10-11). **Loop step 2 (design).** Closes #93. Decision
D-246: transactional mail (never outreach) goes through **Resend**, a BylineCRM sending-only key on
NewswireOS's account, from `no-reply@pinionnewswire.com`.

Until now an address was "verified" only by a provider sign-in, an invitation, or an operator command
(`cli/platform-verify-email`). A password sign-up could act in its workspace without ever proving it
reads the mailbox, invitations were links an admin had to pass on by hand, and `POST
/auth/password/forgot` answered `501`. This package mails the three things that need a mailbox:
a verification link, an invitation, and a password-reset link.

## One kind of single-use link

All three mailed secrets that are not invitations (verify, reset, and #101's set-password link
later) are rows in **one table**, `one_time_tokens`, behind **one service**,
`OneTimeTokenService`:

| Column       | Meaning                                                                                     |
| ------------ | ------------------------------------------------------------------------------------------- |
| `purpose`    | enum `email_verification`, `password_reset` (#101 adds `set_password`)                      |
| `user_id`    | whose account it acts on (cascade on delete)                                                |
| `email`      | the address the link was mailed to; verification only succeeds if it is still the account's |
| `token_hash` | SHA-256 of the secret (`hashToken`), unique; the secret itself is never stored              |
| `expires_at` | `EMAIL_VERIFICATION_TTL_S` (24 h) or `PASSWORD_RESET_TTL_S` (30 min)                        |
| `used_at`    | set when spent; a spent link answers like an unknown one                                    |

- **Opaque random, not signed.** The issue says "signed". A 32-byte random secret whose hash is stored
  is stronger: it can be revoked, it is single-use by a row update, and no key compromise forges
  one. It is the same scheme as sessions, API keys and invitations (`tokens.ts`).
- **Single use under races.** Spending is one conditional update (`used_at IS NULL AND expires_at >
now()`); exactly one of two concurrent requests gets `count = 1`.
- **One live link per purpose.** Issuing a new link deletes the user's unspent links of that
  purpose, so only the newest mail works.
- **A global table, owner client only**, like `sessions`: it is read before any workspace is known.
  The app role has no grant on it (asserted in `schema-invariants`). Verification and reset act on
  the person, not on a workspace, so there is nothing to bind them to. Invitation tokens, which are
  workspace-bound, stay in `workspace_invites` unchanged.

## Verification

- **Who starts unverified.** A password sign-up (open or invite mode) and an account created by
  accepting a workspace invitation. Both get a verification mail at once.
    - **Change from P0-14:** accepting an invitation used to count as verification ("the token proves
      the holder read the mailbox"). But the inviter is also shown the link, so an admin could accept
      it as someone else and get that address verified. With platform admins keyed on verified email,
      that is a privilege-escalation path. Only a link mailed to the address verifies it now.
    - A provider sign-in (Google, OIDC) still verifies: the provider vouched for the address.
- **What an unverified person can do.** Sign in, see `/api/me`, ask for a new link, sign out.
    - **Every tenant route answers `403 email.unverified`.** The `WorkspaceGuard` checks it before
      membership, so it is refused before any tenant query is issued.
    - `POST /api/workspaces` answers the same.
    - The platform check already requires a verified address (P0-14).
    - The web app shows only a "check your inbox" screen, with resend and sign out.
- **The session carries the flag.** `SessionService.resolve` reads `users.email_verified_at` in the
  same query (a join), so the guard costs no extra round trip.
- **Endpoints:**
    - `POST /api/auth/email/verify { token }` (public): `204`; an unknown, spent or expired link →
      `400 token.invalid`.
    - `POST /api/auth/email/verification` (signed in): sends a fresh link, `202`. Rate-limited to
      `VERIFY_RESEND_MAX` per hour per account → `429`. Already verified → `204`, nothing sent.
- **The page does not verify on load.** `/verify-email?token=…` shows a "Verify my email" button
  that posts. Mail scanners and link previews fetch GET URLs, and a GET that spends the link would
  spend it for them.

## Password reset

- `POST /api/auth/password/forgot { email }` (public) **always answers `202`**, with the same body,
  for an unknown address, a provider-only account and a real one. Mail is only sent for an existing
  account. Rate limits, all answered with `429` without saying why:
    - `RESET_REQUEST_MAX` per hour per address+IP
    - `RESET_REQUEST_IP_MAX` per hour per IP
- `POST /api/auth/password/reset { token, password }` (public):
    - Sets the password (same policy as sign-up). It also marks the address verified, because the
      link was mailed to it.
    - **Revokes every session of the account** and starts a new one for this browser: `200`, signed
      in.
    - Bad link → `400 token.invalid`; weak password → `400` validation.
- A provider-only account can set a password this way. Holding the mailbox is the same proof the
  provider gave.

## Invitations are mailed

- **Workspace invitations** (`POST /api/w/:ws/invites`) and the **owner invitation** a platform
  admin creates with a workspace are mailed to the invitee after the transaction commits. The
  response still returns the link once, so the inviter can pass it on by hand as today.
- **Platform sign-up invitations** (`invite` mode) are mailed the same way.

## The mail pipeline

```
service (after commit) → TransactionalMailer.enqueue → BullMQ `transactional-mail`
                                                     → worker → TransactionalMailTransport
                                                                 ├─ ResendTransport (RESEND_API_KEY set)
                                                                 └─ MemoryTransport (otherwise; dev/test)
```

- **Never inside a transaction.** Rows are written first, the transaction commits, and then the
  mail is enqueued. The network call happens in the worker. `ResendTransport` calls
  `assertNoOpenTransaction` like every other network boundary (P2-2a).
- **Idempotent end to end.** The job id is the mail's idempotency key (`verify:<tokenId>`,
  `reset:<tokenId>`, `invite:<inviteId>`, `owner-invite:<inviteId>`, `signup-invite:<inviteId>`).
    - BullMQ drops a second enqueue with the same id.
    - Resend's `Idempotency-Key` header makes a retried request after a lost response a no-op, for
      24 hours.
    - The memory transport honours the key the same way, so tests see what production does.
- **Retries.** Five attempts, exponential from 30 s, for transport errors, `429` and `5xx`. A `4xx`
  that cannot succeed (bad key, unverified domain, invalid address) fails the job at once
  (`UnrecoverableError`) and is logged with Resend's error name, never the payload.
- **The link never sits in Redis in clear.** The job data (recipient, subject, both bodies) is
  sealed with `SecretBox` (`SECRETS_KEY`). Jobs are removed on completion; a failed job is kept 7
  days for diagnosis, still sealed.
- **What is lost, and why that is acceptable for now.** A crash between commit and enqueue loses
  that mail. Each one has a manual way back:
    - verification: "send a new link"
    - reset: ask again
    - invitations: the link shown to the inviter, or revoke and re-invite

    The transactional outbox (#98) moves the enqueue into the transaction. Its relay will publish
    these the same way it publishes domain events, so this package keeps the enqueue in one method
    (`TransactionalMailer.enqueue`) for #98 to replace.

## Configuration

| Variable                    | Meaning                                                                                               |
| --------------------------- | ----------------------------------------------------------------------------------------------------- |
| `NODE_ENV`                  | `development` (default), `test`, `production`                                                         |
| `RESEND_API_KEY`            | Resend key with sending access only. **Required when `NODE_ENV=production`**: boot refuses without it |
| `MAIL_FROM`                 | the From header. Required in production; default `BylineCRM <no-reply@localhost>` elsewhere           |
| `TRANSACTIONAL_MAIL_WORKER` | `1` (default) runs the delivery worker in this process, like `MAIL_SEND_WORKER`                       |

- **Production always needs a key.** Every deployment mails: sign-up and reset need it in every
  sign-up mode, and invitations need it when sign-up is closed. So "refuse to boot when a feature
  needs mail" is the same as "refuse to boot in production without a key", and there is no
  half-configured production.
- **Without a key** (development, CI), mail goes to the in-process `MemoryTransport`. It keeps the
  last 200 messages for the test suite and logs one line per message. Outside production the line
  includes the link, so a developer can click it; production never logs bodies.

## Templates

`transactional-mail/templates.ts`: plain HTML and a text part for each kind.

- **Branding:** the product name "BylineCRM", never a workspace's branding. Invitations name the
  workspace.
- **No tracking pixels, no click redirects:** the link is the app's own URL.
- **Accessibility:** a single-column `role="presentation"` table, real text (not images), sufficient
  contrast, and the URL also printed as text for clients that strip links.
- **Escaping:** every interpolated value (workspace name, address) is escaped. The subject has no
  user-controlled text except the workspace name, which is length-capped by its schema.

## Staging

- **`bootstrap-secrets.sh` keeps the key.** It keeps an operator-installed `RESEND_API_KEY` across
  re-runs (the same keep-what-is-stored pattern as #105's `PLATFORM_ADMIN_EMAILS`). It writes
  `MAIL_FROM="BylineCRM <no-reply@pinionnewswire.com>"`.
- **Installing the key:** `deploy/staging/install-resend-key.sh` reads the key from **stdin**,
  validates its shape (`re_…`), rewrites `staging.env` atomically (0600), and never prints it or puts
  it in argv. The owner runs it from the Mac with the key on the clipboard (`docs/deploy/staging.md`):

    ```
    pbpaste | ssh newswireos-vps 'sudo bash /opt/bylinecrm/current/deploy/staging/install-resend-key.sh'
    ```

    Then the api is restarted.

## Error codes added (`ERROR_CODES`)

`email.unverified` (403) and `token.invalid` (400).

## Tests (written first; failing on `main` shown in the PR)

Cross-tenant suite (`test/cross-tenant/transactional-mail.spec.ts`), against the memory transport:

- #93 (D-246, doc 48 §6.1): sign-up mails one verification link; the link verifies once; a second use, an
  expired link and a tampered link → `400 token.invalid`.
- An unverified member gets `403 email.unverified` on a tenant route, with no `withWorkspace` call.
  After verifying, the same route answers.
- Forgot-password answers identically for an unknown address, a provider-only account and a real
  one; only the real one gets mail.
- Reset sets the password, revokes the other sessions, and signs this browser in. The old password
  and old session fail.
- A workspace invitation is mailed once, even when the transport fails after accepting (lost
  response) and the job retries.
- The mail is enqueued after the commit: a rolled-back invitation mails nothing, and the transport
  is never called inside a transaction.
- A link minted for account A cannot verify or reset account B.
- Resend adapter unit spec: headers (`Authorization`, `Idempotency-Key`), timeout, and the
  retryable/permanent error split.

Web: the verify page posts on click (not on load), the forgot page says the same thing for every
address, the reset page signs in, and the unverified gate shows only the inbox screen.
