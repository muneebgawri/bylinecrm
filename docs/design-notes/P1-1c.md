# P1-1c — The OpenAPI document: response schemas and path parameters, derived from zod

**Package:** doc 49 §5, Phase 1 follow-up. Closes #27. Found by P1-UI-1: `apps/api/openapi.json` (85 paths,
120 operations) had no response schemas and omitted `{workspaceId}` on 105 operations, so `openapi-typescript`
could not generate a usable client.

## What changed

| Gap                            | Before                     | After                                                                                                                       |
| ------------------------------ | -------------------------- | --------------------------------------------------------------------------------------------------------------------------- |
| 2xx response schemas           | 0 of 120                   | every operation: a JSON body, a file (`text/csv`, `application/octet-stream`), `204`, a `302` redirect, or a declared `501` |
| Error envelope                 | none                       | one `ApiError` component on every operation's `4XX` and `5XX`                                                               |
| `{workspaceId}` declared       | 15 of 120                  | all; every templated segment is a path parameter                                                                            |
| Operation ids                  | `PeopleController_list`    | `people_list` — `<module>_<handler>`, unique                                                                                |
| Response types in the services | 33 hand-written interfaces | `z.output` of the schema the document is built from                                                                         |

No response body changed. `openapi.json` stays at 85 paths.

## One definition: zod

Each module has a `responses.ts` with the zod schema of every body it returns, registered under its component
name with `named('Person', …)`. The service's type is `export type PersonView = z.output<typeof personView>`;
the hand-written interfaces are gone. So the type a service builds, the type the route promises and the
schema in the document are one definition.

**Why not nestjs-zod's `@ZodResponse`.** It is already a dependency (MIT) and it was tried first. Two of its
behaviours rule it out here: a schema reused inside another (`Person` inside `PersonPage`) makes
`cleanupOpenApiDoc` throw "multiple schemas with name", and a nullable sibling of a referenced schema was
written as `{ type: array, items: string }` — a wrong document, silently. Instead the response half uses zod 4's
own exporter: `z.toJSONSchema(registry, { target: 'openapi-3.0', io: 'input', uri })` turns the registry into
`components.schemas` with correct `$ref`s, `nullable`, recursion (`FilterGroup`, `RichTextNode`) and examples.
nestjs-zod still documents the request DTOs, as before. No dependency was added for the bridge.

**Dates.** Services hold `Date`; the wire carries ISO strings. `dateTime` is a zod codec (`z.iso.datetime()` ↔
`z.date()`): `z.output` is `Date` for the services, and the document is written with `io: 'input'`, so it says
`string, format: date-time`.

**Shared types.** `Actor`, `Emails`, `Phones`, `Links`, `Address`, `Money`, `RecordTarget`, `RichText`,
`SavedView`, `SearchResults`, `HealthStatus`, `EventActor` and `TimelineActor` stay in `@bylinecrm/shared`
(the web app imports them and must not import zod — P1-4's bundle finding). Each schema is held to its shared
type at compile time (`SharedTypeChecks`, or a `z.ZodType<SharedType>` annotation), so either side changing
alone fails `typecheck`.

## How a route declares its body

`@Returns(personPage)`, `@Returns([memberView])`, `@ReturnsFile('text/csv')`, `@Redirects()`,
`@NotImplementedYet()` (in `src/openapi/responses.ts`). The decorator's descriptor type ties the handler's return
type to the schema: a handler returning anything else does not compile. It records the declaration as an
operation extension; `document.ts` moves it onto the 2xx status Nest already generated from the method and
`@HttpCode`, so a status is never declared twice, then removes the extension. A response schema that is not
registered throws at document build time.

`TenantController('people')` (in `auth/decorators.ts`) is now the one way to mount a tenant controller: it is
`@Controller('w/:workspaceId/people')` plus the `workspaceId` path parameter, so the prefix and its
documentation cannot diverge.

## Guards against regression

- `openapi.spec.ts` (unit): the committed file equals the built document (as before), and: every operation
  documents a success; every operation has the error envelope; every templated segment is declared; operation
  ids are unique and `<module>_<handler>`; every `$ref` resolves. The new assertions were run against `main`'s
  document first and fail there (4 of 4).
- `contract/check.ts`, run by `pnpm --filter api contract:check` in the `test` CI job (no new required check):
  generates a client with `openapi-typescript` into `contract/generated/` (git-ignored) and type-checks three
  typed calls with `openapi-fetch` — people list, pipeline board, workspace standing — including the error
  envelope. Against `main`'s document it fails with 5 errors.

## Shapes documented as they are

- `GET /api/auth/google`, `…/google/callback`, `…/oidc/{issuer}`, `…/oidc/{issuer}/callback` answer `302`, not a
  body; Nest had generated `200`.
- `POST /api/auth/password/forgot` answers `501` (its implementation is a later package); documented as such.
- `GET …/attachments/{attachmentId}/content` streams the stored file's own type; documented as
  `application/octet-stream`.
- `POST …/attachments` reads a multipart body by hand (busboy), so its request schema is an explicit `@ApiBody`
  (one `file` part), the only schema in the API written as a decorator.
- Error bodies are not uniform: Nest's `{ statusCode, message, error }`, the validation pipe's `errors`, and two
  service bodies (`field` on a 409, `issues` on invalid custom values) without `statusCode`. `ApiError` documents
  all of them as optional fields over a required `message`.
- `Group.value` is `unknown` in the schema: it is whatever the grouped field holds.

## What the UI does next

P1-UI packages swap their hand-mirrored client types for `openapi-typescript` output from this file
(`openapi-fetch` for calls), keeping the one client module that adds CSRF and error normalisation.
