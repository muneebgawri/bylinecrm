# P2-1 — The workspace's Google OAuth client and mailbox connect

Doc 48 FR-CRMS-1, D-237 (each customer's Workspace admin supplies their own OAuth client; no Google
app verification in v1), §6.1 (narrow scopes only), doc 50 §E lower half; issue #54.

## What is stored

- `google_oauth_clients` — one per workspace (unique `workspace_id`): client ID, the secret sealed
  with `SecretBox` (the P1-5 key; the secret is presented to Google, so it cannot be a hash), its
  last four characters (the only part ever shown), who configured it, `verified_at` (when a mailbox
  first connected through it — the only end-to-end proof), and the last check's per-step outcomes.
- `mailboxes` — owner member, lower-cased address (unique per workspace), label, purpose
  (`personal | pool`, fixed when connected), status (`connected | reconnect_needed | disconnected`),
  granted scopes, refresh and access tokens sealed, access expiry, `last_error { code, message, at }`.
  CHECKs: a mailbox that is not disconnected holds a refresh token, a disconnected one holds no
  token; an access token comes with its expiry; addresses are lower case.
- Both tables are under RLS in P0-2's shape. The app role has no DELETE on `mailboxes`:
  disconnecting is a status with the tokens wiped, so the address keeps its place and its history.
- No response schema has a field for a token or a secret; a cross-tenant test asserts no issued
  token or secret appears in any response body or log line.

## The connect flow

```
browser ── POST /api/w/:id/mailboxes/connect {purpose} ──▶ API        (mailbox:manage; a member, not a key)
  API: state = random(32), verifier = random(32)
       Redis "mailbox-connect:<state>" = {workspace, member, user, purpose, verifier, client row}  TTL 10 min
  ◀── { authorizeUrl, expiresAt }   (client_id = the workspace's own, scope = gmail.send gmail.readonly,
                                     code_challenge = S256(verifier), access_type=offline,
                                     prompt=consent, include_granted_scopes=true)
browser ──▶ Google consent ──▶ GET /api/mail/oauth/callback?state&code   (public route)
  API: take the state once (GETDEL) ─ unknown/expired/used ─▶ invalid_state
       Google error / no code ─▶ denied
       signed-in user ≠ the user who started ─▶ wrong_user
       no longer a member, or lost mailbox:manage ─▶ not_permitted
       client removed or replaced since the start ─▶ no_client
       exchange (client secret + PKCE verifier) refused ─▶ exchange_failed
       grant includes https://mail.google.com/ ─▶ scope_too_broad
       grant lacks gmail.send or gmail.readonly ─▶ scope_missing
       no refresh token ─▶ no_refresh_token
       address = Gmail users.getProfile (lower-cased)
       address live in this workspace under another member ─▶ owned_by_another
       address live with the other purpose ─▶ purpose_mismatch
       else create, or reconnect the same row (a disconnected one connects afresh) ─▶ connected
  ◀── 302 WEB_URL/w/<workspace>/mailboxes?connect=<result>   (or /workspaces when the state was unknown)
```

The callback is public because Google's redirect carries no API credential. Two decisions go
beyond the brief:

- **The callback is bound to the person who started it.** Without that, someone could start a
  connect in their own workspace and send the consent link to a victim; the victim's consent would
  put the victim's mailbox tokens in the attacker's workspace. The browser's session cookie
  (SameSite=Lax, sent on Google's top-level redirect) must belong to the user who started the
  request, and that user must still be a member holding `mailbox:manage`.
- **A refused grant is not revoked.** Google's revoke ends the whole grant — every token that
  Google account gave this client — so revoking a refused reconnect of an address that is already
  live would disconnect the live mailbox too. Nothing is stored; the person can remove the grant in
  their Google account.

Result codes are one list in `@bylinecrm/shared` (`MAILBOX_CONNECT_RESULTS`); no token or Google
error text is ever put in a URL.

## What can be verified before anyone signs in

`POST /api/w/:id/mail/oauth-client/verify` records three steps:

| Step         | How                                                                                                                                                                                | Outcome                                        |
| ------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------- |
| Format       | The client ID matches `<digits>-<id>.apps.googleusercontent.com`                                                                                                                   | pass / fail (Google is not called on fail)     |
| Credentials  | Exchange a code Google never issued: `invalid_client` = Google does not know the client or refuses the secret; `invalid_grant` = client and secret accepted, only the code refused | pass / fail / unverified                       |
| Redirect URI | The same exchange: `redirect_uri_mismatch` if Google reports it there                                                                                                              | **fail** if reported, otherwise **unverified** |

Whether Google checks the redirect URI during that exchange at all is not something the API relies
on: it is certain only at the authorization step, with a person present. So a correct
configuration shows the redirect URI as _unverified — confirmed when the first mailbox connects_,
and the first successful connect sets `verified_at`. The mapping lives in one function
(`probeFromError`), used by the HTTP adapter and the test fake alike.

## Tokens

`MailboxTokens.getAccessToken(workspaceId, mailboxId)` is the only place an access token is handed
out. It takes the workspace explicitly so the P2-2/P2-3 workers can call it outside a request.

- A token valid for longer than `TOKEN_REFRESH_SKEW_S` (120 s) is returned as stored.
- Otherwise one process refreshes it under a per-mailbox Redis lock (`SET NX PX`, TTL 15 s — longer
  than a Google request's 10 s timeout; released only by its holder via compare-and-delete). Other
  callers poll the row every 100 ms and return the refreshed token; a test runs five concurrent
  callers and counts exactly one refresh at Google.
- A rotated refresh token from Google replaces the stored one.
- `invalid_grant` (revoked, expired, account changed) or a narrow scope missing from the refreshed
  token moves the mailbox to `reconnect_needed` with `last_error`, emits `mailbox.reconnect_needed`
  once (the update only matches a `connected` row, so a repeat announces nothing), and throws
  `MailboxUnavailable` (409 `conflict`). Transient failures are rethrown; nothing retries a dead grant.
- `POST /mailboxes/:id/check` gets a token and asks Google which scopes it carries; a withdrawn
  scope moves the mailbox to `reconnect_needed` the same way.
- Disconnect revokes the refresh token at Google (`revoked: true` when Google confirms) and wipes
  the stored tokens regardless.

## Who sees and changes what

The list and single read require `mailbox:read` (every default member holds it): an admin sees
every mailbox; anyone else sees their own and the sending pool; a mailbox outside that is 404.
Changing (label), checking and disconnecting require `mailbox:manage` and being the owner or an
admin (403 for a mailbox one can see but does not own). A different `purpose` in a PATCH is refused
with 409 — a mailbox's purpose is fixed; disconnect and connect again. The OAuth client routes are
`workspace:admin`. No new capability was added; the three used are already in the catalogue.

**Deviation from the card:** it said a member sees their own personal mailboxes _without_
`mailbox:read`. That needs `@AnyMember`, which the router test reserves for routes that ask what
the caller may do (its allow-list is exact on purpose), so the read routes are gated by
`mailbox:read` instead. A member with `mailbox:manage` but not `mailbox:read` can connect but not
list; no default role is in that state.

## Events

`mailbox.connected` (actor: the member), `mailbox.disconnected` (the caller),
`mailbox.reconnect_needed` (the system, or the caller of a check), all with `recordId` = the
mailbox. `mailbox` is an event object but not a record: the timeline writes nothing for them;
webhooks deliver them.

## Testing without Google

Google sits behind `GoogleOAuthPort` (`GOOGLE_OAUTH_PORT`). The HTTP adapter is the only code that
calls Google. The cross-tenant suite builds the real application from a testing module with the
port overridden by `test/support/fake-google-oauth.ts`, which enforces what Google enforces (client
credentials, redirect URI, PKCE `S256`, a code used once, revoked grants) and records every token it
issues for the leak check. To make that possible, `createApp()` is now `configureApp()` over a
created application, so a test and the server share the same middleware, prefix and documentation.

## What P2-2 (sync) needs from here

- `MailboxTokens` is exported from `MailAccountsModule`; call `getAccessToken(workspaceId, mailboxId)`
  per Gmail request batch and treat `MailboxUnavailable` as "stop syncing this mailbox".
- Only `status = 'connected'` mailboxes are syncable; `purpose` tells sync (personal: 1:1 mail on the
  owner's records) from the pool (outreach, P3).
- Subscribe to `mailbox.connected` to start a first sync and to `mailbox.disconnected` /
  `mailbox.reconnect_needed` to stop.
- The `gmail.readonly` scope is guaranteed on every connected mailbox; `gmail.send` likewise for P2-3.
