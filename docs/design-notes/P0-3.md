# P0-3 — Authentication, roles and capabilities, API keys

**Package:** doc 49 §5, Phase 0. **Loop step 2 (design).** Closes #8. Spec: doc 48 §5, doc 50 preamble.

## Threat model, in ten lines

| Threat                                           | Answer                                                                                                                                                  |
| ------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Session fixation                                 | Login/sign-up issues a **new** session and revokes the one the cookie already named (`sessions.rotated_from_id` keeps the trail).                       |
| Session theft, replay after logout               | Server-side sessions: the cookie is a random token, the row holds its hash; logout revokes the row, so a copied cookie is dead too.                     |
| CSRF                                             | Double-submit: `blc_csrf` cookie echoed in `x-csrf-token` on every cookie-authenticated POST/PATCH/PUT/DELETE; bearer calls have no ambient credential. |
| Account enumeration                              | One `401` body for unknown address, provider-only account and wrong password; sign-up on a taken address answers the same generic `409`.                |
| Password guessing                                | argon2id (OWASP 2023 parameters) and a Redis fixed-window brake per address+IP (`429` after 10 in 15 min; a success clears it). Fails closed.           |
| Key leakage                                      | `blc_<prefix>_<secret>`: shown once, only the SHA-256 stored, compared in constant time; `prefix` is the only identifier ever listed.                   |
| A key used against another workspace             | The workspace guard compares the key's workspace to the path **before** any tenant query; the cross-tenant suite spies `withWorkspace` to prove it.     |
| Privilege staleness                              | Nothing about roles lives in the cookie or key; capabilities are read per request from the role's rows, so a change applies on the next request.        |
| An unverified provider email claiming an account | A provider identity is matched to an existing account by email only when the provider marks it `email_verified`.                                        |
| A tenant route with no gate                      | `@Requires()` is mandatory under `/api/w/`: the guard refuses an undeclared route and `routes-declare-capability.spec.ts` walks the router in CI.       |

## Who may write the global tables

`users`, `workspaces`, `sessions`, `external_identities` are global. The app role is `SELECT`-only on the first two
(under the policies below) and has **no grant at all** on the last two. Writes go through the owner client in exactly
these places, and the design is that nowhere else on a request path does:

| Writer                               | Why the owner client                                                                                                                       |
| ------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------ |
| `AuthService.signup/createWorkspace` | A workspace, its two system roles and its first admin seat are created in one transaction **before any tenant scope exists** to be inside. |
| `AuthService.signInWithIdentity`     | Same: the user may not exist yet.                                                                                                          |
| `AuthService.acceptInvite`           | Looks up the invite by token hash across workspaces (the invitee is not a member yet), then creates the seat.                              |
| `SessionService`                     | A session is read **to find out who the caller is**; there is no identity to scope by until it has been read.                              |
| `ApiKeyService.resolve`              | Same for keys: the key names the workspace, so the lookup by prefix cannot be inside one.                                                  |

Every other read and write is through `RlsPrismaService`: `withUser` for a signed-in user's own view before a workspace
is chosen (`MembershipService`), `withWorkspace` for everything tenant-scoped (roles, members, API-key CRUD, invites).

## Policies (migration `20261009000200_auth`)

- `app_user_id()` — the companion of P0-2's `app_workspace_id()`, same shape (unset → NULL → no row).
- `users`: `+ SELECT USING id = app_user_id()` — a user reads their own row.
- `workspace_members`: `+ SELECT USING user_id = app_user_id()` — their own seats, in any workspace.
- `workspaces`: `+ SELECT USING EXISTS(seat of app_user_id())` — the workspaces those seats name.
- `roles`, `role_permissions`, `api_keys`, `workspace_invites`: tenant tables, P0-2's shape (`ENABLE` + `FORCE`, policy
  `workspace_id = app_workspace_id()` for `USING` and `WITH CHECK`, grants `SELECT, INSERT, UPDATE, DELETE`).
- `sessions`, `external_identities`: no grant; the schema-invariant test accepts a table the app role cannot reach.

`workspace_members.role_id` is added `NOT NULL` without a default: the table is empty in every environment (no release
has shipped), and a seat without a role is not a seat.

## The request pipeline

```
RequestScopeMiddleware   opens one WorkspaceContext scope per request (AsyncLocalStorage.run, never enterWith)
AuthGuard                cookie → SessionService.resolve | Bearer → ApiKeyService.resolve | @Public() → pass | else 401
CsrfGuard                cookie-authenticated mutation must echo blc_csrf in x-csrf-token, else 403
WorkspaceGuard           /api/w/:workspaceId only: member? (withUser) | key's workspace? → capabilities (withWorkspace) → context.set
RequiresGuard            /api/w/ only: @Requires(cap) present and held, else 403
ZodValidationPipe        bodies validated by the zod DTOs (nestjs-zod); the same schemas feed the OpenAPI document
```

The workspace guard makes **two** small transactions per tenant request (membership under `app.user_id`, then the role's
rows under `app.workspace_id`). It could make one by setting both settings, but then a non-member's request would read
the candidate workspace's rows before being refused; two transactions keep "refused before any tenant query" literally
true. A per-request cache of the capability set is a later optimisation, not a correctness change.

## Capabilities

`CAPABILITIES` in `@bylinecrm/shared` is the catalogue (doc 50 preamble). `admin` is every capability **by
construction** (`capabilitiesOf` returns the whole catalogue for the system admin role; no rows are stored for it, so
nothing can drift). `member` starts with `MEMBER_DEFAULT_CAPABILITIES` and is editable. A workspace keeps at least one
admin: `MembersService` locks the admin seats (`FOR UPDATE`) before counting, so two concurrent demotions serialise.

## Identity providers

Google and any OIDC issuer are the same code path (`OidcService`): discovery cached per issuer, PKCE + state + nonce,
the pending request held in Redis for ten minutes and consumed once (`GETDEL`). Scopes are `openid email profile` —
**identity only**; Gmail scopes are P2-1's and never requested here. The redirect URI to register at the provider is
`APP_URL + /api/auth/oidc/<key>/callback` (Google: `…/oidc/google/callback`; `/api/auth/google` is an alias).

## Invitations

An invite row is written by a workspace admin through RLS; its token is returned once and only the hash stored.
Accepting it: a signed-in user whose **verified** email matches, or an account created from the token itself
(`POST /api/auth/invites/:token/signup`) — the token reached the invited mailbox, which is the verification. Sending
the invitation email is not built here; the token is returned to the admin.

## Not handled here — named, not half-built

- **Password reset** and **email verification for local accounts**: `POST /api/auth/password/forgot` answers `501`.
  Both need the transactional sender (sign-in and invitation mail; doc 48 §6.1 last sentence), which arrives with the
  mail work in Phase 2. Until then a local account's `emailVerified` is false and it can join a workspace only by
  creating itself from an invitation.
- **MFA**, **passkeys**, **device/session listing**: not in doc 48 v1 scope.
- **Field-level and record-level (owner) permissions**: P1-1, on top of the capability layer here.
- **Google verification / CASA**: doc 48 Q1.

## Module system note

`@nestjs/swagger` 12 and `openid-client` 6 are ESM-only. The API compiles to CommonJS (Nest CLI) and loads them with
Node's `require(esm)`, which TypeScript permits under `module: NodeNext` and Node supports from 22.12 — hence
`apps/api/tsconfig.json` moves from `Node16` to `NodeNext` and `engines.node` becomes `>=22.12`. No dynamic-import
shim, no CJS fork of either library.
