# P1-4 — Saved views, the filter grammar, sort and group-by, CSV export, global search

**Package:** doc 49 §5, Phase 1. **Loop step 2 (design).** Closes #16. Spec: doc 48 FR-CRMS-UI-1 and
FR-CRMS-UI-4; parity ledger PAR-056… (views). Conventions: P1-1a's and P1-1b's design notes, followed.

## The one vocabulary

`@bylinecrm/shared` (`views.ts`) holds what every side reads: the **field descriptors** of each object
(`STANDARD_FIELDS`: API name, label, kind, sortable, groupable), the **kinds** and the **operators each
kind takes** (`OPERATORS_BY_KIND`), the **grammar** (`filterGroupSchema`, `filterProblem` with the depth,
node and list caps), the view shapes (`SavedView`, `ViewSort`, `ViewColumn`) and the export and search
constants. The filter editor's operator menu, the sort allowlist, the column chooser and the CSV header
all come from this one file; adding a field to a list is a change here, reviewed as a contract change.

The shared package carries **types, constants and pure functions only** — no schema library. The
zod schemas that check a filter's and a view's shape live in the API (`query/grammar.ts`), built from
the shared types and constants. The card asked for the grammar "as a zod schema in packages/shared";
the first cut did that, and the web app's initial bundle grew by 19 kB gzipped past its `size-limit`
budget, because `@bylinecrm/shared` is imported by every page. The contract the web needs is the
types; the schema is the API's.

A field is named as the API knows it (`arr`, `amount`), never as the column (`arrMinor`); the one place
the two meet is `query/fields.ts`, which also turns the workspace's active custom-field definitions into
`custom.<key>` descriptors with the kind the definition's type implies (`CUSTOM_FIELD_KIND`). The three
per-object `SORT_FIELDS` constants of P1-1a/b are gone — the sortable set is the descriptors'.

## The grammar, and how it is checked

`{ and: Node[] } | { or: Node[] }`, a node being a group or `{ field, op, value }`. Two layers, two kinds
of error, both `400` naming the condition's field:

1. **Shape** (shared, zod): known operators, no extra keys, a field name that is a standard name or
   `custom.<key>`; then `filterProblem` — at most `FILTER_MAX_DEPTH` (4) levels, `FILTER_MAX_NODES` (50)
   conditions and groups, `FILTER_MAX_LIST` (100) values in an `in`/`nin`.
2. **Meaning** (API, `compile-filter.ts`): the field exists on this object for this workspace, the kind
   takes the operator (`contains` on a boolean is refused), the value is the kind's type (a `select` takes
   only its options; `between` takes two; null checks take none).

## The compiler — one module, no SQL strings

`compileFilter` turns a checked filter into a Prisma `where`. A **standard field** compiles to the
column's operators; text operators are case-insensitive; money becomes `BigInt` on the minor-units
column; dates and instants become `Date`. `neq` and `nin` are written as "not the value **or** no value",
because SQL's `<>` drops NULL rows and a user asking "not CEO" means the people with no title too.

A **custom field** compiles to Prisma's JSON path operators on `custom` (`path: [key]` with `equals`,
`gt…lte`, `string_contains`, `string_starts_with`, `array_contains`). `is_null`/`not_null` use
`Prisma.AnyNull`, which matches a key that is absent and a key set to JSON null alike — a record that
never had the field and one whose field was cleared both "have no value". Two limits are stated rather
than hidden: JSON text comparisons are **case-sensitive** (Prisma's JSON filters take no `mode`), and a
custom field is **not sortable or groupable** (a JSON path has no index to order or group by). Both are
documented in the refusal messages.

The compiled `where` is untyped at the module boundary (`CompiledWhere`); each record service gives it
the model's type at its one call site, next to its own `where(context, deleted)` and the owner-scope
filter. **Scope is applied once**: `ownerWhere(context)` (P1-1a) is what the lists, the group-by, the
export and the search all spread into their `where`, and the restrictive policy underneath backs it.

## How a request becomes a plan

`resolvePlan(tx, context, customFields, object, raw)` in `query.service.ts` is the one path for a list,
the `POST …/query` twin, the group-by and the export: load the saved view if `view=` names one (under
the caller's sight — `404` otherwise), decode the filter (base64url JSON on a query string, JSON in a
body), read the object's active definitions, and `planQuery` — pure — resolves fields, compiles, and
orders. A view's filter and sorts are **defaults**; an inline `filter` or `sort` replaces them whole
(not merged — a user narrowing a shared view expects their filter to be the filter).

`sort` is `field:asc,field2:desc`, at most `SORT_MAX_FIELDS` (3), ending with `id asc` so a cursor is
stable; the order comes from the descriptors, never from input.

## Saved views

`saved_views` (migration `20261009000600_saved_views`): object, name, icon, `owner_member_id`,
`is_shared`, filter, sorts, columns, group_by, position; a tenant table under the workspace policy. It
carries no `owner_id` and no restrictive policy on purpose: a view's visibility is not the record rule
but its own — **a member sees shared views and their own** — and that predicate (`visibleViews`) is one
function used by the list, the get, the record lists' `view=` lookup and every write check.

Gates: reading needs `record:read`; creating and editing one's own needs `view:save` (the route);
making a view shared, or editing or deleting a shared one, needs `view:share` as well — checked in the
service because it depends on the row. A refusal is `403` (the caller can see the view, nothing leaks);
a view outside the caller's sight is `404` everywhere. `duplicate` gives any visible view a private
copy owned by the caller. Every write validates the filter, sorts, columns and grouping against the
object's fields with the same functions the list uses, so a view can never be saved with something the
list would refuse; a field archived afterwards surfaces as `400` naming it when the view is used.

## The pipeline board (P1-2) takes the same parameters

`GET /pipelines/:id/board` accepts `filter`, `sort`, `view` and `q` exactly as the deal list does and
resolves them through the same `resolvePlan` (with `position asc` as its default order) — one compiler,
one call site in `PipelinesService.board`, so a saved deal view can drive the board and the list alike,
and the per-stage counts and sums are over the same filtered, scoped set.

## Group-by

`GET …/group-by?field=` returns `{ value, count, sum? }` per value of a groupable column, over the same
filtered, searched, scoped set the list shows (Prisma `groupBy` in the caller's transaction). Companies
sum `arr`, deals sum `amount` — in minor units, exact. People have no money field and no `sum`.

## CSV export

`GET …/export.csv?filter&sort&view&q&columns` streams: a **count first**, and a result larger than
`EXPORT_MAX_ROWS` (100,000) is `413` before the first byte — a truncated file that looks complete is
worse than a refusal. Then the BOM, a header of **labels**, and pages of `EXPORT_PAGE_SIZE` (1,000) rows
by cursor, each written with back-pressure, never the result in memory. `columns` names fields (standard
or `custom.<key>`) in order; absent, every standard field. Money exports as minor units under its label.

One CSV writer (`csv.ts`): RFC 4180 quoting, and **formula injection neutralised** — a cell starting
with `=`, `+`, `-`, `@`, tab or CR is prefixed with a quote, so a value a stranger typed into a record
cannot run as a formula on an analyst's spreadsheet. The gate and the scope are the list's.

## Global search

`GET …/search?q=&limit=&objects=` runs each object's ranked candidate query (P1-1a's `searchCandidates`,
the same one `?q=` uses, under the policies) and fetches the rows under the caller's scope, keeping the
rank; hits are `{ object, id, title, subtitle }`, at most `limit` per object (default 5, max 25). A
caller who may not read an object gets no hits from it; the command palette consumes this.

## Routes and module shape

The per-object routes — `POST …/query`, `GET …/group-by`, `GET …/export.csv` — are declared on the record
controllers **before** the `:id` routes, which is how Nest orders static over parameterised paths; they
call `QueryService` / `ExportService` from `QueryModule`. To let `QueryModule` and `ViewsModule` read the
custom-field definitions without a module cycle, `CustomFieldsService` moved into its own
`CustomFieldsModule` (same file, same provider; the records module imports it like the others).

## Failure modes

| Failure                                                | Behaviour                                             |
| ------------------------------------------------------ | ----------------------------------------------------- |
| Filter malformed / too deep / too many nodes           | `400` with the reason.                                |
| Unknown or archived field, wrong operator, wrong value | `400` naming the field.                               |
| Sort on a custom or unsortable field, > 3 fields       | `400`.                                                |
| View outside the caller's sight (`view=`, get, edit)   | `404`.                                                |
| Sharing / editing shared without `view:share`          | `403`.                                                |
| Export over `EXPORT_MAX_ROWS`                          | `413`, nothing written.                               |
| Unknown or duplicate export column                     | `400`.                                                |
| Group-by on a non-groupable field                      | `400`.                                                |
| Another workspace's view, rows, hits                   | Never seen: policies + `visibleViews` + `ownerWhere`. |

## Not handled here — named

Sorting or grouping by a custom field; case-insensitive JSON text matching; a filter editor UI
(P1-UI-2); kanban by stage (P1-2 adds the stage field and its grouping); listing notes/tasks across
records; relative date operators (`last 7 days`); export of notes/tasks/attachments; search over notes
and tasks (their vectors exist; the palette's v1 scope is records); the `413` path has a unit of logic
but no end-to-end test (100k rows are not created in CI).
