# P3-2 — Sending pool (FR-CRMS-6, FR-CRMS-13)

Issue #117. Doc 49 Phase 3, P3-2 (deps P2-3, P3-1). Doc 48 FR-CRMS-6 (caps, rotation, jitter, warm-up,
auto-pause) and FR-CRMS-13 (complaint rate watched per mailbox, paused before Google's 0.3%; sending domains pass
SPF, DKIM and DMARC by DNS lookup, or the service refuses to send). D-248: the outreach domains are bought when
this lands — warm-up starts then.

## What a pool is

A workspace's mailboxes connected with `purpose = pool` (P2-1). Pool mailboxes never send one-by-one from the
composer (P2-3 refuses that); they send what a sequence (P3-3) hands them. P3-2 builds everything a sequence
needs to send safely and the gate every pool send passes; P3-3 calls it.

## Settings (per workspace, `sending_pool_settings`)

| Setting                                 | Default  | Why                                                                                                                                                                        |
| --------------------------------------- | -------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `dailyCap`                              | 40       | FR-CRMS-6's default ("a starting value to be validated in warm-up, not a guarantee"). A mailbox may override it.                                                           |
| `warmupStartPerDay` / `warmupDays`      | 5 / 21   | See warm-up below.                                                                                                                                                         |
| `jitterMinSeconds` / `jitterMaxSeconds` | 60 / 300 | Spacing between two sends from one mailbox; a fixed cadence reads as automation.                                                                                           |
| `bounceRatePause`                       | 5%       | Hard bounces over sends in the window. Mailbox providers treat a few percent of hard bounces as a list-quality problem; 5% is the conservative end of common ESP practice. |
| `complaintRatePause`                    | 0.2%     | FR-CRMS-13: pause _before_ Google's published 0.3% spam-rate line (Google, "Email sender guidelines", support.google.com/a/answer/81126).                                  |
| `rateMinSample`                         | 20       | No rate is judged on fewer sends; one bounce in three sends is not 33%.                                                                                                    |
| `rateWindowDays`                        | 7        | Rates are over the last seven days of sends.                                                                                                                               |

## Allowance: cap and warm-up

A mailbox's allowance for the next send is over a **rolling 24 hours** (Gmail's own sending limits are rolling,
not calendar days): `min(cap, warm-up limit for its warm-up day)`. Used = the mailbox's sends in the last 24 hours
that went or are going (`sending` or `sent`, counted once per send by id — a retry of a send already counted does
not count again).

**Warm-up.** Day 1 is the day the pool mailbox first connected (`warmupStartedAt`). Limit on day _d_:
`min(cap, start + floor((cap − start) × (d − 1) / (warmupDays − 1)))` — 5 a day rising evenly to the cap on day 21.
Google's guidance is to "increase the sending volume slowly" without numbers (support.google.com/a/answer/81126,
"Sending volume"); 5 → 40 over three weeks is our conservative reading, tunable per workspace, and FR-CRMS-6 says
these numbers are to be validated in warm-up. Reconnecting a mailbox does not restart warm-up; an admin can.

## The gate (one place, every pool send)

`SendingPool.claim(tx, mailbox, sendId)` runs inside the transaction that moves a send to `sending`, with the
mailbox row locked (`SELECT … FOR UPDATE`) so two workers cannot both take the last slot. It refuses, in order:

1. `mailbox.paused` — the mailbox is paused (reason shown).
2. `mailbox.domain_unverified` — the mailbox's sending domain has not passed its last DNS check.
3. `mailbox.cap_reached` — the allowance is used up (cap or warm-up day limit named).

A send already counted (it was `sending` before — a retry) is never refused for the cap. A refusal fails the send
with that code and message, like any other refusal (never silently dropped). Personal mailboxes pass straight
through: FR-CRMS-13 is about the outreach domains; personal mail goes from the workspace's own domain.

## Rotation and jitter (what P3-3 calls)

`SendingPool.pick(workspaceId)` returns the pool mailbox to send the next message from, or null when none can:
eligible = connected, not paused, domain verified, allowance left. Among those, the one with the **lowest share of
its allowance used**, then the longest since its last send, then id — so mailboxes fill evenly whatever their caps.
`SendingPool.nextSendAt(mailboxId, earliest)` returns a time at least a random `jitterMin…jitterMax` seconds after
the mailbox's last send (or `earliest`, whichever is later). Picking does not reserve: the claim decides.

## Bounces (FR-CRMS-6, FR-CRMS-7)

Gmail returns a bounce to the sending mailbox as a delivery status notification. Sync (the one writer) already
imports every message; the parser now recognises a DSN — `multipart/report; report-type=delivery-status`, or
Gmail's `X-Failed-Recipients` header — and extracts the failed recipients, the status (`5.x.x` permanent,
`4.x.x` transient) and the `X-BylineCRM-Id` of the original send from the returned headers when present. When a
pool mailbox stores a **permanent** bounce, the same transaction writes a `mail_bounces` row (unique per
mailbox copy and address) and records `email.bounced`. An outbox consumer then suppresses the address
(`hard_bounce`, source `provider`, through P3-1's one write) and re-evaluates the mailbox's rates. Transient
bounces are recorded but neither suppress nor count.

## Complaints — what Gmail does and does not tell a sender

Gmail sends no per-message feedback loop to senders (it offers none to non-ESP senders; its Feedback Loop is
aggregate, for ESPs, keyed on a `Feedback-ID` header). Postmaster Tools reports a **domain-level daily** spam rate
for verified domains, through an API — useful, but not per mailbox or per message, and it needs domain
verification and its own OAuth scope (filed as a follow-up). So the per-mailbox complaint signal is the
suppression list's `complaint` entries attributed to the mailbox (the address's last send from it): a member
marking a reply as a complaint (P3-1's API, reason `complaint`) or, later, Postmaster data. Each such entry feeds
the mailbox's complaint rate exactly as a bounce feeds its bounce rate.

## Auto-pause and resume (FR-CRMS-6, FR-CRMS-13)

After every counted bounce or complaint the consumer recomputes the mailbox's rates over the window; at or above
a threshold (and at least `rateMinSample` sends) it pauses the mailbox — `pausedAt`, `pauseReason
{ code, message, rate, threshold, at }` — and records `mailbox.paused`. Sends from a paused mailbox are refused at
the claim; `pick` skips it. An admin resumes it (`POST /mailboxes/:id/resume`, a note required), which clears the
pause and records `mailbox.resumed`. Resuming does not erase the history: the next evaluation still sees it, so
the admin resumes after fixing the cause (cleaning the list), not to silence the alarm.

## Sending domains and DNS (FR-CRMS-13)

A pool mailbox's sending domain is its address's domain. `sending_domains` keeps one row per (workspace, domain):
the DKIM selector to check (default `google`, Google Workspace's default), the last check's per-step results and
status, `checkedAt`, `nextCheckAt`. Checks, by DNS lookup only (a `DnsPort`; a fake in tests):

- **SPF**: a `v=spf1` TXT record at the domain that includes `_spf.google.com` (Gmail sends from Google's servers;
  the envelope sender is the mailbox address, so SPF is aligned when it passes).
- **DKIM**: a TXT record at `<selector>._domainkey.<domain>` with a public key (`p=` non-empty). Gmail signs with
  `d=<domain>` once Workspace DKIM is set up for that selector, which is what makes DKIM aligned.
- **DMARC**: a `v=DMARC1` TXT record at `_dmarc.<domain>` with a `p=` tag. (Any policy passes the check; enforcement
  is the domain owner's call — doc 48 does not require `quarantine`.)

All three must pass. Checked when a pool mailbox connects, on demand (`POST /sending-domains/:id/check`), and every
six hours by a repeating background job; DNS is never queried inside a transaction. A domain that has never passed
refuses every send from it.

## Postmaster Tools (#129, P3-2b)

The follow-up the Complaints section promised. Postmaster Tools publishes, per **verified domain and day**, the
user-reported spam rate Gmail measured — the complaint signal Gmail never sends per message. The domain check
reads it; one adapter behind a port; the fake in tests; the real credentials come later (below).

- **One account per workspace, through the workspace's own OAuth client.** `POST /sending-pool/postmaster/connect`
  (admin) runs the mailbox connect flow (P2-1: state, PKCE, the same callback) asking for Postmaster's two scopes —
  `postmaster.readonly` and `userinfo.email` (to say whose grant it is) — and nothing of Gmail. The callback stores
  `postmaster_connections` (one row per workspace: the account's address, the scopes, the sealed refresh and
  access tokens, who connected it) and lands on the Mailboxes page with `?connect=<result>&for=postmaster`. A
  grant without the Postmaster scope is `scope_missing`; full Gmail access reported alongside it is refused as for
  a mailbox. The token is refreshed like a mailbox's — one process at a time (`tokenUnderLock`, the mechanism
  `MailboxTokens` uses, under its own key) — and `invalid_grant` marks the connection `reconnect_needed` with the
  reason. `DELETE /sending-pool/postmaster` revokes at Google (best effort) and deletes the row.
- **Behind the existing check, never inside a transaction.** `SendingDomainsService.run` does its DNS lookups,
  then asks the port for **yesterday (UTC)** — Postmaster publishes a day once it is over — at
  `GET /v1/domains/{domain}/trafficStats/{YYYYMMDD}`, then writes once: the domain's `postmaster_status` and
  `postmaster_message` (`not_connected`, `not_verified` — Google answers 403 for a domain the account does not
  own there —, `ok`, `failed` with the status Google gave or "could not be reached") and, when there is a rate,
  one `sending_domain_stats` row per (domain, day), replaced when the day is read again. `ok` with a message and
  no row is Google's 404: no data for the day — it keeps data back under a traffic minimum. A failed lookup keeps
  the last rate: "could not read" is never a zero.
- **The pause.** After the write, `SendingPoolService.evaluateDomain` judges the rate against the workspace's
  `complaintPauseBps` (0.2% by default, under Google's 0.3% line) and pauses every connected, unpaused pool mailbox
  on the domain with code `domain_spam_rate` (`sends: null` — Postmaster gives a rate, not counts), one
  `mailbox.paused` each, through the same write `evaluate` uses. Idempotent: a paused mailbox keeps its first
  reason. An admin resumes each as before; the next check judges the next day's rate.
- **Shown.** `SendingDomainView.spamRate { day, rateBps }` and `.postmaster { status, message }`;
  `SendingPoolView.postmaster { email, status, connectedAt, lastError } | null`. The Mailboxes page's pool section
  shows the rate under each domain, Postmaster's message when it has one, and a Postmaster Tools card: whose
  account, _Connect Postmaster Tools_ / _Connect again_ / _Disconnect_ for an admin.

**The one-time step (owner, when the real credentials come).** Nothing in this package is run against Google yet;
the cross-tenant suite proves the flow against the fakes. To go live, in the Google Cloud project that holds the
workspace's OAuth client: (1) enable the **Gmail Postmaster Tools API**; (2) add the scope
`https://www.googleapis.com/auth/postmaster.readonly` to the OAuth consent screen (and `userinfo.email` if it is
not already there); (3) in [postmaster.google.com](https://postmaster.google.com), signed in as the Google account
that will be connected, add and verify each outreach sending domain (the DNS TXT record Google gives); (4) on the
Mailboxes page, as an admin, _Connect Postmaster Tools_ with that account. Nothing else changes: the next domain
check reads the rate. Until then every domain reports `not_connected`, which pauses nothing.

## Events (outbox, P1-6)

`email.bounced` (object `email`, `recordId` the bounce report message; `bounce` = address, permanent, status,
mailbox, send), `mailbox.paused`, `mailbox.resumed` (`recordId` the mailbox; `pause` = reason). Webhooks deliver
them; the timeline writes nothing for them.

## API

- `GET /sending-pool` — settings + per pool mailbox health (allowance, used in the last 24 h, warm-up day and
  limit, paused reason, sending domain status).
- `PUT /sending-pool/settings` (admin) — the settings above, validated (thresholds 0–100%, cap 1–500, …).
- `PUT /mailboxes/:id/pool` (admin) — `{ dailyCap: number | null }`; `POST /mailboxes/:id/resume` (admin, note).
- `GET /sending-domains`, `PUT /sending-domains/:id` (admin; DKIM selector), `POST /sending-domains/:id/check`.
- `POST /sending-pool/postmaster/connect` (admin; `201 { authorizeUrl, expiresAt }`), `DELETE /sending-pool/postmaster`
  (admin; `204`, `404` while none is connected) — #129.

## UI

Mailboxes page, pool section: per pool mailbox a health row — used / allowance today, warm-up day _d_ of _n_, the
sending domain's status with its three checks and its Postmaster spam rate (#129), and a paused banner with the
reason and Resume (admin). Pool settings in a sheet; the Postmaster Tools card under the table. Light/dark, phone
layout, keyboard and screen-reader labels; the page stays a lazy route.
