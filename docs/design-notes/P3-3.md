## Data model (migration `20261012010000_sequences`)

- `people.source TEXT NULL`, `people.country CHAR(2) NULL` (upper-case ISO alpha-2, checked). Exposed on the
  person API like any field.
- `region_policies (workspace_id, region, allowed, lawful_basis, updated_by_member_id, updated_at)`, PK
  `(workspace_id, region)`; `region ∈ eu | uk | ca | us | other | unknown`. A row is an **override**; no row
  means the default. Allowing a region that is blocked by default requires `lawful_basis` (the database checks).
- `outreach_exclusions (id, workspace_id, address NULL, domain NULL, reason, account_manager_name NULL, source,
external_ref NULL, note NULL, created_at, removed_at NULL, removed_note NULL)`; one of address/domain is set;
  one live entry per address and per domain (partial unique indexes); lower-case (checked).
- `sequences (id, workspace_id, name, status, pipeline_id NULL, stop_on_pipeline_exit, time_zone,
window_start_minute, window_end_minute, window_days, created_by, created_at, updated_at, archived_at)`.
  `status ∈ draft | active | paused | archived`. `window_days` is a Monday-first bitmask (default Mon–Fri);
  `time_zone` is the zone used when a recipient's zone cannot be inferred.
- `sequence_steps (id, workspace_id, sequence_id, position, kind, template_id NULL, reply_in_thread,
wait_days NULL, business_days, created_at, updated_at)`; `UNIQUE (sequence_id, position)`. A draft's list
  is rewritten (delete + insert, the one table the app role may delete from). **Once a sequence has run, its
  existing steps keep their order** — an enrolment knows where it is by position — so `PUT …/steps` must keep
  them, in order, as the start of the list (each may be edited) and may add steps after them; restructuring
  means duplicating the sequence. Edits apply to enrolments that have not reached the step.
- `sequence_enrolments (id, workspace_id, sequence_id, person_id, deal_id NULL, status, step_index,
next_run_at NULL, waiting_outbound_id NULL, held_reason NULL, stop_reason NULL, stop_detail NULL,
enrolled_by, enrolled_at, finished_at NULL, stopped_at NULL, created_at, updated_at)`,
  `UNIQUE (sequence_id, person_id)`; `status ∈ active | held | finished | stopped`.
- `mail_outbound.sequence_enrolment_id`, `mail_outbound.sequence_step_id` (NULL for 1:1 mail): what a step's
  send belongs to, read when its outcome comes back.

All new tables: RLS `workspace_isolation`, `FORCE`, app-role grants without `DELETE` (exclusions and
enrolments are ended by a state change, never deleted, so the history stays).

## The enrolment gates (one function)

`EnrolmentScreen.screen(workspaceId, personIds)` returns, per person, _eligible_ or _refused_ with a code and the
server's message — the enrol dialog shows exactly these; the confirm count is recomputed on submit. In order:

1. `person.not_found` — gone, or not visible to the caller.
2. `email.missing` — no primary address.
3. `source.missing` — FR-CRMS-11.
4. `suppressed` — `SuppressionService.check`; the message names the reason (unsubscribed, bounced, complaint, manual).
5. `excluded` — FR-CRMS-10; "Is a customer (source)" or "Worked by <AM> (account manager)".
6. `region.blocked` — FR-CRMS-12; names the region and says _policy_.

**Country, as inferred:** `people.country`, else the company's address country (an ISO code, or an English
country name), else the address's country-code TLD (`.de` → DE, `.uk` → GB); a generic TLD gives no country →
region `unknown`. **Default for `unknown`: allowed** — FR-CRMS-11 asks for country "if known", and the inference
above already catches every ccTLD address. A workspace that wants unknown-country outreach blocked sets the
`unknown` region to blocked. _(Open question for the owner, below.)_

The same checks except FR-CRMS-11/12 run again **before every step** (a contact can become a customer or
suppressed after enrolment); region and source are properties of the enrolment decision, not re-litigated.

## Running a sequence

The enrolment row is the truth: `status`, `step_index`, `next_run_at`, `waiting_outbound_id`.

- **Scheduling:** one BullMQ delayed job per due enrolment on `sequence-steps`, job id
  `<enrolmentId>:<next_run_at ms>` — so a rescheduled enrolment gets a new job and the old one finds its
  time changed and does nothing. A repeating sweep (the mail-send sweep's pattern) re-adds the job of every
  active enrolment due within the next two passes whose job is gone, and re-delivers outcomes of steps whose
  send finished while the outcome event was missed. Running it twice adds nothing twice.
- **A step (`SequenceRunner.run`):** reads the enrolment; does nothing unless it is `active`, its sequence is
  `active`, and `next_run_at` is the job's and due. Then the stop checks. Then the step:
    - `wait` — advance; next run = `wait_days` later (business days skip Sat/Sun), in the recipient's zone.
    - `email` — the mailbox: the previous step's for a reply-in-thread step, else `pick`. None available → the
      step is rescheduled (`POOL_RETRY`), never dropped. Then the send time: the next open window instant in the
      recipient's zone, spaced by `nextSendAt`. The send is created **in the same transaction** as the enrolment's
      move to _waiting_ (`MailSendService.scheduleOutreach(tx, …)`), its job added after commit.
      Writes are conditional on the row still being where the run read it (`status`, `step_index`, `next_run_at`),
      so two deliveries of one job never both act.
- **The outreach send** is a scheduled send whose request says _outreach_: at its time `activate` builds it as
  the **member who enrolled the person** (#144: `enrolled_by_member_id` on the enrolment is the send's
  `senderMemberId`; an API key's enrolment is its creator's) — the mail itself speaks as the pool mailbox's
  owner (From name, `{{sender.*}}`), since the mailbox is that person's identity — from the step's **outreach**
  template (rendered with the outreach footer and postal address), issues the recipient's unsubscribe token
  and puts both headers on. P2-3's refusals of a pool mailbox and of an outreach template for 1:1 mail stay.
- **Outcomes:** `MailSendService` now records `email.failed` (in the transaction that fails a send) besides
  the existing `email.sent`. The sequence consumer reads the send linked to the event:
    - sent → step done, advance (finish after the last step);
    - failed `mailbox.cap_reached` / `mailbox.paused` / `mailbox.domain_unverified` / mailbox unavailable →
      **reschedule the same step**;
    - failed `recipient.suppressed` → stop `suppressed`;
    - any other failure (`unsendable` — a missing variable — Gmail's refusal, `stale`) → **held**, with the
      send's message as the reason; `POST /enrolments/:id/resume` (after the data is fixed) re-runs the step.
    - a step's send cancelled by a member → held `send cancelled`.
- **Stops as they happen** (outbox consumer, idempotent): `email.replied` (the reply's people) → `reply`;
  `suppression.added` (the address's person) → `unsubscribe` / `complaint` / `bounce` / `suppressed`;
  `deal.*` on an enrolment's deal that left the sequence's pipeline or closed → `pipeline_exit`;
  `person.deleted` → `person_deleted`. A pending step send is cancelled when its enrolment stops.

**Reply, before a step:** any message from the person's address stored after `enrolled_at`. Conservative on
purpose: an out-of-office counts as a reply — a person who wrote back is not mailed again by a machine.

**States of a sequence:** draft (steps edited freely) → active → paused (no step runs; enrolments keep their
place; resuming re-adds due jobs) → archived (read-only; active and held enrolments stop `sequence_archived`).
Activating needs at least one email step, every email step's template of kind _outreach_, and the workspace's
postal address set (the outreach footer refuses without it). Editing steps on a sequence that has run follows the
step rule above: existing steps keep their order; added steps reach the enrolments that have not finished.

## Events (outbox)

`sequence.created`, `sequence.updated` (diff, status included), `sequence.archived`; `enrolment.created`,
`enrolment.stopped`, `enrolment.held`, `enrolment.finished`, `enrolment.step_completed`; `email.failed`. Not
records: no timeline entry (the per-person enrolment timeline is owed to P3-UI-1, doc 50 §D); webhooks deliver
them.

## API

- `GET/POST /sequences`, `GET/PATCH /sequences/:id`, `PUT /sequences/:id/steps` (the whole ordered list),
  `POST /sequences/:id/{activate,pause,resume,archive}` — `sequence:write` (read: `outreach:write` or
  `sequence:write` or `sequence:enrol`).
- `POST /sequences/:id/enrolments/preview`, `POST /sequences/:id/enrolments` (`{ personIds, dealId? }` →
  enrolled / skipped / refused), `GET /sequences/:id/enrolments`, `POST /enrolments/:id/{stop,reenrol,resume}`,
  `GET /people/:id/enrolments` — `sequence:enrol` (read: as above).
- `GET/PUT /outreach/region-policy` — read `outreach:write`, write `workspace:admin`.
- `GET/POST /outreach/exclusions`, `POST /outreach/exclusions/:id/remove` — `workspace:admin`.

## Unknown country (D-251, #142)

A person with no known country (no `country`, no company address, an address with no country-coded
domain) is **enrolled and flagged**: the screen returns a non-blocking `warnings` entry
(`region.unknown`) in both the preview and the enrol, and the enrolment records
`countryUnknownAtEnrol`. EU/UK/Canada stay blocked (D-247). If a country becomes known later and falls in
a blocked region, the enrolment stops with `region_blocked`: the sequences outbox consumer re-checks on
`person.updated` (country, emails, company) and `company.updated` (address), and the check before every
step does the same — so a lost event only delays the stop to the next step. The policy applies to every
running enrolment this way, not only the flagged ones.

## Task step (#136)

Doc 50 §D's builder draws "Task — Call if no reply → owner". A `task` step has a title (1–200
characters, enforced by the DTO and the `sequence_steps_shape` check). When it runs it creates a task on
the person through `TasksService.createIn` — the same write as a member's task (same checks,
`task.created`, timeline) — assigned to **the person's owner, else the member who enrolled them**, due at
the moment the step runs; the enrolment then **moves straight on** (the next step runs now; a wait step
after it sets the gap). The task and the move are one transaction, so a second delivery of the step's
job creates no second task. Completing the task does not drive the sequence: a reply or a stop condition
still does. The builder (P3-UI-1) has **Add task** with a title field.

**Shown (#158):** a task the step made remembers its enrolment and step (`tasks.sequence_enrolment_id`,
`tasks.sequence_step_id`, set by the runner through the one `TasksService.createIn` input — a request never sets
them), so the enrolment view carries `tasks[]`: title, status, due and completed times, assignee, in step order.
Completing the task shows there and drives nothing.
