# P1-6 — Transactional outbox for domain events

Issues #98 (the outbox) and #89 (P0-13, the timeline race in the suite), one change because the second is a
symptom of the first. Doc 48 FR-CRMS-3 (timeline), FR-CRMS-4 (webhooks), FR-CRMS-9 (stage rules). Builds on P0-2
(`withWorkspace`), P1-3 (timeline), P1-5 (webhooks), P2-2/P2-2a (mail sync, the two pools and the
no-network-in-transaction rule).

## What was wrong

A service published a domain event **after** its transaction committed, on an in-process `EventEmitter2`. Listeners
— the timeline, webhooks, stage rules, mail re-matching — then ran their own transactions. Three failure modes:

- **Lost work.** A listener whose transaction failed (pool exhausted, a deadlock, a bug, the process restarting
  between the commit and the emit) logged the error and the work was gone: a timeline entry never written, a webhook
  never delivered, a deal never moved by its rule. Nothing retried it and nothing recorded that it was owed.
- **Nothing durable to retry from.** The event existed only in memory, so even a sweep could not find it.
- **Flaky tests (#89).** `emit` does not await async listeners, so a test reading the timeline right after a request
  raced the listener; specs papered over it with polling loops of different bounds.

## The design

**1. The event is a row written with the change.** `DomainEvents.record(tx, event)` inserts into `outbox_events`
with the mutation's own transaction client, inside `withWorkspace`. The event exists exactly when the change
committed: a rollback takes it with it, a crash after the commit cannot lose it. Called outside a transaction it
throws (`NoOpenTransactionError`) rather than dropping the event. `recordAll` writes a batch with one insert (a bulk
action's hundreds).

**2. The table.** `outbox_events(id, seq, workspace_id, type, payload, created_at, completed_consumers, attempts,
next_attempt_at, lease_until, last_error, completed_at, failed_at)`. A tenant table in P0-2's shape: RLS enabled and
forced, the workspace-isolation policy, and an **append-only grant** — the app role may `SELECT` and `INSERT`, never
`UPDATE` or `DELETE`. Delivery state is written by the relay, which runs as the owner because it spans every workspace
(the same split as the webhook sweep and retention). A partial index on open rows (`completed_at IS NULL AND
failed_at IS NULL`, by `seq`) keeps the relay's scan independent of history. `payload` is the `DomainEvent` as recorded.

**3. The relay** (`OutboxRelay`). A scan claims due rows — open, `next_attempt_at` passed or null, no live lease — in
one statement: `UPDATE … SET lease_until = now + OUTBOX_LEASE_MS, attempts = attempts + 1 WHERE id IN (SELECT … ORDER
BY seq LIMIT OUTBOX_BATCH FOR UPDATE SKIP LOCKED) RETURNING …`. Claims never overlap, so any number of processes may
relay at once. Each claimed event goes to every consumer that accepts it and has not finished it, `OUTBOX_CONCURRENCY`
events at a time, each consumer in a **job scope** — so its `withWorkspace` uses the **background pool**, never a
request's. Then the outcome is written and the lease released:

| Outcome                                     | Written                                                                                         |
| ------------------------------------------- | ----------------------------------------------------------------------------------------------- |
| every consumer succeeded                    | `completed_at`, `completed_consumers`                                                           |
| one failed, attempts left                   | `completed_consumers` (the ones that finished), `last_error`, `next_attempt_at` = doubling wait |
| one failed on attempt `OUTBOX_MAX_ATTEMPTS` | `failed_at`, `last_error` — kept for inspection, never claimed again, logged as an error        |

A relay that dies mid-delivery writes nothing; its lease expires and the next scan claims the event again.

**4. Wake-up.** `withWorkspace` now collects after-commit hooks (`afterCommit` in `transaction-scope.ts`): run once the
commit is through, discarded on rollback. `record` registers one that **kicks** the relay, so a local commit is
delivered at once. The kick runs the relay **detached** from the request's async context (`WorkspaceContext.detached`):
its work is neither on the request pool nor counted by the request's query observers. A timer scans every
`OUTBOX_POLL_MS` for what no local commit announced — retries that came due, expired leases, events another process
committed — and the relay scans once at start. `OUTBOX_RELAY=0` turns both off for a process that must not deliver
(compile-only runs; the placeholder env sets it).

**5. Consumers are idempotent on the event id.** Delivery is at least once, so:

| Consumer (`@OutboxConsumerOf`) | Accepts                               | Idempotent because                                                                                                                                                                                                                                                                         |
| ------------------------------ | ------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `timeline`                     | every event (writes nothing for some) | entries carry `event_id`; unique `(workspace_id, event_id, target_type, target_id)`; written with `skipDuplicates`                                                                                                                                                                         |
| `webhooks`                     | every event                           | automatic deliveries unique `(event_id, endpoint_id)` (a partial index: a person's manual redelivery names the delivery it repeats, `redelivery_of_id`, and is outside the rule); `skipDuplicates`; only `pending` rows are enqueued, under their own id (the queue never holds one twice) |
| `stage-rules`                  | `email.replied`, `meeting.booked`     | a deal already in or past the rule's stage is left alone, so a redelivered event moves nothing                                                                                                                                                                                             |
| `mail-sync`                    | `mailbox.connected`, person changes   | the first import is queued once per mailbox (job id) and a re-sync imports nothing new; re-matching mail that already points at the person changes no participant, so it links nothing                                                                                                     |

A consumer's own events (a rule's `deal.stage_changed`, re-matching's `email.linked`) are recorded in the consumer's
transaction like any other, so they are as durable as the change that caused them. Consumer names are stored in
`completed_consumers` and must never change once deployed.

**6. Ordering.** None is promised. `seq` is insertion order, not commit order (a later `seq` can commit first), and
retries reorder further. No consumer depends on order: the timeline sorts by `happened_at`; webhook receivers get
`occurredAt` and the delivery id; rules compare stage positions.

**7. Retention.** Delivered rows are kept `OUTBOX_RETENTION_DAYS.completed` (7) days, failed ones 30, then deleted by
the relay's hourly pass as the owner (`prune`). Seven days covers inspection and a manual replay after an incident.

## Migrating every call site — no dual path

`EventEmitter2` and `@nestjs/event-emitter` are gone. Every `publish` after a commit became `record(tx, …)` inside the
transaction that makes the change: people, companies, opportunities (single and bulk — the `…In` methods still return
their event and the caller records it in the same transaction), notes, tasks, attachments, templates, stage moves
(`StageMoveService.announce(tx, …)`; pipelines, stage deletion, rules), mailboxes (connect, disconnect,
reconnect-needed), mail sync (`store` records the message's events with the message), mail send (scheduled,
cancelled). Listeners became `OutboxConsumer`s and throw on failure instead of logging and swallowing: the relay
retries them.

## Interaction with P2-2a's no-network-in-transaction rule

Unchanged and respected. `record` is a database insert inside the caller's transaction. The relay holds no
transaction while consumers run: the claim and the outcome are single statements, and each consumer opens its own
short tenant transaction. Network work in consumers — the webhook queue add, the sync job add — happens outside their
transactions, as before. The kick is an after-commit hook, never inside a transaction.

## Testing (#89)

`test/support/outbox.ts` has the two views the suite needs:

- `settle(app)` — `OutboxRelay.drain()`: delivers until nothing is due, waiting for a pass already in flight. Every
  spec that asserts a consumer's effect after a mutation (timeline entries, webhook delivery rows, rule moves, mail
  re-matching) calls it first. The polling helpers (`until`, `eventually`) and the sleeps before negative webhook
  checks are gone: a negative check is "settled, and no delivery row exists".
- `eventLog(app, …patterns)` — reads what was recorded since it was opened (or `reset`), from the outbox, in order.
  Recording is synchronous with the request, so this needs no waiting.

`test/cross-tenant/outbox.spec.ts` runs with the relay's timer off and drives delivery with its own clock: a recorded
event before any consumer ran; a rollback records nothing; recording outside a transaction is refused; a failed
consumer is retried alone after its wait and writes once; a relay that died mid-delivery is redelivered after its lease
with no second timeline entry or webhook delivery; an event that fails every attempt is marked failed; retention; RLS
isolation and the append-only grant. `timeline.spec.ts` reproduces #89's race by holding the timeline consumer until
the request has answered.

Deliberately not covered by the suite: several API processes relaying the same database at once. `FOR UPDATE SKIP
LOCKED` with a lease is the standard pattern; staging and production run one process today.

## Operations

- New env flag `OUTBOX_RELAY` (default `1`). Staging's bootstrap writes it; an existing env without it relays.
- An event stuck open shows in `outbox_events` with `attempts`, `last_error` and `next_attempt_at`; a failed one has
  `failed_at`. Replaying a failed event: set `failed_at = NULL, attempts = 0, next_attempt_at = NULL` as the owner;
  consumers that finished it are skipped (`completed_consumers`).
