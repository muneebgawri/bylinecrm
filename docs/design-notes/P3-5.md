# P3-5 — Free verification layer (FR-CRMS-14, FR-CRMS-16)

Doc 49 Phase 3. Depends on P3-3 (sequences and the one enrolment check, #115) and #142 (the check returns
warnings, D-251), on P3-2's DNS port (FR-CRMS-13) and on P3-1's pattern of one address-keyed check.

**Scope of this package:** the `Verifier` port (FR-CRMS-16: the interface a vendor adapter plugs into — doc 49 lists
P4-1 against it, so P3-5 names it on the port's test only) and the free layer behind it (FR-CRMS-14), the stored answers and how long
they stand, the results wired into the one enrolment check and into the step runner before every send, and
the settings section that explains the four results and sets the age. No SMTP probing — nothing connects to a
recipient's mail server — and no vendor: P4-1 adds a vendor adapter behind the same port, off by default.

## What the FRs ask, and where it is enforced

| Requirement                                                                            | Where                                                                                                                                                                                                                                       |
| -------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Syntax, MX lookup, disposable-domain list, role-address detection (FR-CRMS-14)         | `address-checks.ts` (pure: `parseAddress`, `isRoleAddress`, `isDisposableDomain`, `judgeAddress`); `FreeVerifier` does the one MX lookup through `DnsPort.resolveMx`                                                                        |
| Results `valid \| invalid \| risky \| unknown`; `unknown` is not valid, does not enrol | `EMAIL_VERIFICATION_RESULTS` in `@bylinecrm/shared`; `EnrolmentScreen` refuses `invalid` (`email.invalid`) and `unknown` (`email.unverified`), flags `risky` (`email.risky`), enrols `valid`                                                |
| One check: wired into the existing enrolment check                                     | `EnrolmentScreen.screen` calls `EmailVerificationService.check` last, for the people every cheaper gate let through — the preview and the enrol make the same decision, and the dialog shows these reasons like any other                   |
| Re-verified before the next send (FR-CRMS-14)                                          | `SequenceRunner.run` calls the same `check` before every email step: `invalid` stops the enrolment (`invalid_address`, with the reason), `unknown` reschedules the step (`SEQUENCE_VERIFY_RETRY_MS`) — never sent unverified, never dropped |
| A result older than a workspace-set age (default 90 days) is stale and re-run          | `email_verification_settings.max_age_days` (1–365; no row = 90); `isVerificationStale` dates it from `verified_at`; `unknown` is always stale, so a DNS failure is never kept                                                               |
| No network inside a transaction                                                        | `check` reads in one short transaction, verifies with none open (the DNS adapter asserts it), writes in another                                                                                                                             |

## The verdict (`judgeAddress`)

In order, each `invalid`: not an address (one `@`, a dot-atom local part of at most 64 characters, a dotted host
name with a letters-only TLD; an internationalised domain by its ASCII form); no such domain (NXDOMAIN); the
domain exists but has no MX record (NODATA); a null MX (RFC 7505, the single exchange `.`). Then `risky`: the
domain is on the disposable list (`disposable-email-domains`, MIT, exact match) or the local part names a
function (`ROLE_LOCAL_PARTS`: RFC 2142 and the common ones around it — `info`, `press`, `editor`, `hello`…).
Otherwise `valid`. A lookup that fails (timeout, SERVFAIL) is `unknown`, with the domain named.

**Why no MX is `invalid` and not `risky`:** RFC 5321's implicit MX (an A record) is a corner case outreach
verifiers treat as undeliverable; refusing it costs one prospect, sending to it costs a bounce on a pool mailbox.
**Why `risky` enrols with a warning:** the FR singles out `unknown` as the result that does not enrol; a role
or disposable address is deliverable, and whether to mail `press@` is the member's call — the preview shows it
beside the no-country flag (D-251). Open question 1 below.

## Data model (migration `20261012060000_email_verification`)

- `email_verifications (workspace_id, address, result, reason, message, source, verified_at, created_at,
updated_at)`, PK `(workspace_id, address)`; `address` is stored as compared (lower case, trimmed — checked);
  `result ∈ valid | invalid | risky | unknown`; `reason` is the `EmailVerificationReason`; `source` names the
  verifier (`free`). One row per address per workspace: two people with one address share it; a changed address
  is a new one. Replaced by the next check, never deleted.
- `email_verification_settings (workspace_id, max_age_days, updated_by_member_id, updated_at)`: an override;
  no row means 90 days. `max_age_days BETWEEN 1 AND 365` (checked).
- `enrolment_stop_reason` gains `invalid_address`.

Both tables: RLS `workspace_isolation`, `FORCE`, app-role grants without `DELETE`. The schema-invariants spec
covers them.

## The check (`EmailVerificationService.check`)

`check(workspaceId, addresses, { force?, now? })` → every address asked for, keyed, each with `stale`. It reads the
stored rows and the age in one transaction; the missing, stale (`verified_at` older than the age) and `unknown`
ones go to the verifier with no transaction open, at most `VERIFY_CONCURRENCY` lookups in flight (`mapPool`,
now in `infra/` — the one bounded fan-out, shared with mail sync); the answers are upserted in another
transaction. `force` finds every address again (the person's _Verify now_).

Who calls it: the enrolment screen (one call per preview or enrol, for the batch), the step runner (one address,
before each email step), the person endpoint (forced). No outbox event: a verification is a fact about an
address, not a change to a record; the enrolment it stops records `enrolment.stopped` as any stop does.

## API

- `GET /outreach/verification` (`outreach:write`), `PUT /outreach/verification` `{ maxAgeDays }` (`workspace:admin`)
  → `{ maxAgeDays, isDefault, updatedAt }`.
- `GET /people/:id/verification` (`record:read`) → `{ address, verification | null }`: what is stored, never a
  lookup. `POST /people/:id/verification` (`outreach:write`) → the result, found again now; `409` when the person
  has no address; `404` when they are not visible.
- Enrolment preview and enrol: `refused[].code` gains `email.invalid` and `email.unverified`; `warnings[].code`
  gains `email.risky`; the message is the verdict's, naming the domain.

## Screen (Settings → Verification)

Read with `outreach:write`, the age set by an admin: the four results with what each means and what the
enrolment check does with it, then _Re-verify after_ (days; the server refuses the range with the field named,
`fieldErrorAt`). The enrol dialog needs no change: it already lists every refusal and warning the server returns.

## Open questions for the owner

1. **`risky` enrols with a warning** (role address, disposable domain) — or should a disposable domain refuse?
   Both are a one-line change in `EnrolmentScreen`.
2. **Reading of FR-CRMS-16:** `docs/fr-scope.txt` lists it under P4-1 (the vendor adapter); the handoff lists it on
   P3-5 too. Taken here as the `Verifier` port, which P4-1 implements; the re-verification age is FR-CRMS-14's.
   If FR-CRMS-16 is something else, the titles move, nothing else.
3. **The disposable list** is a dependency (`disposable-email-domains`, ~120k domains, MIT) refreshed with
   dependency updates; a workspace cannot add to it. A per-workspace extension is small if wanted.
