# P3-1 — Suppression and one-click unsubscribe

Issue #103. Doc 48 FR-CRMS-7 (and §6.1, FR-CRMS-12's footer); doc 49 §Phase 3; doc 50 §C/§D (refusals are shown,
never silent); parity ledger PAR-017, PAR-040, PAR-043. Builds on P2-3 (`SendPolicy`, `buildMime`, `deliver`), P2-4
(the outreach footer and `{{unsubscribe_url}}`), P2-5 (a scheduled send is checked again at its time).

## What FR-CRMS-7 asks, and where each part lives

| Requirement                                                              | Here                                                                                       |
| ------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------ |
| A suppression list per workspace: unsubscribes, hard bounces, complaints | `suppressions` table + `SuppressionService`                                                |
| Checked on every send                                                    | `SendPolicy.assertSendable` — at the request, at a scheduled send's time, before each try  |
| Checked on every enrolment                                               | `SuppressionService.check` — the same query; P3-3's enrolment calls it                     |
| `List-Unsubscribe` + `List-Unsubscribe-Post` (one-click) on outreach     | `UnsubscribeService.issue` → `buildMime({ listUnsubscribe })`                              |
| A visible link                                                           | the outreach footer's `{{unsubscribe_url}}`, replaced per recipient (`withUnsubscribeUrl`) |

## Data (migration `20261011000600_suppression`)

- **`suppressions`** — one live row per (workspace, address): `address` (lower case, checked), `reason`
  (`unsubscribe` | `hard_bounce` | `complaint` | `manual`), `source` (`recipient` — the person used the link;
  `member` — added in the CRM; `provider` — a bounce or complaint report, P3-2), `person_id` and `outbound_id`
  when known (the person the address belonged to and the message that led to it), `note`, `created_by_member_id`,
  `created_at`. **Removal is recorded, never deleted**: `removed_at`, `removed_by_member_id`, `removal_note`. A partial
  unique index (`workspace_id, address WHERE removed_at IS NULL`) keeps one live entry per address; the history stays.
- **`unsubscribe_tokens`** — one per (workspace, recipient, message): `token_hash` (SHA-256 of a 32-byte random
  token, unique), `address`, `person_id`, `outbound_id`, `created_at`, `used_at`. The token itself is never stored.
- Both are tenant tables in P0-2's shape (`workspace_isolation`, FORCE). The app role has SELECT, INSERT, UPDATE and
  **no DELETE** on either.

## One check

`SuppressionService.check(workspaceId, addresses)` → the live entries among them (one indexed query). It is the only
place the list is read for a decision:

- **`SendPolicy.assertSendable(workspaceId, recipients)`** calls it on every send. A suppressed recipient refuses the
  whole send with **`422 recipient.suppressed`**: one `fieldErrors` entry per suppressed recipient at the field it was
  in (`to`, `cc`, `bcc`), saying why (`unsubscribed`, `hard bounce`, `spam complaint`, `suppressed by a member`). A
  send is never quietly trimmed of a recipient — what was written is what goes, or nothing does.
- It runs at the request (P2-3), at a scheduled send's time (P2-5's `activate` rebuilds through `prepare`), and in the
  delivery job **before every Gmail attempt** — so an address suppressed while a send waited in the queue, or between
  two attempts, is not sent to. On a retry after an attempt that may have reached Gmail, the job still looks for the
  message first (P2-3a): a message Gmail already accepted is recorded as sent, because it was; only an unsent message is
  refused. A refused delivery fails the send with `last_error.code = 'recipient.suppressed'`.
- **P3-3** (enrolment) calls `check` for the people it is about to enrol and lists the refused ones with the reason
  (doc 50 §D: "refused ones are listed, not silently skipped").

## Which mail carries the unsubscribe headers

FR-CRMS-7: "Every **outreach** message carries `List-Unsubscribe` and `List-Unsubscribe-Post`". So:

- **Outreach** (a sequence's step, from the sending pool, rendered from an outreach template): both headers, and the
  footer's visible link — one token per recipient and message. These are what inbox providers require of bulk senders
  (RFC 8058; Gmail's and Yahoo's 2024 sender rules).
- **Personal 1:1 mail** (P2-3's send from a member's own mailbox, never an outreach template — P2-3 refuses one):
  **no** unsubscribe headers or link. It is correspondence, not a mailing; a `List-Unsubscribe` header would make Gmail
  offer "unsubscribe" on a reply to a client. The suppression check still applies to it: a person who unsubscribed is
  not mailed by anyone in the workspace.

Until P3-3 builds the outreach send, nothing in production calls `issue`; the tests drive it through the same
functions P3-3 will (`issue` → `withUnsubscribeUrl` → `buildMime`), end to end with the public endpoint.

**No `mailto:` in `List-Unsubscribe`.** RFC 8058 requires the HTTPS URI; a `mailto:` is optional, and it would promise
an inbox that reads unsubscribe requests. None exists yet. P3-2 (bounce and complaint ingestion) owns the pool's
inbound processing; if it adds a reply-to-unsubscribe address, it adds the `mailto:` then.

## Tokens

- `randomToken()` (32 bytes, base64url) — unguessable; stored as `hashToken()` only. It names nothing: no workspace id,
  person id or address can be read from it, and a changed character is a token that does not exist (`404`).
- One per (workspace, recipient, message), created when the message is built (`issue`, inside the same workspace
  scope). A token suppresses its own address **in its own workspace only** — the workspace is read from the token's
  row, never from the request. The same address in another workspace is untouched.
- **They do not expire.** An unsubscribe link must keep working (CAN-SPAM: at least 30 days after the send; inbox
  providers expect it always). A used token stays usable — clicking twice is harmless.

## Public endpoints (no session, `@Public()`)

| Route                                | Does                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| ------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `POST /api/unsubscribe/:token`       | One-click (RFC 8058) and the confirmation page's button: suppresses the address (`reason = unsubscribe`, `source = recipient`), marks the token used, publishes `suppression.added`. Idempotent: an address already suppressed answers the same and writes nothing. The body is ignored (RFC 8058 sends `List-Unsubscribe=One-Click` as form data, urlencoded or multipart) — the token is the proof. `200 { recipient, unsubscribed: true }`. |
| `GET /api/unsubscribe/:token`        | Never changes anything — link scanners and mail clients prefetch GETs. `303` to the web page `/unsubscribe/:token`. A client that opens the header's URL in a browser lands on the page.                                                                                                                                                                                                                                                       |
| `GET /api/unsubscribe/:token/status` | What the page shows: `{ recipient, unsubscribed }`. `recipient` is masked (`d•••@acme.example`) — the token holder learns nothing they did not already have, and a leaked link shows no full address.                                                                                                                                                                                                                                          |

- An unknown token is `404 not_found` on all three, with nothing about why.
- **Rate limit:** `UNSUBSCRIBE_RATE_LIMIT` requests per client IP per window, on all three routes (Redis fixed window,
  the auth limiter's). Over it is `429 rate_limited`. The limiter fails closed, as login's does.
- **No CSRF dependency:** the route needs no session, so a forged request can at most unsubscribe the address the
  token was issued to — which is the action the token exists to allow. A signed-in member opening the page gets the CSRF
  header from the web client like any other call.
- The visible link points at the web page (`${WEB_URL}/unsubscribe/:token`); the header points at the API
  (`${APP_URL}/api/unsubscribe/:token`), which takes the POST.

## Members' list (Settings → Suppression)

| Route                                                   | Gate                               |
| ------------------------------------------------------- | ---------------------------------- |
| `GET /api/w/:id/suppressions?q=&reason=&cursor=&limit=` | `outreach:write`                   |
| `POST /api/w/:id/suppressions` `{ address, note? }`     | `outreach:write` — reason `manual` |
| `POST /api/w/:id/suppressions/:id/remove` `{ note }`    | `workspace:admin`                  |

- Adding an address already suppressed is `409 conflict.unique` naming `address`.
- **Who can lift an entry, and which ones.** An `unsubscribe` or a `complaint` is the person's own choice and is
  **never lifted from inside the CRM** (`409 conflict`): only the person can undo it, and v1 offers no re-subscribe.
  A `hard_bounce` (an address can be fixed) or a `manual` entry can be lifted by an admin, with a note saying why; the
  entry keeps who lifted it and when. This follows Twenty's rule that bounces and complaints are permanent (PAR-043) and
  goes further for unsubscribes, which Twenty lets only the person reverse too.
- `outreach:write` is the gate because the list is the outreach list's other half; members without it never send
  outreach and see their own sends refused with the reason, not the list.

## Events

`suppression.added` and `suppression.removed` (object `suppression`, `recordId` the entry): `suppression = { address,
reason, source, personId }`, `related` = the person when known. Recorded with `DomainEvents.record` in the transaction
that writes the entry (the outbox, P1-6) — a superseded entry's `suppression.removed` and the new entry's
`suppression.added` in the same one — so an event exists exactly when its change committed; the relay delivers
them and webhooks send them. No timeline entry: a suppression is not one of the timeline's record or linked objects;
showing it on the person page is P3-UI's (the record page's associations).

## The write API P3-2 uses

`SuppressionService.suppress(workspaceId, { address, reason, source, personId?, outboundId?, note? })` — background,
explicit workspace, idempotent (an address already suppressed keeps its first entry; a stronger reason does not
overwrite history — the event says nothing new happened). Bounce and complaint ingestion calls it with
`source = 'provider'`.

## Web

- **Settings → Suppression** (`/w/:id/settings/suppression`, lazy, `outreach:write`): the list with search and a reason
  filter, _Suppress an address_ (address + optional note), _Lift_ on a liftable row (admin; confirmation with a required
  note). The page says above the list that unsubscribes and complaints are permanent; their rows have no menu. Light and dark through the tokens; on a phone the
  table collapses to cards (`DataTableChrome`'s phone layout).
- **`/unsubscribe/:token`** (public, lazy, outside the shell): reads the status, shows the masked address and one
  **Unsubscribe** button; after it, "You're unsubscribed". Already unsubscribed shows that at once. An unknown link
  says the link is not valid. No sign-in, no workspace name, no CRM chrome.

## Decisions and deviations

- **A refused send fails whole** rather than dropping the suppressed recipient (Twenty skips per recipient,
  PAR-040). A personal send is written to specific people; sending it to some of them silently changes what was
  written. Sequences (P3-3) send one recipient per message, so for them refusing and skipping are the same thing.
- **Tokens are stored, not signed.** A signed token would have to carry the workspace and address (encrypted), could
  not be revoked, and would tie every link ever sent to one key. A stored random token is revocable, carries nothing,
  and costs one row per outreach message.
- **Owner client for the token lookup only**, as invitation acceptance does: the public route has no workspace until
  the token names one. The lookup reads one column (`workspace_id`) by hash; everything after runs under RLS in that
  workspace.
