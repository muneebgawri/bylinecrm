# P2-2a — Background mail work can't starve requests

Issue #86, found in the real-Gmail test (2026-10-11). Doc 48 FR-CRMS-2. Builds on P0-2 (the RLS client,
`withWorkspace`), P1-5 (webhook workers and sweep), P2-2 (sync), P2-3 and P2-5 (send, scheduling).

## What happened

The initial import of two real mailboxes made 16 ordinary requests (`/me`, `/mailboxes`,
`/mail/oauth-client/status`, `/mail/blocklist`) fail with Prisma **P2028**, "Transaction API error: Unable to start
a transaction in the given time". Every tenant query is an interactive transaction pinning one pooled connection.
Workers (sync runs 4 mailbox jobs, each fetching 5 messages at a time), the event listeners each stored message
triggers (timeline entries per record, webhook deliveries) and every request shared one pool of 10. Listener bursts
held it; requests waited past Prisma's 2 s `maxWait` and failed. `withWorkspace` retried P2024 (pool exhausted) but not
P2028, so the failure reached the caller. The load test in `test/cross-tenant/pools.spec.ts` reproduces it on `main`:
the import itself dies with P2028.

## The fix

**1. Two tenant pools, one `withWorkspace`.** `RlsPrismaService` stays the request pool; it now also owns
`backgroundClient` — same role, same URL, its own connections. Which pool a transaction uses is decided by the
`WorkspaceContext` it runs in, not by the caller:

| Context                                                                                                                | Pool                                  |
| ---------------------------------------------------------------------------------------------------------------------- | ------------------------------------- |
| A request's scope (`begin`, opened by the request middleware)                                                          | request (`REQUEST_POOL_SIZE` 10)      |
| A job's scope (`run`), a BullMQ worker callback, a sweep, a listener triggered by any of these, code outside any scope | background (`BACKGROUND_POOL_SIZE` 6) |

No service picks a pool, so none can pick wrong; a forgotten timer or a new worker lands on the background pool by
default. Background work may wait for its own pool; it can never take a request's connection. A listener triggered by a
request still runs in that request's scope, on the request pool, which is right: it is that request's work.

**2. Known connection total.** The owner client now gets an explicit size too (`OWNER_POOL_SIZE` 5) instead of Prisma's
CPU-based default, so one API process opens at most **10 + 6 + 5 = 21** connections. Postgres' default
`max_connections` is 100 (local compose and CI's service container); the staging/production compose sets its own and
runs one API process — 21 must stay below it minus `superuser_reserved_connections` (3 by default). An explicit
`connection_limit` in a URL still wins. The sum lives in the header of `rls-pool.constants.ts`, next to the numbers.

**3. Retry the start timeout — only when nothing ran.** `withWorkspace` now passes `maxWait: TRANSACTION_MAX_WAIT_MS`
(5 s; Prisma's default is 2 s) and retries, with the existing bounded doubling backoff (3 tries, 100 ms base), when the
transaction never got a connection: Prisma **P2024**, or **P2028** _while the callback had not started_. P2028 is
Prisma's code for every Transaction API error — including a transaction that expired or closed mid-work — so the
retry is gated on a `started` flag set as the callback begins: retrying after the callback ran could do its work twice.
Matched by code, never by message text.

**3a. An explicit run timeout.** Every tenant transaction also gets `timeout: TRANSACTION_TIMEOUT_MS` (15 s) instead of
Prisma's 5 s default. That timeout counts wall time from start to commit; in the first full run of the suite on a
heavily loaded machine, transactions that do milliseconds of work — a guard's membership read, a synced message's
store, a listener's timeline entry — expired at 5.2–5.6 s because the process was paused, and an expired transaction
is not retried, so its work was lost. No transaction waits on the network (point 4), so a long-running one is a stuck
one; 15 s is the ceiling after which Prisma rolls it back and releases its connection.

**4. No transaction across a network call — enforced.** `withWorkspace` runs its callback marked in an
`AsyncLocalStorage` (`infra/transaction-scope.ts`). `assertNoOpenTransaction(call)` throws
`TransactionAcrossNetworkError` inside a marked chain. It is called at every network boundary the tests reach: the
Gmail fake (`getProfile`, `listMessages`, `listHistory`, `getMessage`, `send`), the Google OAuth fake (`exchangeCode`,
`refresh`, `mailboxAddress`, `grantedScopes`, `revoke`, `probeClient`) and the production webhook sender. Any code path
that calls out while holding a tenant transaction now fails the suite at that call.

## The audit

Every Gmail, Google and webhook call was already outside a transaction: read in a short `withWorkspace`, let it end,
call out, write in another. The instrument confirms it across the whole cross-tenant suite.

- **Sync** (`MailSyncService`): mailbox and state reads, `knownIds`, the blocklist and each `store` are separate short
  transactions; list, history and `getMessage` fetches happen between them (`importIds` fetches a chunk, then stores
  sequentially).
- **Send** (`MailSendService.deliver`): the outbound row is read and marked `sending` in their own transactions; the
  token, the `findSent` lookup and `gmail.send` run outside; the result is written in a new transaction.
- **Tokens** (`MailboxTokens`): read, refresh under a Redis lock (`google.refresh` outside any transaction), write.
- **Connect / disconnect / check / verify**: the code exchange, address lookup, revoke, scope probe and client probe
  all run between transactions.
- **Webhooks** (`WebhooksService.attempt`, `test`): delivery prepared in one transaction, `sender.send` outside,
  outcome written in another.

**No transaction boundary had to move.** What changed is the pool those transactions use, and the retry.

## Tests

- `test/cross-tenant/pools.spec.ts` — 4 mailboxes × 150 messages (each concerning matched people, so timeline and
  webhook listeners fire per message) import concurrently outside any request while rounds of 50 concurrent GETs run
  until the imports end: every GET answers 200 and all 600 messages are imported. **Fails on `main` with P2028.**
  Teardown waits for the imports, then removes the deliveries and jobs they queued for its never-answering endpoint,
  so later specs on the shared queue and database do not inherit a backlog.
- `src/infra/rls-prisma.service.spec.ts` — request scope → request pool; job and no scope → background pool; P2028
  retried before the callback starts, not after; every transaction gets the explicit wait and timeout; the guard throws inside a transaction and not outside;
  `withPoolDefaults` applies the given size.
- Every existing spec that reaches Gmail, Google or a webhook receiver now also checks the network rule.

## Not in this card

A separate worker process (the `*_WORKER` flags already allow it) would give background work its own process as well
as its own pool; on one box the separate pool is the part that matters.
