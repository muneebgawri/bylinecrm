# P2-3a — Gmail rewrites our Message-ID (#87)

**Finding (real Gmail, 2026-10-11).** A send with `Message-ID: <f5cd0e89-…@bylinecrm>` was stored and
delivered by Gmail as `<CABNQ5Yo…@mail.gmail.com>`. Two consequences:

- **Lost answer → double send.** P2-3's retry looked the send up with `rfc822msgid:<ours>`, which can
  never match a rewritten id. Proven red on `main`: with a fake that rewrites like Gmail and a send whose
  answer is lost, the message went out twice (`expected 10 to be 9`).
- **Reply matching survived, by luck of order.** The real reply carried Gmail's id in `In-Reply-To`. It
  matched through `mail_messages.rfc822_message_id` of our send's _stored copy_ (linked a second after
  sending by the send job's import), not through the send row, and the thread fallback would have caught
  it too. The new tests for both paths pass on `main` and still pass here.

**What changed**

1. **Our own header.** Every MIME carries `X-BylineCRM-Id: <send id>` (`MAIL_CRM_ID_HEADER`). Gmail keeps
   custom `X-` headers. The send's id is fixed (`randomUUID`) before the message is built, so a scheduled
   send rebuilt at its time carries the same id.
2. **Finding a send after a lost answer.** Before any re-send, `findSent` lists `in:sent to:<first
recipient> after:<created − skew>` (newest first) and reads each candidate's `X-BylineCRM-Id` only
   (`format=metadata`, new `GmailPort.getMessageHeaders`), at most `MAIL_SEND_DEDUPE_MAX_CANDIDATES` (25).
   A match is recorded as sent; no match re-sends. Every lookup request counts against the mailbox quota
   (`MailSyncService.chargeQuota`). **Deviation from the card:** the subject is not in the Gmail query.
   Gmail's `subject:` search tokenises and needs quoting that a subject with quotes or symbols breaks, so
   a subject filter could hide the message we are looking for and cause the double send it exists to
   prevent. Recipient + time window bound the search; the header confirms it.
3. **One source for Gmail's Message-ID.** `mail_outbound.provider_rfc822_message_id` (migration
   `20261011000100`) is written by sync's writer when it links the stored copy — the one writer. The copy
   is linked by our header first, then Gmail's message id, then our Message-ID where Gmail kept it. A
   send whose answer was lost also learns Gmail's message and thread ids there.
4. **Reply matching** reads both ids from the send row (`rfc822_message_id`, `provider_rfc822_message_id`)
   plus the thread fallback; the join to the stored copy is gone. Still one `email.replied` per reply.

**Not changed:** statuses, events, API shapes (`openapi.json` is unchanged).

**The fake Gmail rewrites every send's Message-ID**, as real Gmail does, with no opt-out. A fake that kept
our Message-ID is how #87 got past the P2-3 suite. Each `sent` entry records the Message-ID Gmail
delivered (`messageId`), so a test replies the way a real recipient does. One older test relied on the
old behaviour — the P2-3 reply test named our own Message-ID, which no recipient of a real Gmail send
sees; it now names the delivered one.

**Fixes a defect shipped in P2-3 (#78).** The same-thread fallback compared the reply's `Date` header
(whole seconds, RFC 5322) with the send's `created_at` (milliseconds), so a reply within the send's own
second read as older than the send and was missed. It now compares with `date_trunc('second',
o.created_at)`; the regression test is "recognises a reply in the same Gmail thread without
In-Reply-To", which delivers the reply dated at the send's whole second.

**Interaction with P2-2a (#86).** That card moves transaction boundaries in mail-send; this one touches
MIME building, `findSent` and reply matching only. `findSent` runs inside the `gmailRequest` callback and
opens no transaction.
