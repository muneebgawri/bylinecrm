# P1-2b — Delete a stage by moving its deals; restore archived custom fields

Issue #74. Builds on P1-2 (pipelines, the one move service), P1-2a (one move = one event) and P1-1d
(the one error envelope).

## Deleting a stage

`DELETE /api/w/:id/pipelines/:pipelineId/stages/:stageId[?moveDealsTo=<stageId>]` (`pipeline:configure`).

- **The plan is a pure function** (`pipelines/stage-delete.ts`, `planStageDelete`), unit-tested rule by
  rule. In order: a stage rule pointing at the stage refuses (`conflict`, `details.rules`); the last
  stage of a pipeline refuses; without `moveDealsTo`, a stage holding deals refuses with
  `details: { liveDeals, trashedDeals }` so the UI can say what is in the way without parsing the
  message; with it, the target must be another stage of the **same pipeline** (else `404`) and
  **open** (else `400 validation.failed` on `moveDealsTo` — closing deals is never a side effect of a
  delete; architect's decision); more than `STAGE_DELETE_MOVE_LIMIT` (5,000) deals answers `413
payload_too_large` with `details: { deals, limit }`.
- **`moveDealsTo` is a query parameter**, not a body: DELETE request bodies do not reliably survive
  proxies. (The issue said "accepts `{ moveDealsTo }`"; the name and meaning are the same.)
- **The move goes through the one move service.** `StageMoveService.moveAllInStage` is set-based —
  one `updateMany`, one `createMany` of history rows — because the interactive transaction has a 5 s
  limit and thousands of per-deal moves would not fit. It is still the only code that sets `stage_id`
  for this case, and it applies `move`'s rule for an open target: a deal that was won or lost
  reopens (its close columns cleared). Trashed deals move too; they hold the stage as firmly as live
  ones, and after a restore they sit in the target stage.
- **Events:** after commit, one `deal.stage_changed` per moved deal (the target is open, so never
  `deal.won`/`deal.lost`), reason `stage_deleted`, actor the caller. The timeline and webhooks see
  ordinary moves.
- **Owner scope:** this is configuration over every deal in the stage, so an own-scoped caller (who
  sees only their own deals) is refused with `403` up front rather than half-served; for everyone
  else owner scope does not narrow it. Before this change an own-scoped configurer could delete an
  empty stage; now they cannot delete any stage.

## History outlives the stages it names (a latent defect, fixed)

`opportunity_stage_history.from_stage_id/to_stage_id` were foreign keys with `ON DELETE RESTRICT`, so
**a stage that had ever held a deal could never be deleted** — even empty, the delete answered 500.
The existing "removes an empty stage" test passed only because that stage never held a deal. History
is an audit log: it must record where a deal was, including stages that no longer exist. Migration
`20261010000100_stage_delete`:

- adds `from_stage_name` / `to_stage_name`, backfilled from the current names, written by every
  history writer (`place`, `move`, `moveAllInStage`) from stages read in the same transaction;
- drops the two stage foreign keys (ids are kept: the web reads them, and the contract stays
  additive — `GET …/history` gains `fromStageName` / `toStageName`).

A deal page can now name a deleted stage; the web still looks names up by id (P1-UI-11 may switch).

## The error envelope gains `details`

`ApiErrorBody.details?: Record<string, string | number | boolean>` — flat facts a client acts on
(counts, limits), present only when the error has some. One definition in `@bylinecrm/shared`, the
filter renders it, the OpenAPI `ApiError` schema documents it. New typed errors: `StateConflict`
(409), `TooLarge` (413), `Forbidden` (403).

## Restoring an archived custom field

`POST /api/w/:id/custom-fields/:fieldId/restore` (`workspace:admin`) un-archives; the key is accepted
on records again and the cache is invalidated. Restoring an active field changes nothing. **It cannot
collide:** the key's uniqueness `(workspace, object, key)` includes archived definitions, so no new
field can take an archived field's key (a test pins that). The issue's "conflict.unique on collision"
case is therefore unreachable by construction.

## What P1-UI-11 does with this

"Move N deals to…" on a refused stage delete (using `details` for the counts and `moveDealsTo`), and
Restore for archived custom fields; optionally show `fromStageName`/`toStageName` in deal history.
