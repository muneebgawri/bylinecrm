# P3-4 — Tracking (FR-CRMS-8)

Doc 49 Phase 3. Depends on P3-3 (sequence steps sent through the one outreach send path), on P3-1 (the
unsubscribe link, never rewritten; the public-route pattern: an opaque hashed token names its workspace, a
rate guard per client IP), on P3-2's DNS port (FR-CRMS-13) and on P1-2's stage rules (FR-CRMS-9).

**Scope of this package:** a short-link domain per workspace, verified by its CNAME; links in outreach mail
rewritten to short links only while it is verified; the public redirect and open pixel; clicks and opens as
domain events through the outbox, on the person's timeline and counted on the send and the sequence step;
opens labelled _indicative_ everywhere and never able to move a stage; scanner hits kept out of every count.

## The short-link domain

An admin sets a hostname (`PUT /tracking/domain`, lower-cased, a hostname by the same rule the database
checks). The page shows the record to publish — `<domain> CNAME <API host>` — where the API host is `APP_URL`'s,
known before any domain is set (`GET` answers `{ cnameTarget, domain | null }`). _Check now_ resolves the CNAME:
`pass` when it points at that host, otherwise `fail` with the reason (no record; a record to another host; a
lookup that failed). Until `pass`, every outreach email goes out as written, and the page says so.

There is **no scheduled re-check**. A domain that stops resolving stops redirecting, which is visible at once
(the links in sent mail break), and the admin checks it again; a background re-check would add a job for a
state nobody acts on automatically. Open question 2 below.

A domain is one workspace's (`409 conflict.unique` to a second). The API serves every workspace's domain on
the same routes: the host is not checked, because the token already names its workspace and a host check
would add nothing a forged `Host` header could not pass.

## Tokens, hits and the two public routes

Building an outreach message (inside `prepareOutreach`, after the unsubscribe link), `trackOutreach` lists the
distinct `http(s)` links of the HTML part (decoded), issues one `click` token per link and one `open` token per
send (`tracking_tokens`, hashed), rewrites every `href` to `https://<domain>/r/<token>` and appends the pixel
`https://<domain>/o/<token>` before `</body>`. The text part keeps the real URLs: a plain-text reader sees
where they are going. Tokens are issued in one short transaction before the MIME is built; a send that then
fails leaves tokens nobody will hit, which is harmless and cheaper than issuing them in the send's own
transaction.

`GET /r/:token` and `GET /o/:token` are outside the `api` prefix (`setGlobalPrefix … exclude`) so the whole link
is the short domain and a path. Each resolves the token's workspace through the owner client (one column by
hash, as the unsubscribe route does), then under RLS: writes a `tracking_hits` row (the send, the person, the
step and the enrolment copied from the send, so a count never joins), and — unless the hit is a bot's — records
`email.clicked` / `email.opened` in the same transaction. Both answer `Cache-Control: no-store`: every fetch is
a hit. A click always redirects, bot or not: a scanner that is answered `404` flags the mail.

**Replay and tampering.** A token names exactly one (send, link). A second click is a second click (clicks 2,
unique 1), never a replay of the first. A changed character is a different hash: `404`, nothing written. There
is no workspace in the URL to tamper with; one workspace's tokens are invisible to another through RLS, and
the cross-tenant spec reads the tables from the other workspace to prove it.

## Bot filtering — the rule

A hit is a scanner's, kept with its `bot_reason` and **counted nowhere, announced as nothing**, when:

1. `scanner_user_agent` — the `User-Agent` is empty, or contains one of the marks in `bots.ts`: security
   gateways' names (Barracuda, Proofpoint, Mimecast, Safe Links, …), fetch libraries (`curl/`, `python-requests`,
   `Go-http-client`, …), headless browsers, and the generic `bot`, `spider`, `crawler`, `preview`,
   `linkexpanding`. A mail client's image proxy (Gmail's `GoogleImageProxy`) is **not** a scanner: it fetches
   when the person opens the mail, which is exactly what an indicative open means.
2. `too_soon_after_delivery` — the hit is within `TRACKING_BOT_WINDOW_MS` (2 s) of the send's `sent_at`. A
   gateway follows every link as the mail arrives; a person cannot.

Both are decided at the hit, from the request and the send row; nothing is re-classified later. A bot hit stays
in `tracking_hits` so the rule can be audited and tuned (open question 1). Changing the list or the window is
changing this note.

## Opens are indicative

An open is a `GET` of a 1×1 image. Mail clients prefetch images (Apple Mail Privacy Protection fetches every
one; Gmail proxies them), and an image blocked by the client is a read that never shows. So an open says a
client fetched the image, not that a person read anything. The product rule (doc 48 §7) follows: the event
carries `indicative: true`, the timeline line says "(indicative)", every count says "(indicative)", and no
decision reads it — the `stage_rule_event` enum has no `email.opened` (the DTO refuses it, the engine ignores
it: both tested), and sequences have no stop condition on it. A click is a person's act and may move a deal.

## Data model (migration `20261012070000_tracking`)

- `tracking_domains (workspace_id PK, domain UNIQUE, status, last_check, checked_at, created_at, updated_at)`;
  `status` reuses `sending_domain_status` (`unchecked | pass | fail`); `domain` is a lower-case hostname (checked).
- `tracking_tokens (id, workspace_id, outbound_id, kind, token_hash UNIQUE, url, created_at)`; `kind ∈ click |
open`; `url` with a click and never with the pixel (checked). Cascades with its send.
- `tracking_hits (id, workspace_id, token_id, outbound_id, kind, person_id, sequence_step_id, enrolment_id,
happened_at, user_agent, bot_reason, created_at)`; `bot_reason` is null or one of the two reasons (checked);
  indexed by `(outbound_id, kind)` and `(sequence_step_id, kind)` for the counts.
- `stage_rule_event` gains `email.clicked`.

All three: RLS `workspace_isolation`, `FORCE`; the app role may delete a domain (the admin clears it), never a
token or a hit. The schema-invariants spec covers them.

## Events

`email.clicked` and `email.opened` join `DOMAIN_EVENT_TYPES`: `recordId` is the send, `tracking` the
`EmailTrackingPayload` (send, person, URL or null, step, enrolment, `indicative`), `related` and `targets` the
person. The timeline consumer writes `linked-email.<action>` on the person with `linked.name` the send's
subject (`linkedName('email', …)` now falls back from a stored message to a send) and `properties.tracking`.
Webhooks deliver both like any event.

## Open questions

1. **The scanner list is a judgement.** `bots.ts` errs towards filtering (`preview`, `validator`, `bot`), so a
   rare real client containing one of those words would be dropped. The kept rows make a wrong call visible;
   the list grows from them.
2. **No automatic re-check of the CNAME.** If a product later shows "tracking is down" proactively, a due-time
   re-check through the sending pool's maintenance job (`SendingDomainsService.checkDue`'s pattern) is the
   place; nothing in this package needs it.
3. **The edge must route the short-link hosts to the API** (any host → the API's `/r/*` and `/o/*`), with TLS for
   each domain. The deploy's reverse proxy serves `APP_URL`'s host today; a customer's `go.example.com` needs a
   certificate (on-demand issuance, or a wildcard the operator owns). Documented in the deploy notes as a
   follow-up; the API side needs nothing more.
