# P1-2a — one stage move emits exactly one event

Issue #37, found by P1-UI-3: a single move into a won stage was announced twice — `deal.stage_changed` and then
`deal.won`, with the same change — so the timeline wrote two entries and a webhook endpoint subscribed to `*`
received two deliveries for one thing that happened.

## The rule

One move, one event, named by the kind of stage the deal lands in:

| Move                          | Event                |
| ----------------------------- | -------------------- |
| open → open                   | `deal.stage_changed` |
| any → won                     | `deal.won`           |
| any → lost                    | `deal.lost`          |
| won or lost → open (a reopen) | `deal.stage_changed` |

All three carry the same shape: `recordId` (the opportunity), `diff.stageId { from, to }` and `stage { pipelineId,
fromStageId, toStageId, reason }`. A close's details (won amount, lost reason) are on the deal itself, as before;
the event does not repeat them.

## Where the decision lives

`moveEventType(toKind)` in `pipelines/stage-moves.ts` is the whole rule, as a pure function; `StageMoveService.announce`
publishes the one event it names. Manual moves, rule moves and closes all go through that one service, so they
all follow the rule. The timeline (P1-3) and webhooks (P1-5) modules are unchanged: both take every catalogue
event as it comes, so one event in means one timeline entry and one delivery per subscribed endpoint.

## Who listened to `deal.stage_changed`

Checked before changing what it covers. Nothing in the API reacts to `deal.stage_changed` by name: the stage-rule
engine is triggered by `email.replied` and `meeting.booked` only; the timeline and webhook subscribers listen on
`**`; no stage rule, view or job filters on the type. So no behaviour stopped firing. The one consumer that sees
the narrowing is an external webhook endpoint subscribed to `deal.stage_changed` alone: it no longer receives
closing moves. The catalogue comment and the README now say to subscribe to all three to see every move.

## Tests

- Unit: `moveEventType` for open→open, open→won, open→lost and won→open.
- Cross-tenant (pipelines): a close emits only `deal.won` / `deal.lost`, a reopen only `deal.stage_changed`, and
  four moves of all four kinds leave exactly four timeline entries on the deal, each named by where it landed.
- Cross-tenant (webhooks): the same four moves deliver exactly four `deal.*` events to an endpoint subscribed to
  `*`, each landing stage under the event that names it.
