# P1-3 — Timeline activities

**Package:** doc 49 §5, Phase 1. **Loop step 2 (design).** Closes #15. Spec: parity ledger PAR-013 (an
activity per event), PAR-014 (a linked thing writes on each target), PAR-015 (deviated: mail and
company activity are one list, doc 50 §A); doc 48 §8 (an integration's event is a generic timeline entry).
Conventions: P1-1a's and P1-1b's design notes, followed exactly.

## Data touched

One tenant table, `timeline_activities` (migration `20261009000600_timeline`), under row-level security in
P0-2's shape, plus the enum `linked_object` (`note | task | attachment`).

| Column                      | What                                                                                                     |
| --------------------------- | -------------------------------------------------------------------------------------------------------- |
| `target_type`, `target_id`  | The record the entry is on: a `record_object` and its row, polymorphic like a note target.               |
| `kind`                      | `<object>.<action>`, `linked-<thing>.<action>` or `external.<kind>` — the shape says where it came from. |
| `happened_at`               | The event's `occurredAt`, or what the integration said.                                                  |
| `actor`                     | `TimelineActor`: a record's actor kinds plus `rule` (P1-2) and `external` (`id` = the source).           |
| `properties`                | The update's diff, as the event carried it; the linked thing's id and name; the external payload.        |
| `linked_type`, `linked_id`  | For `linked-…` entries, the note/task/attachment; both set or both null (the database checks).           |
| `source`, `idempotency_key` | External entries only; unique together per workspace; both set or both null, and only on `external.%`.   |

**Append-only is a grant, not a convention.** The app role gets `SELECT, INSERT` on the table and nothing
else; there is no update or delete route; `timeline.spec.ts` proves an `UPDATE` and a `DELETE` through the
RLS client are refused by Postgres. `schema-invariants.spec.ts` (P0-2) still sees a tenant table with its
policy — a policy `FOR ALL` whose `WITH CHECK` scopes inserts to the workspace; the missing grants are what
make it append-only.

## Where entries come from — two writers, one table

**The subscriber** (`TimelineSubscriber`) listens on `**` and keeps only catalogue events (`isDomainEventType`).
That is deliberate: an event a later package adds to the catalogue — P1-2's stage moves — is on the timeline
the day it is first published, with no edit here and nothing to coordinate; the kind is the event type itself,
derived by one function (`timelineKindOf`), never a second spelling. Delivery from the bus is synchronous to
the request that published, after that request's transaction committed; the subscriber catches and logs a
failure rather than throwing into a request that has already succeeded. `timeline.*` is never published, so
nothing loops.

- A **record's own event** (`person.updated`) leaves one entry on the record. An `updated` event's `diff`
  travels into `properties.diff` as the event carried it; nothing is re-read to recompute it.
- A **linked thing's event** (`note.created` with `targets`) leaves one entry on **each** target (PAR-014).
  The thing's display name — note title, task title, attachment name — is read once at write time and
  cached on every entry, so a timeline renders without a lookup and still says what a since-deleted note was
  called. An event with no targets leaves nothing.

**An integration** writes through `POST /api/w/:id/timeline/external` (`record:write`, member or API key):
`{ target, kind: 'external.<name>', happenedAt, title, url?, amount?, source, idempotencyKey }`. The
entry's actor is `{ kind: 'external', id: source }` and `properties.recordedBy` keeps the caller. The API
knows no integration by name — "order paid in NewswireOS" is `external.order_paid` from source `newswire`,
and the adapter that sends it lives on the other side (doc 48 §8). **Idempotent** on
(workspace, source, key) by a unique index: a replay answers `201` with `created: false` and the entry
already written, so a retrying sender never doubles history. The same key in another workspace is another
workspace's entry.

## Reading — visibility follows the records

`GET /api/w/:id/timeline?target=<object>:<id>&kinds=&cursor=&limit=` (`record:read`), newest first,
`limit ≤ 100`. Who may read a timeline is who may read its record: `readableTargets` (P1-1b's one function)
under the caller's policies — a target outside their owner scope, or in another workspace, "has no timeline"
(`404`), never an empty page that confirms it exists. `kinds` is a comma-separated list of prefixes
(`linked-note`, `opportunity.`), matched with `startsWith`, so one spelling serves both the exact kind and
its family.

**A company's timeline merges its people's** (the deviation from PAR-015 that doc 50 §A draws): the query
takes the company's live people — under the caller's policies, so an own-scoped member sees only their own
people's part — and returns the company's entries and theirs in one order, each row tagged with the record
it is on (`target`). A person's and a deal's timeline are their own.

## Failure modes

| Failure                                           | Behaviour                                                      |
| ------------------------------------------------- | -------------------------------------------------------------- |
| Timeline write fails after the request committed  | Logged with the event; the request already answered. A defect. |
| Event with no targets for a linked thing          | Nothing written (there is no record to write on).              |
| External target unreadable / elsewhere / deleted  | `422` naming it (the write rule).                              |
| External replay (same workspace, source, key)     | `201`, `created: false`, the existing entry.                   |
| External kind not `external.<snake_case>`         | `400` (DTO).                                                   |
| Timeline of a record the caller cannot see        | `404`.                                                         |
| An `UPDATE`/`DELETE` on the table by the app role | Refused by Postgres (no grant).                                |

## What later packages add

- **P1-2:** publishes its stage-move events through the catalogue with `object: 'opportunity'` and the move
  in the event; the subscriber writes them unchanged. A move made by a rule carries actor `{ kind: 'rule' }`.
- **P1-5 (webhooks):** a second subscriber on the same bus; it does not read this table.
- **P2 (mail):** a message becomes an entry the same way — a catalogue event, one kind, one list (doc 50 §A).
- **The NewswireOS adapter (P5-1):** calls the external route; nothing here changes for it.
- **Not v1:** retention or compaction of history; an entry's own read route (`GET /timeline/:id`); timelines
  of notes, tasks and members; a workspace-wide feed (P1-4's views decide how that is filtered).
