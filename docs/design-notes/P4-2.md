# P4-2 — Enricher interface + free sources (FR-CRMS-15)

Doc 49 Phase 4. Depends on P1-1 (records and their one update path), P1-6 (the outbox) and P3-2's DNS port.
Journalist data is out of scope (D-252); nothing here reaches outreach (D-247: an enriched country is a fact on
the person, and the region policy reads it as it reads any country).

**Scope of this package:** the `Enricher` port with four free sources behind it, every answer kept with its
source and the time it was asked, the "better than what is there" rule (defined below, per field type), no answer
kept as no answer, background runs on the background pool, re-asking after a workspace-set age, _Enrich now_ and
an enrichment panel on the person and company records, and Settings → Enrichment. No paid API; nothing behind a
login; the verification (P3-5) and importer (P4-4) code is untouched.

## The sources

| Source (`source`) | Reads                                                                        | Facts (`field`)                                                                                                                                                                                                                                | Rank      |
| ----------------- | ---------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------- |
| `website`         | `https://<company domain>/`, up to 3 redirects and 512 kB, public hosts only | `name` (og:site_name 3 › application-name 2 › title's first segment 1), `logo_url` (og:image 2 › icon 1), `linkedin_url`, `x_url` (a profile link in the page, never a share link; 2), `domain` (the host it was served from, without www.; 2) | as listed |
| `dns`             | the domain's MX records through the sending pool's `DnsPort`                 | `mail_provider` (`google` / `microsoft` / `other`) — shown on the record, never written to a field                                                                                                                                             | 1         |
| `gravatar`        | `HEAD https://gravatar.com/avatar/<sha256(address)>?d=404`                   | `avatar_url`                                                                                                                                                                                                                                   | 1         |
| `email_domain`    | the addresses themselves, no network                                         | person `country` (a country-coded domain, the same inference the region policy uses); company `domain` (the domain most of its people write from, free mail excluded)                                                                          | 1         |

A source is asked only when it `applies` — a company with no domain has no site to visit, a person with no address
no Gravatar — and only when it is on in the workspace's settings. A source that throws (the site down, DNS silent)
is kept as `failed` for each of its facts, with why; what it looked for and did not find is `no_answer`.

## "Better than what is there" (`isBetterAnswer`)

Per fact, the rule compares the answer against the field's current value and **who wrote it**: the field was
written by enrichment when the newest _applied_ answer for it still equals the value (anything else — a member's
edit, an import — is a person's and is never replaced).

- An empty field takes any answer.
- A member's or an import's value is never replaced.
- An enrichment-written value gives way to an answer of **equal or higher rank** (a source that changed its mind
  wins over its own older answer); never to a lower-ranked one; the same value is never rewritten.
- Per type, within a rank: `url` — https beats http; `domain` — the apex beats its `www.` form; `text`,
  `country` — rank only; `enum` — never written (panel only).

The facts and what each maps to: `name → name`, `domain → domain`, `logo_url → logoUrl` (a new company
column), `linkedin_url → links.linkedin`, `x_url → links.x`, `avatar_url → avatarUrl`, `country → country`.

## Data model (migration `20261012070000_enrichment`)

- `companies.logo_url TEXT NULL` — the company's logo, on the API as `logoUrl` (a member may set it too).
- `enrichment_answers (id, workspace_id, object, record_id, field, source, status, value, rank, note, applied,
asked_at, created_at)`; `status ∈ answered | no_answer | failed`; `object ∈ person | company` (checked); `value`
  exactly when answered and never empty (checked); `applied` only when answered (checked). Indexed by
  `(workspace, object, record, asked_at desc)` for the panel and `(workspace, asked_at)` for the sweep.
- `enrichment_settings (workspace_id, reask_after_days, disabled_sources, updated_by_member_id, updated_at)`: an
  override; no row means every source on and 90 days. Stored as the sources turned _off_, so a source added
  later is on everywhere without a migration.

Both tables: RLS `workspace_isolation`, `FORCE`, app-role grants without `DELETE`.

## Running

- **Queue:** `enrichment`, one job per record (`<object>.<id>`); a second ask while one waits is the same job,
  a forced ask replaces a waiting unforced one. `ENRICHMENT_WORKER` runs the jobs, two at a time, with the
  hourly sweep on `enrichment-maintenance`.
- **Who queues:** _Enrich now_ (forced); the outbox consumer on `person.created/restored`,
  `company.created/restored`, `person.updated` (emails, company), `company.updated` (domain) — not forced, so a
  source asked within the age is not asked again; the sweep (not forced).
- **A run** (`EnrichmentRunner.enrich`): the subject (the company's name, domain, logo, links and its people's
  addresses; the person's address and country), the settings, the last ask per source → the due sources, asked
  two at a time with no transaction open → one transaction: every answer kept, the better ones written through
  `updateIn` (one `updated` event per run), those answers marked applied.

## API

- `GET /enrichment/settings` (`record:read`), `PUT /enrichment/settings` `{ reaskAfterDays, sources }`
  (`workspace:admin`).
- `GET /enrichment/:object/:recordId` (`record:read`) → `{ object, recordId, lastAskedAt, pending, answers[] }`;
  `POST` the same path (`record:write`) → `202`, the history with `pending: true`. A record the caller cannot
  see is `404`.

## Screens

- **The record** (person and company): an _Enrichment_ rail card — the newest answer per fact and source with
  its value (a link for a URL), source and time, _Applied_ where it was written, _No answer_ and _Failed_ said
  plainly — and _Enrich now_ (`record:write`), which polls while the run is queued and reads the record again
  when it settles. The header shows the person's picture or the company's logo when one is known.
- **Settings → Enrichment**: each source on or off with what it reads, and _Ask again after_ (days).
- Rail cards are named regions now (`aria-labelledby`), so a screen reader lands on "Enrichment" as it lands on
  "People".
