# P0-14 — Sign-up closed by default; platform admins create workspaces

**Package:** doc 49 §5, Phase 0 (added 2026-10-11). **Loop step 2 (design).** Closes #91.

Staging went public with open sign-up: anyone could create an account and a workspace. This package
makes the server take no sign-ups unless its operator says otherwise. Workspaces are created by
platform admins, who invite each owner.

## Sign-up modes

`SIGNUP_MODE` is read once at boot. It defaults to `closed`, and any value outside the three below
stops the API from booting (`env.ts`, unit spec `env.spec.ts`).

| Mode     | `POST /api/auth/signup`                                                                                    | `POST /api/workspaces` | Member invitations |
| -------- | ---------------------------------------------------------------------------------------------------------- | ---------------------- | ------------------ |
| `closed` | `403 signup.closed`                                                                                        | platform admins only   | work               |
| `invite` | needs `inviteToken`: a platform sign-up invitation for that address, else `403 signup.invitation_required` | platform admins only   | work               |
| `open`   | anyone (unchanged); a presented `inviteToken` must still be valid                                          | anyone signed in       | work               |

- **The codes are in the catalogue.** `signup.closed`, `signup.invitation_required` and
  `platform.forbidden` are in `ERROR_CODES` (`packages/shared/src/errors.ts`), so they appear in
  `openapi.json`. A client branches on the code, never on the message.
- **The sign-in page learns the mode from `GET /api/auth/providers`.** It now returns
  `{ providers, signup }` (an additive change). The page offers "Create a workspace" only when the
  mode is `open`. Otherwise it says "Ask your administrator for an invitation."
- **Joining by invitation works in every mode.** `/sign-up?invite=<token>` is the member-invitation
  accept page: sign up from the invitation, or join with the signed-in account. It is how anyone
  gets in when sign-up is closed.
- **Sign-up invitations live on their own page.** `/sign-up?signup=<token>` opens the sign-up form
  that carries a platform sign-up invitation (`invite` mode).
- **Both links are built in one place.** `invitationUrl()` in `packages/shared/src/platform.ts`
  builds them, from `WEB_URL` on the API and from the window's origin on the web (the Invites
  settings page uses it too).

## Platform admins

`PLATFORM_ADMIN_EMAILS` is an optional comma list. It is lower-cased and de-duplicated, and boot
fails on an entry that is not an email address.

- **Status is decided on every request.** A caller is a platform admin when they are a **person**
  (session, not an API key) whose `users.email` is in the list **and** whose `email_verified_at` is
  set (`PlatformAccess`).
- **Nothing is stored or cached.** Removing an address takes effect on the next request the process
  serves with the new list. The cross-tenant spec swaps the list between two requests to prove it.
- **Revocation needs a restart (accepted).** The list is an environment variable, read at boot. On a
  server, removing an address takes effect from the first request after the api restarts with the
  new value. There is no runtime switch, and none is planned. The operator ruled this acceptable for
  P0-14.
- **No admins is a valid, safe state.** With the list unset, no one is a platform admin. In
  `closed` mode, nobody can then create a workspace through the API, and member invitations still
  work.

### What "verified" means today

`email_verified_at` is set in exactly these places:

1. Signing up from a workspace invitation, or from a platform sign-up invitation. Holding the token
   proves the holder read that mailbox.
2. Signing in through an OIDC provider that marks the email verified (P0-3).
3. The operator command `node dist/cli/platform-bootstrap-admin.js <email>` (#101; it replaced
   `platform-verify-email`), run on the server inside the api container.
    - It uses the owner connection.
    - It **refuses any address not in `PLATFORM_ADMIN_EMAILS`**, so it cannot verify anyone else.
    - It records a `platform.admin_email_verified` audit row with actor `null`.
    - It is the bootstrap for an admin whose account was made by password sign-up (staging's
      existing account was) — and, with no account at all, it creates one and prints a single-use
      set-password link (#93's reset link; audited `platform.admin_bootstrapped`).

A password account created by plain sign-up is **unverified**. The email-verification card will add
a mailed verification link. That link replaces (3) and makes "verified" mean the same for every
account.

Accepting a member invitation while signed in keeps P0-3's rule: the account must be the invited
address **and** that address must be verified. An unverified existing account is told to verify
first. This package does not weaken that rule.

## Provider sign-in outside open mode

P0-3's `signInWithIdentity` created a user for any verified provider address. Left as it was, a
Google or OIDC sign-in would be a back door to sign-up on a closed server. Now, when the mode is
not `open`, a **first-time** provider identity whose address has no account gets one only when the
normalised address meets one of these:

- it is in `PLATFORM_ADMIN_EMAILS`;
- a pending, unexpired workspace invitation names it;
- a pending, unexpired platform sign-up invitation names it.

Otherwise the service throws the same `SignupClosed` error the password path uses. Nothing is
written: no user, no external identity, no session. The callback is a browser navigation, so the
controller turns that one error into a redirect to `/sign-in?error=signup.closed`. The sign-in page
shows a generic "this server does not take new accounts" message there.

An existing account signs in as before, whatever the mode. Open mode is unchanged. All of this is
covered in `platform.spec.ts` ("provider sign-in outside open mode"), against a stand-in provider.

This also gives a fresh server one way to make its first platform admin: list the address and sign
in with Google or OIDC. A password-only first admin needs `platform-bootstrap-admin` (#101), which
lands after #93 because it reuses #93's set-password token.

## Routes (`apps/api/src/platform`)

All of these require a signed-in person. An API key always gets `403`.

| Route                                              | Who                     | Does                                                                                                                                                        |
| -------------------------------------------------- | ----------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `GET /api/platform/access`                         | any signed-in caller    | `{ platformAdmin, signupMode }`: the web app shows the platform page and the create buttons from this                                                       |
| `GET /api/platform/workspaces`                     | platform admin          | every workspace: name, slug, created, member count, pending admin-role invitations (the owner's, until they join); newest first, ≤ 500                      |
| `POST /api/platform/workspaces {name, ownerEmail}` | platform admin          | workspace + system roles + pipeline, **no member**, and an admin-role invitation for `ownerEmail` → `{ workspace, invite: {email, url, token, expiresAt} }` |
| `POST /api/platform/signup-invites {email}`        | platform admin          | a platform sign-up invitation (`invite` mode only; `409` otherwise) → `{ email, url, token, expiresAt }`                                                    |
| `GET /api/auth/invites/:token` (public)            | whoever holds the token | `{ email, workspaceName, expiresAt }` for the accept page; `404` unknown, `410` spent or expired, the same answers accepting gives                          |

`PlatformAdminGuard` is the gate on each admin route. The routes are not tenant routes, so the
workspace and capability guards pass them by. The same `PlatformAccess` check gates
`POST /api/workspaces` outside `open` mode.

### The owner's way in

- **Creating the workspace.** The workspace is created by `AuthService.createWorkspaceForOwner`.
  AuthService stays the one writer of `workspaces` and of the rows that make one usable. P0-3's
  `createWorkspaceWithAdmin` is split into a shell (workspace, roles, pipeline) plus the first seat;
  the platform path uses only the shell.
- **Who sent the invitation.** A platform invitation has no inviting member, so
  `workspace_invites.invited_by_id` is now nullable. A new `invited_by_user_id` column names the
  platform user instead. A CHECK constraint (`num_nonnulls(...) = 1`) requires exactly one of the
  two.
- **An owner who already has an account** opens the link signed in and joins. Their address must be
  verified (above).
- **A new owner** creates their account from the link, which works in every mode. They become admin
  of that workspace only. The cross-tenant spec asserts:
    - their `/me/workspaces` is that one workspace;
    - another workspace answers `403`;
    - they are not a platform admin.

## Audit

Every platform action appends a row to `platform_audit` (who, what, when, and a subject of ids and
addresses, **never a token**). The row is written in the same owner-client transaction as the change
it records. After commit, the matching event is emitted on the bus:

- `platform.workspace_created`
- `platform.signup_invite_created`
- `platform.admin_email_verified`

These types are `PLATFORM_EVENT_TYPES`, deliberately outside `DOMAIN_EVENT_TYPES`. The timeline and
webhook subscribers filter on the domain catalogue, so no workspace's timeline or webhooks ever sees
an operator action.

`platform_audit` is append-only:

- A trigger refuses UPDATE, DELETE and TRUNCATE for every role, the owner included.
- The app role has no grant on it, and none on `platform_signup_invites` either.
- The schema-invariant test's rule ("out of the app role's reach") covers both tables.

## Owner-client readers and writers added

This extends the P0-3 table:

| Where                                                   | Why                                                                                     |
| ------------------------------------------------------- | --------------------------------------------------------------------------------------- |
| `AuthService.createWorkspaceForOwner`                   | creates the workspace before any tenant scope exists (as `signup` does)                 |
| `AuthService.signup` (spending a sign-up invitation)    | global table, no tenant                                                                 |
| `AuthService.previewInvite`                             | looks the invitation up by token hash across workspaces, as `acceptInvite` already does |
| `PlatformAccess.isPlatformAdmin`                        | one `users` row by primary key, as `AuthService.me`                                     |
| `PlatformService.listWorkspaces`                        | reads across workspaces by nature; reachable only behind `PlatformAdminGuard`           |
| `PlatformService.createSignupInvite`                    | global table + audit                                                                    |
| `bootstrapPlatformAdmin` (CLI only, not a request path) | the operator bootstrap above                                                            |

## Web

- **Sign-in** hides "Create a workspace" unless the mode is `open` (`SignIn.spec.tsx`).
- **`/sign-up`**
    - With no token, the form shows only in `open` mode. Otherwise the page says "Sign-ups are closed"
      and offers a sign-in action.
    - `?signup=` adds the token to the form.
    - `?invite=` is the accept page. It never calls `/api/me` without a session cookie pair, because a
      401 would send the visitor to sign-in, away from the invitation (`SignUp.spec.tsx`).
- **`/workspaces`** offers "New workspace" only to platform admins, or to anyone when sign-up is
  open. Platform admins also get a link to the platform page, even with one workspace.
- **`/platform/workspaces`** (its own lazy chunk, behind `RequireAuth`) has:
    - the list, as phone cards through `DataTableChrome`'s data mode;
    - "New workspace" (name and owner email), with the invitation link shown once through `CopyValue`;
    - "Invite to sign up" in `invite` mode.

    A non-admin sees the 403 state.

- **Route gate.** It visits `platformWorkspaces` and a new `accept-invite` state, with typed
  fixtures for `/api/auth/providers` (mode `closed`), `/api/auth/invites/:token`,
  `/api/platform/access` and `/api/platform/workspaces`.

## Test environments

Nearly every cross-tenant spec makes its tenants through `/api/auth/signup`, so the cross-tenant
config sets `SIGNUP_MODE=open`. `platform.spec.ts` replaces the environment with one mutable object
and switches modes between requests. `.env.example` sets `open` for local development, with a
comment.

## Deploying

A deployment that sets nothing is `closed` with no platform admins. Nobody can sign up or create a
workspace, and existing members keep working. To let someone create workspaces:

1. Set `PLATFORM_ADMIN_EMAILS=<address>` in the runtime env and restart the api.
2. Have that person sign in through a verifying provider. A listed address gets an account even in
   `closed` mode. **Or**, for an account that already exists, run
   `node dist/cli/platform-bootstrap-admin.js <address>` in the api container; on a fresh server it
   creates the account and prints a single-use set-password link (#101).
3. To take an address off the list, change the variable and restart the api. Access ends from the
   first request after the restart.
