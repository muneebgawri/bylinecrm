# P2-3b — A record's sends from the server (#104)

## Problem

`mail_outbound` keeps every send's outcome, including failures with their reason, but no route
listed a record's sends. The record page (P2-UI-1) therefore showed a failed send only in the tab
that made it — gone after a reload — and found scheduled sends by reading the member's whole
`/mail/scheduled` list a page at a time and filtering it to the record on the client.

## The route

`GET /mail/messages?target=<type>:<uuid>&status=<s1,s2…>&limit=&cursor=` → `MailRecordSendsPage`
(`{ items: MailOutbound[], nextCursor }`).

- **Which sends a record is about** — the same rule the timeline and the thread list use:
  a person's (`person_id`), a deal's (the sends written from it, `deal_id`), a company's (its live
  people's, as the company timeline merges them). A company with no live people lists nothing.
- **Statuses** are required and explicit (`failed,scheduled` for a record page); any of
  `MAIL_OUTBOUND_STATUSES`, validated, `400` naming `status` otherwise.
- **Order**: newest first (`created_at desc, id desc`), cursor pagination (`paginate`), 25 by
  default, at most 100.
- `@Requires('email:send')`, like every other `mail/*` send route.

## Who sees what

Two rules, both already the API's, applied together — no new visibility rule:

1. **The record must be one the caller can read.** `readableTargets` runs under RLS and the role's
   restrictive `owner_scope` policy, so a record outside an own-scoped role's reach — or another
   workspace's — is `404 not_found`, never a hint that it exists. This is the thread list's rule.
2. **A send is its sender's, or an admin's, to see** — the rule `GET /mail/messages/:id`,
   reschedule and cancel already enforce. A member who can read a person does not see a colleague's
   failed or scheduled sends to that person (they could not open, move or cancel them either).

Widening rule 2 to "anyone who can read the record" would make this list show sends whose detail
route answers `404` to the same caller; if that is wanted, it is one decision for all the send
routes together, not a divergence in one of them.

## The web

- `useRecordSends(workspaceId, target)` reads the record's `failed,scheduled` sends (infinite query,
  key `mailRecordSends(ws, target)`), replacing `useScheduledMail` and the client-side filter. The
  record's pending sends are this tab's sends (polled as before) plus the server's, de-duplicated by
  id; each is still read back until final.
- Company pages now list sends too (they had none before: the old list could not be filtered by
  company).
- "Show more sends" follows the API's cursor.
- A send, reschedule or cancel invalidates every record's list (`mailRecordSendsAll`).
- The client for `/mail/scheduled` is removed from the web (nothing else read it); the API route
  stays for API clients.

## Retry after a reload

Retry sends again exactly what this tab wrote (`SessionSend.input`). The API keeps a send's outcome
and its built MIME, not the written subject/body/template input, so a failure read from the server
shows its reason **without** Retry. A server-side "retry this send" would be new semantics (re-run
the checks against today's person and mailbox, a new send id or the same one, what the timeline
shows) — out of scope here; raised as an open question.

## Tests

- `test/cross-tenant/mail-record-sends.spec.ts` (#104): person listing newest first with a
  failure's typed reason; status filter; cursor to the end; company and deal targets; another
  record's sends excluded; sender/admin rule; own-scope record → `404`; another workspace → `404`;
  `400` for missing target/status and an unknown status.
- `apps/web/src/routes/w/mail/sends.spec.tsx`: the request carries the record's target and
  `failed,scheduled`; a failed send shows after a reload with its reason and no Retry; a company's
  sends; "Show more sends" with the cursor; scheduled sends (cancel, reschedule) read from the list.
