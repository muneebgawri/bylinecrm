# P4-4 — The Twenty importer (doc 48 §11) and its screen (P4-UI-2)

Doc 49 Phase 4, build plan P4-4. Depends on records (P1-1a/b), pipelines (P1-2), custom fields
(P1-1a), the outbox (P1-6), outreach exclusions (P3-3, FR-CRMS-10), views (P1-4) and templates
(P2-4) — it writes through every one of them and adds no second way to write a record.

**What this package is:** an importer _in the product_, not a script. An admin connects a Twenty
workspace (its URL and an API key), sees what it holds beside what is mapped here, starts a run,
and follows it object by object. The run reads Twenty's public REST API, maps every record by its
Twenty id — so a run can be repeated and only writes what changed — and reports, per object, what
Twenty held and what the run created, updated, left alone, merged, skipped or could not write.
The real run against Pinion's workspace happens later, with a key provided out of band; everything
here was built and proven against a fake of Twenty's answers (`test/support/fake-twenty.ts`).

## What is read, and where it lands

The objects, in the order they are read (a later one refers to earlier ones through the links):

| Twenty object                         | Lands as                                                                                                                                                                                                                                                                                                                                                                                                                                    |
| ------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `workspaceMembers` (owners)           | The member here with the same sign-in address (`users.email`). Without the accounts option an owner nobody matches is counted _skipped_ and named in the report; with it (#184, below) they get an account and a seat on the same run.                                                                                                                                                                                                      |
| `companies`                           | Companies: name, domain (the host of `domainName`, without `www.`), employees, ICP, ARR (micros → minor units of its currency), address, links, owner. Twenty's own fields (`biginrecordid`, `stripeltv`, …) become custom fields on the company.                                                                                                                                                                                           |
| `people`                              | People: name, emails, phones (a number keeps its country code, or the one its calling code implies; without either it is left out), job title, city, links, company and owner through the links, `source` = `twenty:<inboundLeadSource>` (FR-CRMS-11), the rest as custom fields. A Twenty avatar URL carries a signed token and is never copied.                                                                                           |
| `opportunities`                       | Deals in the default pipeline. The stage is matched by name (`CLOSED_LOST` → "Closed lost"); a stage the pipeline lacks is added at its end with the kind its name implies (won for `WON`/`CUSTOMER`, lost for `*LOST*`, else open). A closed deal is created in the first open stage and then closed through `StageMoveService.move` — so it has its history (`import`, then `close`) and its `deal.won`/`deal.lost` event like any other. |
| `notes` / `noteTargets`               | Notes on every target the note had that exists here (person, company, deal); the body (markdown) as rich text; the Twenty author as the note's author when they are a member. A note whose targets are all on objects with no home here (a lead lookup) is _skipped_, and the report says so.                                                                                                                                               |
| `tasks` / `taskTargets`               | Tasks, likewise; `TODO`/`IN_PROGRESS`/`DONE` → the task statuses, `DONE` completed now; the assignee through the member link.                                                                                                                                                                                                                                                                                                               |
| `leadLookups` (Lead Engine)           | **FR-CRMS-10 exclusions.** An _Assigned_ lookup excludes its address as `account_managed` with the account manager's name, `source` `twenty`, `externalRef` the lookup's id — through `ExclusionsService.addIn`, the same write an admin's route makes. One that becomes _Unassigned_ ends the exclusion (`removedNote` "Unassigned in Twenty"); the row stays.                                                                             |
| `leadViews` (Lead Engine)             | The person Twenty links (`personId`), else whoever has the lead's address, else a new person (`source` `twenty:lead`): the lead's fields land on them as custom fields under `lead_` (`lead_id`, `lead_assigned_am`, `lead_lifetime_value` + `_currency`, `lead_opportunity_stage`, …). Like a journalist, a lead only adds to a person that exists.                                                                                        |
| `messageLists` / `messageListMembers` | A `lists` multiselect custom field on people whose options are the list names, each member's `lists` carrying the lists they are on, and one **shared view** per list ("List: _name_", filter `custom.lists contains name`) — what a member would build by hand to mail a list.                                                                                                                                                             |
| `messageCampaigns`                    | Outreach templates (name, subject, body as rich text). A campaign's send counts stay in Twenty: a template here has no sends of its own.                                                                                                                                                                                                                                                                                                    |

**Not read, by ruling (D-252, 2026-10-12):** `journalists` — journalist outreach (a client's press release
to journalists) is a different activity from customer outreach and is deferred; whether it becomes a BylineCRM
module, runs on Herald, or lives in NewswireOS/Pressboard is decided later, and Twenty keeps that data
meanwhile; `leadLookupRequests` (Lead Engine's audit log of who looked up what, not CRM history), `inboundFailedLeads` /
`inboundTestLeads` (Lead Engine's intake diagnostics), `messages`, `messageThreads`, `messageParticipants`
(mail comes through each mailbox's own sync, P2-2), `blocklists` (each member's own), `attachments`
(bytes behind Twenty's file tokens; owed with a later package), `timelineActivities` (the timeline here is
written by the outbox from what the import does), `calendar*`, `callRecordings`, `dashboards`,
`recordShares`.

**Twenty's own fields on standard objects (doc 48 §11, the ledger's "Pinion workspace objects").**
A field the mapper did not read as a standard one becomes a custom field on the same object, through
`CustomFieldsService` (so the cache every list and filter reads is kept right). Its key is the field's
name in snake case (`prLink` → `pr_link`), its label the words of that; the type is read from the value
— an instant, a date, a select option (`GOOGLE_ADS`, `NEW`), a URL, text; a number; a boolean — and
Twenty's composites are flattened: a currency to a number (major units) and `<key>_currency`, a link to a
URL, an email, a phone, a name. A select grows the options a page brings. An empty answer (`""`, `null`)
clears the field; a value that disagrees with the definition's type is carried as that type when it can be
(a number as text) and left out when it cannot. Relations are never values.

## Idempotence: the links

`twenty_import_links (workspace_id, object, external_id) → (local_type, local_id, label)` is what makes a
run repeatable: a Twenty record already linked is **updated where it differs and otherwise left alone**
(`updateIn`'s "a no-op is no event" rule — P1-4a); one not yet linked that matches an existing record by its
unique key — a person's primary address, a company's domain — is **merged** into it (restoring a trashed
one first, PAR-002) rather than refused as a duplicate; one with no match is **created**. Two Twenty records
may map to one row (a lead and a person with one address). A linked record an admin trashed here is
not resurrected: the run counts it _skipped_. A run writes as `actor: { kind: 'import', id: <run id> }`
(PAR-003's `import` actor, through `WorkspaceRunContext.actor`), so every imported record says so and every
event the outbox delivers — timeline, webhooks, stage rules — names the run.

The record diff was made key-order-insensitive on the way (`records/diff.ts`): `jsonb` stores an
object's keys in its own order, so `{ linkedin, x }` read back as `{ x, linkedin }` compared unequal and a
repeated run re-announced every person. The fix lands in the one helper the routes use too, so a `PATCH`
that changes nothing is a no-op there as well.

## Accounts for Twenty members who are not here (#184, P4-4e)

Every Twenty member (the account managers) must exist here so imported records are attributed to them; they
connect Gmail when they first sign in. Pinion's first production run matched 1 of 33 owners and left the rest
unowned, so the importer makes the accounts itself — one mechanism, no special path:

- **The option.** `POST runs { mode, createMembers: { roleId } }` — off unless chosen; the screen shows the
  option with a role picker over the workspace's roles (`member` by default; the workspace may first create an
  _Account manager_ role with outreach permissions) and, after _Check connection_, how many accounts it would
  create (`preview.accountsToCreate`: Twenty members with a usable address and no seat here, held or left).
  The role is looked up inside the workspace (another workspace's is a `422` at `roleId`) and remembered on the
  run (`create_members_role_id`); `accounts_created` counts what the run made.
- **What is made, and how.** Before the member pass's page transaction, each unmatched member with a usable
  address (#180's one normaliser) goes through `AuthService.provisionMember`: the user if absent — **no
  password, unverified**, display name from Twenty's — and the seat through `takeSeat`, the one seat-making
  helper `acceptInvite` uses too (a seat they left comes back as the same seat, #147), with the chosen role and
  `source = 'twenty-import'` (the seat's provenance; `signup` and `invite` are the other two). The users table is
  the owner's, so this happens outside the page's tenant transaction and before it; the pass then matches the
  member by address and links them like any other, so `accountOwnerId`, `personOwnerId`, `ownerId`, note
  authors and task assignees resolve on the same run. **No mail is sent.**
- **First sign-in.** A Google/OIDC sign-in with that address lands on the existing account (the closed-mode rule
  admits an existing user; the sign-in verifies the address) and `/me/workspaces` lists the workspace — proven in
  the cross-tenant suite with sign-up closed. A password comes through the normal invitation: an admin's _Send
  invitation_ on the member's row (Members shows them as _Not signed in yet_: no password, no verified address)
  creates the usual invitation; accepting it with a password on an account that has no credential sets that
  password and keeps the seat (`acceptInvite`'s one new branch) — no second flow.
- **Re-runs.** Idempotent: a member with a seat is matched, never duplicated; records already imported get their
  owner on the next run, updated where it differs (the links).
- **Deactivated Twenty members** are soft-deleted there and no longer listed, but records can still be theirs.
  With the option on, a run reads them once (`filter=deletedAt[is]:NOT_NULL`, PAR-066) and, when a page refers
  to one not mapped yet, makes the account with the seat already left (`left_at` = Twenty's `deletedAt`): history
  is attributed, access there is none. One no record names is never made.

## Running

- **Where:** a BullMQ job per run (`twenty-import` queue, job id = run id, one at a time per process) in a
  worker process (`TWENTY_IMPORT_WORKER`, `1` by default like the other workers) — the mail-sync
  precedent for a long import. The run row (`twenty_import_runs`) is the truth: `phase` and a cursor per
  object say where it is; `report` what it did. One queued or running run per workspace (a partial unique
  index; a second start is a `409`).
- **A page at a time, never across the network in a transaction (#86):** a page of 60 (Twenty's ceiling) is
  read outside any transaction, in id order (so a resumed run sees every record once, whatever Twenty does to
  positions meanwhile); its relations' links are loaded; the records are mapped (pure); the custom-field
  definitions they need are put in place; then every record is written **in one transaction with the run's
  progress** — each record under a savepoint, so one the services refuse (a validation, a reference, a
  template variable Twenty's campaign uses and ours does not) costs only itself and is named in the report.
  A page that commits is never done again; a process that dies resumes from the page after it.
- **A bad record is that record's failure, never the run's (#168):** a mapper that throws, or a write the
  client rejects (a timestamp that does not parse, a value of the wrong shape) is counted under **Failed**
  with the reason and the Twenty id, and the page goes on. Only the database being unavailable
  (`databaseUnavailable`: the connection, the pool, the transaction, the engine) or Twenty failing is the
  run's to retry. The first production run stopped after 30,357 companies on one link that did not parse;
  the tolerant readers (P4-4b) fixed that link, this rule fixes the class.
- **Retries:** a `429` or `5xx` from Twenty is retried with a doubling wait; a refused key or an object this
  Twenty has none of is final. A job that throws (the database, Redis) is retried by the queue from the
  cursor; the third failure marks the run failed with the last error. A run left queued or running by a
  dead process is given its job again at the next start.
- **Modes:** `full` reads everything; `changes` asks Twenty for what it updated since the last successful
  run's start (`filter=updatedAt[gte]:…`), and reads everything when there was none; `reconcile` (#156,
  ruling 4) writes no record: it reads every id Twenty still returns, marks their links `checked_at` page by
  page (in the run's own transaction, so a resumed pass loses nothing), and once an object's last page is read
  flags the links no page named — never checked, or checked before this pass started — with `missing_since`.
  The report says how many per object (`missingInSource`); `GET missing` lists them with the local record's
  name for review. Nothing is deleted on its own; any run that writes a link (sees the record) clears its flag.
- **Cancel:** a request flag the runner reads after every page; the run ends `cancelled` where it is, and
  what it wrote stays mapped. The next run carries on.
- **Counts:** per object, `remote` (Twenty's total at the start of the pass), `before`/`after` (records of
  the object mapped here when the pass started and ended), and the outcomes, which sum to `read`.

## Automatic sync (#185, P4-4f)

The team keeps working in Twenty for a while after the import; BylineCRM stays current on its own. Built on
the importer, not beside it: a scheduled run is a `changes` run with `scheduled = true`, started by the same
`queueRun` a person's start goes through, driven by the same worker, counted in the same run list.

- **Setting:** `twenty_import_settings.sync_interval ∈ off | 15m | hourly | daily` (off by default; `PUT sync`),
  a setting on the connection — there is nothing to sync without one. Turning it on is a fresh start: the
  failure streak and a cutover are cleared.
- **Schedule:** one BullMQ job scheduler per workspace on the `twenty-import` queue, keyed `sync:<workspace
id>`, upserted at the interval when the setting changes (after the row commits) and removed when it is off.
  Its job is a tick, not a run: `TwentySyncService.tick` starts a run only when one is due. The settings row
  is the truth; a worker's start puts the schedulers in line with it (one per syncing workspace, none for any
  other), so a lost Redis loses nothing. BullMQ runs an `every` scheduler's first job at once: syncing starts
  the moment it is turned on, then every interval.
- **Never two runs of one workspace:** the tick starts nothing while a run is queued or running — the partial
  unique index the importer already has is the lock — and a person's start meanwhile is the usual `409`. A
  scheduler holds at most one pending job, so ticks never stack either.
- **Cursor:** each run reads from the last _successful_ run's start (`since`), as `changes` always has; a run
  that fails moves nothing, so the next run resumes from the same place (and the links make re-reading a
  page idempotent).
- **Failures:** a scheduled run that ends `failed` counts on the settings row (`sync_failures`,
  `sync_last_error`); a success resets both. The tick backs off by the count — the interval doubled per
  failure in a row, at most a day — and keeps trying. The third failure in a row records one mail per admin
  (`twenty_sync_failing`, through the mail outbox in the run's own transaction; the admins are the members
  whose role holds `workspace:admin`, resolved as the guard resolves it) and no more until a success starts a
  new streak. The screen shows the streak and the last error on the sync card; the failed runs themselves are
  in the run list, marked _Automatic_.
- **Precedence while syncing:** Twenty is the source for the fields the importer maps. A field edited in
  BylineCRM _after Twenty last touched the record_ (Twenty's `updatedAt`) keeps BylineCRM's value: the run
  asks the timeline which fields anyone but the import changed on the record since then (`fieldsEditedAfter`:
  the record's own `updated` entries, `diff` keys, any actor but `import`; a deal's stage is `stageId`, so a
  move here is kept too) and drops them from Twenty's patch. The record counts as a **conflict** in the report
  (`conflicts`, with the fields per record in `kept`, capped like `errors`) beside its outcome — it is still
  `updated` or `unchanged` — never silently. Once Twenty updates the record again, later than the edit here,
  Twenty's value applies: last writer wins, at field level on this side and record level on Twenty's, which is
  the finest Twenty's API allows. A record Twenty gives no `updatedAt` for keeps every local edit. The rule
  holds for people, companies and deals, the records with a timeline; notes, tasks, templates and views have
  no field history and take Twenty's version, as before. It applies in `full` runs too — it is the importer's
  rule, not the schedule's — and a lead view (a sidecar that only fills what is empty) is outside it.
- **Deletions** remain report-only (#156): the schedule runs `changes`, never `reconcile`.
- **Accounts (#184) on a scheduled run:** the accounts option is the workspace's saved choice —
  `twenty_import_settings.create_members_role_id`, set (or cleared) by every start a person makes outside a
  reconcile pass, offered back on the screen next time — and a scheduled run carries it exactly as a start
  would: a Twenty member who is not here gets an account and a seat with that role, and nothing is mailed
  (owner ruling, 2026-10-14). With no choice saved, the run skips them as before.
- **Cutover:** _Stop syncing (cutover)_ (`POST sync/cutover`) sets the interval off, removes the scheduler and
  records `cutover_at`, shown on the card. Syncing again clears it: the importer stays reusable (D-252).

## Data model (migration `20261012050000_twenty_import`)

- `twenty_import_settings (workspace_id PK, base_url, api_key_ciphertext, api_key_last4, configured_by_id,
updated_at)` — the key sealed with `SecretBox` (P1-5's one box), shown by its last four characters only,
  deleted when the connection is removed. The base URL is held to the webhook target rule (`url-guard`: a
  public host, never the API's own network; the development flag that admits a local receiver admits a local
  Twenty, which is what the cross-tenant suite runs).
- `twenty_import_runs (id, workspace_id, status, mode, since, phase, cursor, report, error,
cancel_requested, scheduled, started_by_id, create_members_role_id, accounts_created, queued_at, started_at,
finished_at, updated_at)`; `status ∈ queued | running | succeeded | failed | cancelled`; the state is checked by
  the database; `scheduled` (#185) says the schedule started it.
  `workspace_members.source` (#184, migration `20261014090000_twenty_import_members`): `signup`, `invite` or
  `twenty-import`; null for seats from before it.
- #185 (migration `20261014120000_twenty_scheduled_sync`): on the settings row, `sync_interval` (checked:
  `off | 15m | hourly | daily`), `sync_failures`, `sync_last_error`, `cutover_at`; on a run, `scheduled`.
  Migration `20261014130000_twenty_sync_members`: `create_members_role_id` on the settings row (FK roles, set
  null), the saved accounts choice.
- `twenty_import_links` as above; `label` names a local thing with no row of its own (a list's name).

All three: RLS `workspace_isolation`, `FORCE`, app-role grants; `DELETE` only on the settings row (runs are
history, links are what makes a run repeatable). The cross-tenant suite proves one workspace sees none of
another's connection, runs, links or imported records, and that a run id from elsewhere is a `404`.

## API (`/api/w/:id/import/twenty`, all `workspace:admin`)

`GET` (overview: settings, latest run, what is mapped per object) · `PUT/DELETE settings` ·
`POST preview` (Twenty's count per object, read now; a refused key is a `422` at `apiKey`) ·
`POST runs` (`{ mode, createMembers? }` → `202`, the queued run; `409` while one is queued or running; a role not
this workspace's is a `422` at `roleId`) · `GET runs` ·
`GET runs/:id` · `POST runs/:id/cancel` · `GET missing` (`?object=&limit=&cursor=`: what a reconcile pass
flagged, oldest flag first, with the record's name — #156) · `PUT sync` (`{ interval }` → the sync: interval,
`nextRunAt`, `failures`, `lastError`, `cutoverAt`; also on the overview as `sync` — #185) · `POST sync/cutover`.

## The screen (P4-UI-2): Settings → Import from Twenty

Lazy route under settings (its own chunk; the initial bundle is unchanged at 177.65 kB), an admin's
section; a member who is not one is told whose it is. The connection card (URL, write-only key, _Check
connection_ → the counts table, and how many accounts the option would create), the import card (_Everything_ /
_Changes since last run_ / _Reconcile with Twenty_, the accounts option with its role picker (#184), _Start
import_; while a run goes: its status, the object it is reading, _Cancel import_, and the per-object report read
every 1–5 s until it is over; a finished run says how many accounts it created) and the previous runs. Between
them the _Automatic sync_ card (#185): the interval (_Off_ / _Every 15 minutes_ / _Hourly_ / _Daily_), the next
sync, the failure streak with its last error, and _Stop syncing (cutover)_ behind a confirmation; an automatic
run is listed as such, and the report has a _Conflicts_ column with the kept fields named under it. Design tokens only; the counts tables are
`DataTableChrome`, so a phone sees cards (FR-CRMS-UI-12).

## Twenty's API, as used (PAR-066)

`GET <base>/rest/<objects>` with `Authorization: Bearer <key>`; `limit` (≤ 60), `depth` (`0` bare, `1` with
one-to-many relations — notes and tasks come with their targets), `order_by=id[AscNullsFirst]`,
`starting_after=<cursor>`, `filter=updatedAt[gte]:"<iso>"`; the answer `{ data: { <objects>: [...] },
pageInfo: { hasNextPage, endCursor }, totalCount }`. Composites as the instance reports them (name, emails,
phones, links, currency, address). The adapter (`twenty.http.ts`) is the only code that calls Twenty; the
fake answers the same grammar.

## Owner rulings (D-252, 2026-10-12)

1. **Lead views stay as `lead_*` custom fields on the person.** Revisited only if a person can have many
   lead views; if so, filed for after P4-3.
2. **Journalists are not imported.** Journalist outreach is a different activity from customer outreach and is
   deferred (module, Herald, or NewswireOS/Pressboard — decided later); Twenty keeps that data meanwhile.
3. **`leadLookupRequests` are not imported.** Lead Engine's audit log is not CRM history.
4. **No automatic deletion mirroring.** Done as #156: the `reconcile` run mode flags CRM records whose Twenty
   id is no longer returned as "missing in source", listed on the import screen for review — never deleted on
   its own.
