# P4-4 — The Twenty importer (doc 48 §11) and its screen (P4-UI-2)

Doc 49 Phase 4, build plan P4-4. Depends on records (P1-1a/b), pipelines (P1-2), custom fields
(P1-1a), the outbox (P1-6), outreach exclusions (P3-3, FR-CRMS-10), views (P1-4) and templates
(P2-4) — it writes through every one of them and adds no second way to write a record.

**What this package is:** an importer _in the product_, not a script. An admin connects a Twenty
workspace (its URL and an API key), sees what it holds beside what is mapped here, starts a run,
and follows it object by object. The run reads Twenty's public REST API, maps every record by its
Twenty id — so a run can be repeated and only writes what changed — and reports, per object, what
Twenty held and what the run created, updated, left alone, merged, skipped or could not write.
The real run against Pinion's workspace happens later, with a key provided out of band; everything
here was built and proven against a fake of Twenty's answers (`test/support/fake-twenty.ts`).

## What is read, and where it lands

The objects, in the order they are read (a later one refers to earlier ones through the links):

| Twenty object                          | Lands as                                                                                                                                                                                                                                                                                                                                                                                                                                    |
| -------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `workspaceMembers` (owners)            | The member here with the same sign-in address (`users.email`). No accounts are invented: an owner nobody matches is counted _skipped_ and named in the report, so an admin can invite them and run again.                                                                                                                                                                                                                                   |
| `companies`                            | Companies: name, domain (the host of `domainName`, without `www.`), employees, ICP, ARR (micros → minor units of its currency), address, links, owner. Twenty's own fields (`biginrecordid`, `stripeltv`, …) become custom fields on the company.                                                                                                                                                                                           |
| `people`                               | People: name, emails, phones (a number keeps its country code, or the one its calling code implies; without either it is left out), job title, city, links, company and owner through the links, `source` = `twenty:<inboundLeadSource>` (FR-CRMS-11), the rest as custom fields. A Twenty avatar URL carries a signed token and is never copied.                                                                                           |
| `journalists` (Pinion's custom object) | People, with `source` `twenty:journalist`; outlet, niche, story link, bylined flag, confirmations and the rest as custom fields on the person. One with a person's address is that person (merged), and only _adds_ to them — a journalist record never overwrites a person's own fields.                                                                                                                                                   |
| `opportunities`                        | Deals in the default pipeline. The stage is matched by name (`CLOSED_LOST` → "Closed lost"); a stage the pipeline lacks is added at its end with the kind its name implies (won for `WON`/`CUSTOMER`, lost for `*LOST*`, else open). A closed deal is created in the first open stage and then closed through `StageMoveService.move` — so it has its history (`import`, then `close`) and its `deal.won`/`deal.lost` event like any other. |
| `notes` / `noteTargets`                | Notes on every target the note had that exists here (person, company, deal, journalist → person); the body (markdown) as rich text; the Twenty author as the note's author when they are a member. A note whose targets are all on objects with no home here (a lead lookup) is _skipped_, and the report says so.                                                                                                                          |
| `tasks` / `taskTargets`                | Tasks, likewise; `TODO`/`IN_PROGRESS`/`DONE` → the task statuses, `DONE` completed now; the assignee through the member link.                                                                                                                                                                                                                                                                                                               |
| `leadLookups` (Lead Engine)            | **FR-CRMS-10 exclusions.** An _Assigned_ lookup excludes its address as `account_managed` with the account manager's name, `source` `twenty`, `externalRef` the lookup's id — through `ExclusionsService.addIn`, the same write an admin's route makes. One that becomes _Unassigned_ ends the exclusion (`removedNote` "Unassigned in Twenty"); the row stays.                                                                             |
| `leadViews` (Lead Engine)              | The person Twenty links (`personId`), else whoever has the lead's address, else a new person (`source` `twenty:lead`): the lead's fields land on them as custom fields under `lead_` (`lead_id`, `lead_assigned_am`, `lead_lifetime_value` + `_currency`, `lead_opportunity_stage`, …). Like a journalist, a lead only adds to a person that exists.                                                                                        |
| `messageLists` / `messageListMembers`  | A `lists` multiselect custom field on people whose options are the list names, each member's `lists` carrying the lists they are on, and one **shared view** per list ("List: _name_", filter `custom.lists contains name`) — what a member would build by hand to mail a list.                                                                                                                                                             |
| `messageCampaigns`                     | Outreach templates (name, subject, body as rich text). A campaign's send counts stay in Twenty: a template here has no sends of its own.                                                                                                                                                                                                                                                                                                    |

**Not read, by decision:** `leadLookupRequests` (an audit log of who looked up what), `inboundFailedLeads` /
`inboundTestLeads` (Lead Engine's intake diagnostics), `messages`, `messageThreads`, `messageParticipants`
(mail comes through each mailbox's own sync, P2-2), `blocklists` (each member's own), `attachments`
(bytes behind Twenty's file tokens; owed with a later package), `timelineActivities` (the timeline here is
written by the outbox from what the import does), `calendar*`, `callRecordings`, `dashboards`,
`recordShares`.

**Twenty's own fields on standard objects (doc 48 §11, the ledger's "Pinion workspace objects").**
A field the mapper did not read as a standard one becomes a custom field on the same object, through
`CustomFieldsService` (so the cache every list and filter reads is kept right). Its key is the field's
name in snake case (`prLink` → `pr_link`), its label the words of that; the type is read from the value
— an instant, a date, a select option (`GOOGLE_ADS`, `NEW`), a URL, text; a number; a boolean — and
Twenty's composites are flattened: a currency to a number (major units) and `<key>_currency`, a link to a
URL, an email, a phone, a name. A select grows the options a page brings. An empty answer (`""`, `null`)
clears the field; a value that disagrees with the definition's type is carried as that type when it can be
(a number as text) and left out when it cannot. Relations are never values.

## Idempotence: the links

`twenty_import_links (workspace_id, object, external_id) → (local_type, local_id, label)` is what makes a
run repeatable: a Twenty record already linked is **updated where it differs and otherwise left alone**
(`updateIn`'s "a no-op is no event" rule — P1-4a); one not yet linked that matches an existing record by its
unique key — a person's primary address, a company's domain — is **merged** into it (restoring a trashed
one first, PAR-002) rather than refused as a duplicate; one with no match is **created**. Two Twenty records
may map to one row (a journalist and a person with one address). A linked record an admin trashed here is
not resurrected: the run counts it _skipped_. A run writes as `actor: { kind: 'import', id: <run id> }`
(PAR-003's `import` actor, through `WorkspaceRunContext.actor`), so every imported record says so and every
event the outbox delivers — timeline, webhooks, stage rules — names the run.

The record diff was made key-order-insensitive on the way (`records/diff.ts`): `jsonb` stores an
object's keys in its own order, so `{ linkedin, x }` read back as `{ x, linkedin }` compared unequal and a
repeated run re-announced every person. The fix lands in the one helper the routes use too, so a `PATCH`
that changes nothing is a no-op there as well.

## Running

- **Where:** a BullMQ job per run (`twenty-import` queue, job id = run id, one at a time per process) in a
  worker process (`TWENTY_IMPORT_WORKER`, `1` by default like the other workers) — the mail-sync
  precedent for a long import. The run row (`twenty_import_runs`) is the truth: `phase` and a cursor per
  object say where it is; `report` what it did. One queued or running run per workspace (a partial unique
  index; a second start is a `409`).
- **A page at a time, never across the network in a transaction (#86):** a page of 60 (Twenty's ceiling) is
  read outside any transaction, in id order (so a resumed run sees every record once, whatever Twenty does to
  positions meanwhile); its relations' links are loaded; the records are mapped (pure); the custom-field
  definitions they need are put in place; then every record is written **in one transaction with the run's
  progress** — each record under a savepoint, so one the services refuse (a validation, a reference, a
  template variable Twenty's campaign uses and ours does not) costs only itself and is named in the report.
  A page that commits is never done again; a process that dies resumes from the page after it.
- **Retries:** a `429` or `5xx` from Twenty is retried with a doubling wait; a refused key or an object this
  Twenty has none of is final. A job that throws (the database, Redis) is retried by the queue from the
  cursor; the third failure marks the run failed with the last error. A run left queued or running by a
  dead process is given its job again at the next start.
- **Modes:** `full` reads everything; `changes` asks Twenty for what it updated since the last successful
  run's start (`filter=updatedAt[gte]:…`), and reads everything when there was none.
- **Cancel:** a request flag the runner reads after every page; the run ends `cancelled` where it is, and
  what it wrote stays mapped. The next run carries on.
- **Counts:** per object, `remote` (Twenty's total at the start of the pass), `before`/`after` (records of
  the object mapped here when the pass started and ended), and the outcomes, which sum to `read`.

## Data model (migration `20261012020000_twenty_import`)

- `twenty_import_settings (workspace_id PK, base_url, api_key_ciphertext, api_key_last4, configured_by_id,
updated_at)` — the key sealed with `SecretBox` (P1-5's one box), shown by its last four characters only,
  deleted when the connection is removed. The base URL is held to the webhook target rule (`url-guard`: a
  public host, never the API's own network; the development flag that admits a local receiver admits a local
  Twenty, which is what the cross-tenant suite runs).
- `twenty_import_runs (id, workspace_id, status, mode, since, phase, cursor, report, error,
cancel_requested, started_by_id, queued_at, started_at, finished_at, updated_at)`;
  `status ∈ queued | running | succeeded | failed | cancelled`; the state is checked by the database.
- `twenty_import_links` as above; `label` names a local thing with no row of its own (a list's name).

All three: RLS `workspace_isolation`, `FORCE`, app-role grants; `DELETE` only on the settings row (runs are
history, links are what makes a run repeatable). The cross-tenant suite proves one workspace sees none of
another's connection, runs, links or imported records, and that a run id from elsewhere is a `404`.

## API (`/api/w/:id/import/twenty`, all `workspace:admin`)

`GET` (overview: settings, latest run, what is mapped per object) · `PUT/DELETE settings` ·
`POST preview` (Twenty's count per object, read now; a refused key is a `422` at `apiKey`) ·
`POST runs` (`{ mode }` → `202`, the queued run; `409` while one is queued or running) · `GET runs` ·
`GET runs/:id` · `POST runs/:id/cancel`.

## The screen (P4-UI-2): Settings → Import from Twenty

Lazy route under settings (its own chunk; the initial bundle is unchanged at 177.65 kB), an admin's
section; a member who is not one is told whose it is. The connection card (URL, write-only key, _Check
connection_ → the counts table), the import card (_Everything_ / _Changes since last run_, _Start
import_; while a run goes: its status, the object it is reading, _Cancel import_, and the per-object
report read every 1–5 s until it is over) and the previous runs. Design tokens only; the counts tables are
`DataTableChrome`, so a phone sees cards (FR-CRMS-UI-12).

## Twenty's API, as used (PAR-066)

`GET <base>/rest/<objects>` with `Authorization: Bearer <key>`; `limit` (≤ 60), `depth` (`0` bare, `1` with
one-to-many relations — notes and tasks come with their targets), `order_by=id[AscNullsFirst]`,
`starting_after=<cursor>`, `filter=updatedAt[gte]:"<iso>"`; the answer `{ data: { <objects>: [...] },
pageInfo: { hasNextPage, endCursor }, totalCount }`. Composites as the instance reports them (name, emails,
phones, links, currency, address). The adapter (`twenty.http.ts`) is the only code that calls Twenty; the
fake answers the same grammar.
